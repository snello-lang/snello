## Task 2.1: Generic functions and types

**Description:** Type parameters on functions and types, inference at call sites, instantiation in the checker, monomorphization in the emitter.

**Acceptance criteria:**
- [x] `List<T>` and `Map<T, U>` from example 08 check and run (2026-10-18: in `examples/run/generics.teak`, cut from example 08; example 08 itself waits for `MaxBy`'s `Ord` and `Clone` bounds, task 2.5)

**Verification:**
- [x] Tests pass: `go test ./compiler/types/ ./compiler/emit/c/` (2026-10-18)

**Done:** 2026-10-18, in three slices. The third, monomorphization (`compiler/emit/c/mono.go`): a generic function or a method of a generic type is written once per set of type arguments the program uses, named after them (`Map_int_string`, `tk_List_int_Push`), from a worklist the calls fill, including the calls inside the instances themselves; an instance of a generic type is a C type of its own, declared when a value of it is first written. The emitter walks a generic body with a substitution in effect, and every type it reads from the checker's tables, including the types of the variables a body declares, passes through it. The checker gained the cycle check on calls that grow their own type parameter, which would otherwise make the instances endless. The review's probe found that the dropper named a generic type's `Drop` method without asking for its instance, so a `Box<T> impl Drop` failed to link; the call goes through the worklist now, and the run program has such a type.

**Progress:** first slice 2026-10-18, generic types in the checker (`compiler/types/generic.go`): a declaration with type parameters is a `Named` holding `TypeParam`s, and a use with arguments is an instance kept on the declaration, one per argument list, so identity stays a pointer comparison; an instance's underlying type and methods are the declaration's with the arguments substituted, computed on first use, and an enum instance has variants of its own so a pattern binds the arguments' types. A method's receiver names the type's parameters, and its body is checked once with each parameter as an owned type that moves unless bounded by `Copy`; other bounds are kept by name until traits exist. A variant of a generic enum takes its instance from the context. The C backend refuses a generic type by name until monomorphization. The review's probes found that a generic type referring to itself with a growing argument, `S<S<T>>`, hung the checker, and that a type containing itself by value, generic or not, was never refused and overflowed the stack (a stage 1 gap); `compiler/types/cycle.go` now refuses both once the declarations are resolved, before anything asks what a type contains. Second slice 2026-10-18, generic functions and inference (`compiler/types/infer.go`): a function's type parameters are on its signature, and a call finds its type arguments from those written, then by matching each parameter type against its argument's, the arguments that take their type from context last, then from the expected result; the moves and borrows happen as each argument is evaluated, so a generic call is checked as a plain one, and only the type check waits. Each call records its instance in `Info.Instances` for the backend. Variants of generic enums and literals of generic structs written without arguments infer the same way. A method may have type parameters of its own, on any type, which Go forbids and Rust allows; the owner directed that Teak's generics follow the mature model, so the one restriction, no generic method called through a trait used as a type, is for task 2.4. Example 06 now checks completely, and example 08 but for `MaxBy`, whose `Ord` and `Clone` bounds wait for traits. Still to do: monomorphization in the emitter, which must also refuse a generic function whose calls grow its own arguments; example 08's list code end to end.

## Task 2.2: Trait declarations and `impl`

**Description:** `trait` declarations with required methods; `impl` lists on struct and enum declarations; the check that every required method exists with the right signature; traits as bounds on type parameters.

**Acceptance criteria:**
- [x] A type missing a required method reports the trait and the method (2026-10-19: `Tri does not implement Shape: missing method Name() string`, at the trait's name in the impl list; a method with another signature reports both, `have (Sq) Label() int, want (ref Sq) Label() string`)
- [x] `TotalArea<T: Shape>` monomorphizes for `Circle` (2026-10-19: `examples/run/traits.teak`, for `Circle`, `Rect`, `Scaled<Circle>` and `Scaled<Scaled<Circle>>`)

**Verification:**
- [x] Tests pass: `go test ./compiler/types/` (2026-10-19; `go test ./...` too)

**Done:** 2026-10-19, one slice (`compiler/types/trait.go`). A trait is a type of its own, as an interface is in go/types, but nominal: a `Named` lists the traits it implements and a `TypeParam` the traits that bound it, as traits now rather than names. A trait's methods are signatures over its own `Self` type parameter, so the impl check is a substitution, `Self` for the type, followed by a signature comparison, and a bound's method on a `T` is the same substitution with `T` for `Self`, made once per parameter and method. The trait lists (impls, refinements, bounds) resolve before any type does, since a field of type `Copied<string>` asks about `Copied`'s bound and a type's Copy-ness asks whether it implements `Drop`; a bound question asked while the types are still resolving waits, as the storable questions do. A type argument is checked against its bounds wherever one is formed: a written instance, an inferred call, a variant or a struct literal. The standard traits are predeclared in the universe, so `impl Drop` and `T: Copy` resolve like any trait; `Drop` requires `func (t mut Self) Drop()`, `Copy` as a bound is satisfied by structure, and the other eleven admit everything until task 2.5 gives them methods; `impl Copy` on a type with a field that moves is not refused yet, which is task 2.5's own acceptance criterion. The checker's allocation count over the core programs rose from about 1,890 to about 1,910, one trait list and one visited set per type with an impl list; the baseline in `CODING_STANDARDS.md` is updated. The C backend writes a call through a bound against the type argument's own method, directly, one per instance (`boundCall` in `compiler/emit/c/expr.go`). Refinement cycles are refused, and a missing method reached through two traits of one impl list is reported once. Left for their tasks and reported as "not supported yet": default methods, trait fields (2.3), a trait as a type (2.4), generic traits and generic trait methods (example 18), and the operator traits' arguments, `Add<Vec3>` (example 16, 2.5). ## Task 2.3: Defaults, fields, super, resolution order

**Description:** Default methods inherited by implementors; trait fields stored inline and set at construction; `super`; the resolution order (own methods, then the `impl` list right to left); trait refinement.

**Acceptance criteria:**
- [ ] Example 07 prints `[logged] circle with area 3.14` then `a rectangle` (needs `super`, trait fields, a trait as a type from 2.4, and `math.Pi` from 2.6)
- [x] Two traits providing the same default with no override on the type reports an ambiguity (2026-10-19: `G inherits Greet from both Waver and Greeter: declare G.Greet to choose`, once per method)

**Verification:**
- [x] Tests pass: `go test ./compiler/types/ ./compiler/emit/c/` (2026-10-19)

**Done:** 2026-10-19, in three slices, below. The first acceptance criterion waits for a trait as a type (2.4) and `math.Pi` (2.6); example 07 checks but for those two. Third slice, `super`: `super.M(args)` is checked as `recv.M(args)` with `M` found differently (`superCall` in `compiler/types/trait.go`): inside a trait's default, the first default for `M` among the traits it refines in their order; inside a type's own method, the first among the type's traits. The `super` identifier is recorded as a use of the receiver variable, so the move and borrow passes see an ordinary receiver, and the C backend resolves the definition per implementing type from the resolution order (`Named.SuperMethod`), so a default's copy for each type calls the right next definition. A default's C copy is now named after the type and the trait, `tk_Circle_Shape_Describe`, since a type may need the default behind the one it took. The next definition is read in the implementing type's order, so it may belong to a trait the current one does not refine when the impl list puts one between (`Gift impl Fancy, Wrapped` in the run program); the book states the rule. The review's probes found three holes, closed: a value receiver passed through `super` was not recorded as moved (the operand carries the `super` expression now); the `super` identifier had no recorded type, so a `mut` receiver calling a `ref` default produced C that did not compile (the receiver's type is recorded); and a redeclared method was compared only with the first definition each refined trait could see, so two defaults behind one trait could leave the checker's type and the backend's target apart (`checkRedeclared` compares with every trait in the refining trait's order). `super` inside a closure in a method captures the receiver, through `Checker.recv`, which closures do not swap. Found and fixed on the way, a stage 1 hole: a `mut` method called on a variable that is itself a `ref` borrow, `func f(n ref Node) { n.Bump() }`, was accepted; only a value reached through a borrow, `xs[0].Bump()`, was refused. The receiver check now refuses both (`cannot borrow n as mut: n is a ref borrow`), with cases in `compiler/types/borrow_test.go`.

**Progress:** first slice 2026-10-19, default methods and the resolution order. A default is a generic method over `Self`: its body is checked once with `Self` as a type parameter bounded by the trait, so it sees the trait's methods and nothing else, and the C backend writes one copy per implementing type that takes it through the instance worklist, named as the type's own method would be (`tk_Circle_Describe`). The checker computes each type's resolution order from its impl list (`linearize` in `compiler/types/trait.go`): right to left, each trait followed by the traits it refines, duplicates kept at their last place, which is the linearization that puts a refining trait before the traits it refines wherever the list names them; the first provider in that order wins, an own method overrides every default, a second provider the winner does not refine is the ambiguity error, and a default a type does not take must still agree with the method it has. A default of one trait satisfies another trait's requirement. A trait that redeclares a method of a trait it refines must give it the same signature, checked once at the trait (`checkRefinements`): the review's probe found that without it a type was taken to implement the refined trait with a method of another type, and a bound call typed by the refined trait reached it. `examples/run/traits.teak` runs an inherited default, an override, a refining trait's override, a generic instance's copy and an inherited `Drop`; `examples/run/traits.out` has the output. Second slice 2026-10-19, trait fields: a trait's `var` fields are resolved with its lists, and when an implementing struct resolves they are appended to its own fields in its resolution order, with `Self` read as the type, so literals, reads, writes, printing, layout and the cycle and Copy checks need nothing more (`traitFields` in `compiler/types/trait.go`); a `Self` value inside a default, or a bounded `T`, reaches a field through its bound as it reaches a method (`boundField`). A field named twice, by the type and a trait or by two traits, is refused, and so is a trait with fields on a type that is not a struct. The review's probe found that a field putting `Self` in owned data, `var kids []Self`, was asked the storable question only of `Self`, so a type holding a borrow could be stored through it and read after its owner died; the substituted type is asked again (`storableParts`), through the same pending list a struct's own fields use. The run program's `Named` trait carries `name` and a default `Name` reading it, and its `Loud` and `Rect` wrap the default they override with `super`. A disagreement settled by the owner 2026-10-19: example 07's `func (n ref Self) Name() string { return n.name }` moved a `string` out of a borrowed `Self`, which the ownership rules refuse for a plain struct too; the rule stands, the example returns `ref string` and borrows the field, and the design document says a trait field obeys a struct field's rules with no exception. Still to do: `super`.

## Task 2.4: Trait as a type

**Description:** A trait name used as a type is an owned interface value: a pointer to the owned data and a pointer to a table of the holding type's methods, one allocation and one indirect call; trait fields reachable through synthesized accessors.

**Acceptance criteria:**
- [x] `[]Shape` in example 07 holds a `Circle` and a `Rect` and dispatches correctly (2026-10-19: the same slice, `PrintAll` and `TotalArea` over it, runs in `examples/run/traits.teak`; example 07 itself builds once `math.Pi` exists, task 2.6)
- [x] Assigning a non-implementing type reports the missing trait (2026-10-19: `cannot use b (Blob) as Shape in return: Blob does not implement Shape`)

**Verification:**
- [x] Tests pass: `go test ./compiler/emit/c/` (2026-10-19)

**Done:** 2026-10-19, in two slices. The second, the C backend (`compiler/emit/c/trait.go`): a trait value is two pointers, to a table and to the data it owns on the heap. The table type is written once per trait, with the drop, one function per method a value can call (`Trait.ValueMethods`, which leaves out the methods written with `Self`) and one accessor per field (`Trait.ValueFields`). A table is written per implementing type and trait when a value first becomes a trait value, in `valueTo`, the one place every assignment, argument, return and element passes: each entry is an adapter that casts the data pointer and calls the method the type has for that name, resolved as any call on the type is (`methodNameOf`, shared with bound calls), so an own method, an inherited default, `super` behind it and a generic instance's method all serve. A ref receiver is passed as the value in C, so the adapter copies the data; a mut receiver is the pointer; a value receiver takes the data and frees the box, as the trait value was consumed. A field accessor returns a pointer into the box, so reads, writes and partial moves go through it unchanged. Dropping a trait value calls the table's drop, which drops the held value and frees the box, unless the value moved away and left no table; a trait value counts as guarded against panics, since what it holds may have a Drop method. A generic function instantiated with a trait type dispatches the same way (`TotalArea<Shape>`). Printing a trait value is refused with a message, where the printer would otherwise have recursed into itself. The checker also refuses reaching a field written with `Self` through a trait value, as it refuses such a method. The review's probes found four holes, closed: a method called on a trait value built in the same expression, `Make().Describe()`, leaked the box and skipped the held value's Drop, since the receiver did not pass through the operand path that holds a lent temporary (it does now); a trait standing as a type argument whose bound has a method written with `Self` passed the checker and produced C that did not compile, so a trait value now satisfies a bound only when nothing in the bound's traits mentions `Self`, refused with the method or field named (`selfMention`); a struct holding a trait value whose methods take the struct was refused as holding itself by value, since the table's function pointer types were defined rather than declared while the struct was being defined (`entry` declares them); and a stage 1 hole, a value built in the argument and lent as `ref Make()` was never dropped, for a plain `Drop` struct silently, for a trait value as a leak the debug build reported (`lent` looks through the `ref`). The run program covers each. Deferred and recorded: a refining trait's value as the refined trait, printing a trait value.

**Progress:** first slice 2026-10-19, the checker. A `Trait` is usable as a type wherever a type is written; `assignable` converts an owned value of an implementing declared type into it (`convertsToTrait`), and the mismatch message says why not: a borrow, another trait's value (not yet), a type that does not implement the trait, or no declared type at all. A trait value is owned and not Copy, holds no borrow, satisfies its trait as a bound, and has the trait's methods and fields with the trait itself for Self (`valueMethod`, `valueField`), found through the existing selector path so the receiver, move and borrow rules apply unchanged; a method whose parameters or results mention Self is refused through a trait value. The review's probe found that a type holding a borrow could become a trait value and the borrow then escape unseen; the conversion refuses such a type. Two requirements on the second slice: a field accessor must return a pointer into the box, since the move pass accepts a partial move out of a trait value's field and the emitter empties the moved place through it; and `print` of a trait value is accepted by the checker, so the backend prints through the table or refuses it. A composite literal of a trait type is refused by the existing literal check, and `==` on trait values by the existing comparability rule. A loose end for 2.5: the checker has no rule for what may be a map key, so `map[Shape]int` is accepted today as any key type is; the rule belongs with `Hash` and `Eq`, and a trait value will not be a key. Example 07 now checks but for `math.Pi`. The C backend reports a trait type as unsupported until the second slice: the boxed value, a method table per implementing type and trait with the resolved methods, field accessors and the drop, and the conversion at every place a value becomes a trait value.

**For the owner at the checkpoint.** The decisions the stage made on its own, to confirm or revise, and the loose ends it carries, each recorded where it arose:

1. *The stage closes with seven examples pending.* 02, 03, 12, 13 and 18 wait for `spawn`, channels and `sync`, which the plan's own line gives to stage 3; 04, 17 and 19 for `heap`, `net` and `regexp`, placeholders for a later library. Thirteen run and compare; `examples/suite_test.go` names the seven with their reasons.
2. *A closure copies a `Copy` value it only reads* and keeps the value of that moment; it holds no borrow and may be returned or stored (`00-syntax-conventions.md`, chapter 6). The design said `ref` for every read before; example 18 said copy. A function value is never copied in, since its borrows are its holder's.
3. *A type argument may hold a borrow* for a generic function that only borrows values of the parameter, a `mut` one alone among them, and returns none (`00-syntax-conventions.md`, chapters 6 and 12). It is what lets `fmt.Fprintln` and `io.Copy` take a `bufio.Writer`.
4. *Two checker gaps found by review and left open*: a `mut` argument of a borrow-holding type is not recorded as holding the other arguments' borrows, so `store(dst mut (View?), v View)` keeps a borrow past its value; and a borrow built inside a nested literal, `Outer{in: Inner{s: ref s}}`, has no record for the returned-borrow analysis to follow. Both predate the stage; both want the holder records extended.
5. *A field may be moved out of a value whose type has a `Drop` method*, and `Drop` then runs over the emptied field; Rust refuses the move (task 2.5). Deferred calls do not run when a panic ends the program (stage 1, left here).
6. *`rc` has no interior mutability*: a tree with `Weak` back-links, as `examples/01-tree/README.md` describes, cannot be built, since a node is shared by the time its link is set (`05-standard-library.md`). A `Cell`-like type, or leaving linked structures to arenas, is the choice.
7. *A library type prints as its insides*: an `Rc` prints as `{Some({1 0 Some(3)})}`. Types implementing `Error` print as their message by a rule of their own; a `Stringer`-like trait would be the general answer.
8. *Limits that wait for other features*: `Fields`, `Split` and `Lines` are typed as a slice of borrows a program cannot write, and a range over an arena or a scanner's lines is a loop, until the iterator trait; `time.After` and `Tick` wait for channels; a generic trait is not a type and a bound's arguments are not inferred from the implementing type (chapter 11); arrays are not sliced, pushed to or ranged over, and are not `Eq` or `Hash` by structure (chapter 9); `os.Exit` and `panic` are known to the checker by name until a signature can say `never`.
9. *Examples changed to the design's spellings* rather than the design to theirs: `append` to `Push`, `sort.SliceBy` to `SortBy`, `ToOwned` to `Clone`, `unreachable()` to `panic`, `os.Args()` to `os.Args`, map reads taken apart to `Get`, and `?` outside a function returning an `Option` to `??`; example 11's helpers were written.

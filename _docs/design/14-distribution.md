# Distribution

Status: designed, and partly built. Built: the release workflow, the scripts under `release/` that prepare a release, build its archives and smoke-test them, and the changelog; no release has been cut yet. Not yet built: the install scripts, the Homebrew formula, the winget manifests, the container image and the GitHub Action, each a task of its own.

The compiler is one binary that carries the runtime and the standard library inside it, so one file is the whole toolchain but for the system's clang. Today that file reaches a developer in one way, built from source with Go, which the language's own users have no reason to have. This note decides how a release of Snello is numbered, when it is cut, what it holds, how anyone can trust it, which platforms it ships for, what a developer needs beside it, how it is installed and where it goes, and what a `0.x` release promises; the tasks that build the release workflow, the install scripts, the package managers, the container image and the documents each follow it.

## The precedents

- **Go**: a minor release every six months by the calendar, whatever is ready, and the latest two minor releases get fixes; one archive per platform on go.dev/dl, named by version, system and processor, `go1.27.2.linux-amd64.tar.gz`, a `.zip` and an installer on Windows; builds reproducible bit for bit since Go 1.21, with `-trimpath` and no build ID; telemetry collected only when turned on, since Go 1.23; a `go` line in `go.mod` naming the version a module is written for.
- **Rust**: a release every six weeks on a train of three channels, nightly, beta and stable; `rustup` installs and switches toolchains, and every nightly is kept and pinnable by date; a tier policy saying what each target is promised.
- **Zig**: one archive per platform with clang and LLVM inside it, so that a download builds C with nothing installed, at about ten times the size of a compiler alone; builds from master published beside the releases.
- **Deno and Bun**: one static binary; installed by `curl -fsSL … | sh` on Unix and `irm … | iex` in PowerShell, by Homebrew, and by winget and Scoop on Windows; a canary build of every commit, which `deno --version` names by the commit.
- **The supply chain**: SLSA's build provenance, which GitHub's attestations produce and `gh attestation verify` checks; Sigstore's keyless signing, `cosign`, from a workflow's own identity; an SBOM in SPDX; the OpenSSF Scorecard's checks of a repository's hygiene, which the OpenSSF runs over the large projects itself; Keep a Changelog's form, which Rust's `relnotes` drafts from merged pull requests and Go's `relnote` from fragments written with each change.

Taken: Go's two supported releases, its archive names and its reproducible build; Rust's tiers, which the platforms note already follows, and its release notes drafted from the changes; Deno's one binary, its two scripts and its canary that names its commit; GitHub's provenance and Sigstore's signatures, since the workflow that builds a release can sign it with nothing kept as a secret. Left out: a release calendar, section 2; a nightly, a beta or any channel but the releases, section 2; a toolchain manager like `rustup`, since one binary needs no manager and the install script run again is the upgrade; bundling clang, weighed in section 7; and a bot that opens the release pull request and pushes the tag, weighed in section 1.

## 1. Versions

A release is a Semantic Versioning 2.0 version, `MAJOR.MINOR.PATCH`, the scheme the module file's `snello` line already names a release by (`08-packages.md`, decided 6), and the first is `0.1.0`. A release is a tag `vX.Y.Z` on `main`, and nothing else: no release branch exists until a fix must be backported (section 3). A patch release fixes the compiler and changes no rule of the language; a minor release may change anything while the major is `0`, and after `1.0.0` only what SemVer allows a minor to change.

The version is written in two places that must agree, and a release is refused when they do not. A maintainer prepares a release in a pull request like any other: raises `version.Current`, the constant `snello version` prints and the module's line is checked against, and adds the release's changelog, a file of its own under `changelogs/` with a line in the index `CHANGELOG.md`, which `release/changelog.sh` writes from the Conventional Commits since the last release, grouped under Keep a Changelog's headings, so that the changelog is read from the commits and not typed; merges it; and pushes the tag on the merge, `git tag -a v0.1.0 -m 'snello 0.1.0' && git push origin v0.1.0`, as a maintainer tags Go itself, Zig and most Go projects. The release's build refuses a tag whose version is not the constant and a version with no changelog file, in its first minute, so a slip is caught before anything is built. A pre-release, `0.1.0-alpha.1` as SemVer writes one, is prepared and tagged the same way and published marked as a pre-release and never as the latest, so that a build reaches people before the version it leads to and a script asking for the latest release skips it; its changelog covers what came since the last tag of any kind, and a release's covers everything since the last release, the pre-releases between them included, so that a release's notes are whole, as Rust's and Go's are. A bot that keeps a release pull request open and pushes the tag, release-please, was weighed and left out: it needs a maintainer's token in a workflow, two files of its own and a pull request it rewrites on every push to `main`, and a tag pushed by a machine is one nobody decided; the maintainers decide what is released and when.

## 2. When a release is cut

**When the maintainers decide**, of what `main` holds on the day: a minor release when there is something to ship, a patch release when a fix cannot wait, a program the checker accepts and should refuse, a memory-safety hole, or a build broken on a tier-1 platform. No calendar: Go and Rust release by the calendar with a team that keeps it, and a cadence promised and missed costs more trust than none; a release that is a decision is one someone stands behind, and the release notes say what it holds.

**One channel.** A release is a tag, and nothing else is published: no nightly and no preview, since what is published is what a maintainer decided to release, and a build of `main` for trying is a workflow run's artifact, which the release workflow started by hand leaves for ninety days without publishing. The channel is stamped into the binary at the link, `version.channel`, `stable` for a release, and a build from source says `devel`, which is what it is.

## 3. Support

The latest two minor releases get fixes, as Go fixes its latest two: a fix for the compiler or the runtime that a patch release would carry lands on `main` and, when the previous minor is still supported and the fix matters there, on a branch `release-0.N` made from that minor's tag at the first backport, from which its patch release is tagged. A release older than the two gets nothing, and the release notes say so. Security fixes go to both supported releases on the day they are released.

## 4. What `0.x` promises

Nothing between minor releases. A `0.x` minor may change the language, the library or the command, and a program may need changing; the release notes say what changed and what to change, under a heading of their own, before anything else, since that is what a reader of release notes is looking for. Two things keep a change from being a surprise. The module's `snello` line says which release a module was written for, so a release that changes a rule applies it to the modules that name it or a later version and compiles the older ones as they were written, and a compiler refuses a module written for a later release than itself with what to do (`08-packages.md`, decided 6). And a patch release changes no rule at all. After `1.0.0`, the promise is SemVer's: a program written for `1.x` builds with every later `1.y`.

## 5. What a release holds

**One archive per platform**, named as Go names its own, by version, system and processor: `snello-0.1.0-linux-amd64.tar.gz`, `snello-0.1.0-linux-arm64.tar.gz`, `snello-0.1.0-darwin-amd64.tar.gz`, `snello-0.1.0-darwin-arm64.tar.gz`, `snello-0.1.0-windows-amd64.zip` and `snello-0.1.0-windows-arm64.zip`, a zip on Windows because Windows opens one with nothing installed. Each unpacks to a directory of the archive's name holding the `snello` binary, `snello.exe` on Windows, the `LICENSE` and the `README.md`, and nothing more: the binary carries the runtime and the standard library, and a release has no library directory, no headers and no second file to keep beside the binary.

**`SHA256SUMS`** lists the digest of every archive, signed by Sigstore with the workflow's own identity, `cosign sign-blob` with no key kept anywhere, the signature beside it as `SHA256SUMS.sigstore.json`; a developer checks an archive against the list and the list against the signature, and the install scripts check the list for them. **Build provenance** for each archive, SLSA's statement that this workflow on this commit built this file, which GitHub's attestations make and `gh attestation verify snello-0.1.0-linux-amd64.tar.gz --repo snello-lang/snello` checks. **An SBOM** per archive in SPDX, listing what the binary is built from, which is Go's standard library at one version and nothing else, since the compiler has no dependency; short, and true.

**Reproducible.** The compiler is pure Go, so one Linux runner builds all six platforms with `CGO_ENABLED=0`, `-trimpath`, the build ID cleared, and the commit and its time read from the build information Go records, which is what `snello version` prints; the files in an archive carry the commit's time and a fixed owner and mode, so that the archive, not only the binary, is the same wherever it is built. The workflow builds each platform twice on different runners and refuses to publish a difference: a release whose bytes depend on the machine that built it cannot be checked by anyone else, and the check is cheap. The **changelog** is one file per release under `changelogs/`, in the Keep a Changelog form, written by `release/changelog.sh` from the commits since the last release, with `CHANGELOG.md` at the root as the index of every release, which stays short however many there are, where one file for every release would grow without end; the release's notes are the release's file, with the tier of each archive (section 6) and the checksums under it.

## 6. Platforms

A release ships the six platforms of `12-platforms.md`, at the tier each holds there: `linux/amd64` and `linux/arm64` with glibc, `darwin/amd64` and `darwin/arm64`, and `windows/amd64` at tier 1, and `windows/arm64` at tier 2. A tier-1 archive is smoke-tested on a runner of its platform before the release is published, unpacked and made to build, run and test `snello new`'s program with nothing but the archive and the runner's clang, and a failure publishes nothing: a release that fails its own first five minutes on a platform it promises is not a release. A tier-2 archive is built the same way and smoke-tested where a runner exists, `windows/arm64` on GitHub's arm64 Windows runner, and a failure there is recorded in the release notes and fixed before the next release, which is what tier 2 promises; it does not stop the release. The release notes name each archive's tier so that a developer knows what is promised of the one they download, and a platform that moves between tiers (`12-platforms.md`, section 1) moves in the next release's notes.

The `snello` binary itself is a static Go program and runs on any Linux, musl's included; what it builds runs on the systems the platforms note names, kernel 5.4 and glibc 2.29 or later on Linux, macOS 14.4 or later, and Windows 10 or Windows Server 2016 or later. There is no musl archive and no need for one: the Linux archive runs on Alpine, and whether the programs it builds do is the platforms note's question, not this one's.

## 7. What a developer needs beside the binary

**clang 15 or later**, the first that reads the IR the backend writes, whose pointers are opaque, which `snello doctor` checks by compiling a line of that IR rather than reading a version number. **A linker that links with clang's link-time optimization**, since a release build links with `-flto`: on Linux the distribution's own `clang` package brings one, and the install line names `clang` alone, which the distributions job of CI shows on every change by running a developer's first five minutes on a clean Debian 13, Ubuntu 24.04, Fedora and Arch with nothing installed but that package, `snello doctor`'s link check among them; the build never names a linker. On macOS, clang comes with Xcode's Command Line Tools, `xcode-select --install`, and Apple's linker links its LTO; Homebrew's formula depends on `llvm` instead, so that a Mac without the Command Line Tools gets a clang with the formula. On Windows, clang and `lld-link` come from LLVM's own installer, `winget install LLVM.LLVM`, and the SDK and the C runtime from Visual Studio's Build Tools with the C++ workload, which clang finds by itself; `snello doctor` checks both. **The C backend** needs any C compiler, `cc` or the one `CC` names, clang on Windows. **git** only to fetch a module a `require` line names by version. **Go, never**: Go is what the compiler is written in and a contributor's tool.

**Bundling clang** is weighed and left for `1.0`. Zig ships clang and LLVM inside its archive, and a download then builds C and links with nothing installed, at about ten times the size of the compiler alone, and with a copy of LLVM to keep current and to build on every platform; `snello doctor` with its install line makes the one missing piece a one-line fix, and the container image covers a machine with nothing on it. The question is reopened for `1.0`, when a self-contained download may be worth its size.

## 8. Ways in, and where the binary goes

- **`install.sh`**, POSIX `sh`, under `release/` with the rest of the release's tooling and served from the repository's `main`, `curl -fsSL https://raw.githubusercontent.com/snello-lang/snello/main/release/install.sh | sh`. It finds the platform, downloads the archive of the latest release, or of the version `SNELLO_VERSION` names, or of the newest pre-release while no release exists yet, which it says, since GitHub's latest release is never a pre-release, checks it against `SHA256SUMS` and refuses a mismatch, verifies the provenance when `gh` is installed and says so when it is not, unpacks the binary into `~/.local/bin`, the directory the XDG base directory specification sets aside for a user's own programs, or into `SNELLO_INSTALL`, says when that directory is not on the path and how to add it, and ends by running `snello doctor`; when a build still needs clang, the script asks whether to install it now and on yes runs the system's own package manager or Apple's Command Line Tools, so that one line ends with a machine that builds, as `rustup` ends with a working toolchain; the question goes through the terminal, since a script piped into `sh` has the script on its standard input, and `SNELLO_YES=1` answers it for a machine with nobody at the keyboard. What stays the developer's is what no script should take: a `sudo` password, Apple's dialog, an installer's own prompt. Run again, it upgrades; `rm ~/.local/bin/snello` uninstalls, and the book says so.
- **`install.ps1`**, PowerShell 5.1 or later, the same from `irm https://raw.githubusercontent.com/snello-lang/snello/main/release/install.ps1 | iex`: the archive of the processor, the checksum, the binary into `%LOCALAPPDATA%\Programs\snello`, the directory Windows sets aside for a user's own programs, or `SNELLO_INSTALL`, added to the user's path when it is not there, and `snello doctor` at the end; on Windows the script also puts LLVM's directory on the path, which LLVM's installer does not, and offers LLVM and then Visual Studio's Build Tools with the C++ workload through `winget`, each on a yes.
- **Homebrew and winget, after the first release**: `brew install snello-lang/tap/snello` from a tap whose formula the release workflow is to rewrite with each release's version and checksums, depending on `llvm`; and `winget install snello-lang.snello` from manifests the workflow is to submit to `microsoft/winget-pkgs`, naming LLVM as the dependency. Neither is built: a package manager is how a developer keeps tools current, not how the first install happens, and the scripts carry the first release.
- **The container image and the GitHub Action**, for a machine with nothing on it and for continuous integration, each with a task of its own.

**Signing for the systems' gatekeepers** comes when a download link exists, not before. macOS quarantines a binary a browser downloaded and refuses one not signed with a Developer ID and notarized; `curl`, Homebrew and the script download without the quarantine, so nothing in the ways above needs it. Windows' SmartScreen warns of an unsigned program a browser downloaded, and the script and winget sidestep it the same way. A download link on a website is what makes an Apple Developer ID and an Authenticode certificate necessary, and the task that adds the link adds the signing.

## 9. The release is made by the workflow, and trusted by its record

The procedure, step by step with the reason for each step, is `release/README.md`, beside the tooling. A maintainer pushes the tag, and the tag starts the release workflow: the six builds, twice, compared; the archives, `SHA256SUMS`, its signature, the provenance and the SBOMs; the smoke test of each archive on its runner, Windows' with LLVM installed as the test workflow installs it and the Build Tools GitHub's Windows runners carry; and only then the release made public, a draft until every tier-1 smoke test passed. Started by hand, the workflow is a dry run: the same builds and checks, and no release. The workflow is the only thing that makes a release, and its record is what a developer trusts: the provenance names the commit and the workflow, the signature the workflow's identity, and the repository that holds it keeps the hygiene the OpenSSF Scorecard checks for, every action pinned by its commit hash, each job's token given the least it needs, Renovate keeping the actions, the image's base and Go current and pinned by digest, and the rule that changes come through a pull request applied to administrators too; the Scorecard's own workflow and badge are left out, as Go and Rust leave them out, since the OpenSSF scores a public repository without them.

## 10. No telemetry

The command reports nothing to anyone: no usage, no crash, no version check at start. A new language cannot spend the trust an opt-out collection costs, and Go's own, collected only when turned on, is the most a toolchain should ask; Snello asks nothing. `snello` opens a network connection for two things alone, both the developer's own doing: `git`, run to fetch a module a `require` line names by version, and `snello doc -http`, which serves the local machine's browser. Whether a newer release exists is told by the release notes and by the package manager that installed it, never by the command.

## Before 1.0

A `1.0.0` is a promise that `1.x` programs build with every later `1.y`; `0.x` releases make none, and what `1.0` needs beyond them is the stages that remain. The language and the library have had a release cycle with no breaking change, and the module's `snello` line has carried a rule change once, so that the mechanism is known to work. The language server exists, since a language with no editor support is not finished. The question of bundling clang is answered (section 7), and musl's tier is decided (`12-platforms.md`, section 2). `windows/arm64` holds tier 1 or is named tier 2 in the release notes for a reason. A website with a download link exists, with the Developer ID and the Authenticode certificate it needs. A security policy names where a hole is reported and how long a fix takes. Until then every release is `0.x`, cut when the maintainers decide, and says so.

## Decisions

**Decided 1: SemVer, the tag by a maintainer's hand, held to the constant.** A release is prepared in a pull request that raises `version.Current` and adds the release's changelog file, written from the commits, and is cut by a tag the maintainer pushes, the common practice; the release's build refuses a tag that is not the constant, so the version is written twice and can never disagree. A bot for the pull request and the tag was left out: more machinery than a few releases a year are worth, and a tag nobody decided.

**Decided 2: releases when the maintainers decide, one channel.** No calendar, since a promised date missed costs more than none and the maintainers decide what is released and when; no nightly and no preview, since nothing is published that a maintainer did not decide to release, and a build of `main` for trying stays a workflow run's artifact.

**Decided 3: one archive, one binary, built twice.** An archive holds the binary, the license and the README, since the binary carries everything else; it is reproducible, signed by the workflow's identity, attested and listed in an SBOM, because each is what a toolchain is expected to ship now and each costs the workflow a step and the project no secret; it is built twice so that the reproducibility is checked and not claimed.

**Decided 4: six platforms, each at its tier, and a tier-1 failure publishes nothing.** The release ships what the platforms note supports, at the tier it holds there, and names the tier beside each archive; a smoke test on each tier-1 platform stands between the build and the public release, since the first five minutes are what a release is for.

**Decided 5: clang stays the system's, until 1.0.** The system's package, the Command Line Tools or LLVM's installer, with `snello doctor` naming the one line that installs what is missing; bundling clang is weighed and reopened at `1.0`, when a self-contained download may be worth ten times the size.

**Decided 6: a script for each kind of system first, a package manager after.** `install.sh` on Unix and `install.ps1` on Windows, because a script is the fastest first time, checks what it downloads, and never passes through a browser, so no system quarantines what it installs; Homebrew and winget after the first release, because a package manager is how a developer keeps tools current, not how the first install happens; into `~/.local/bin` and `%LOCALAPPDATA%\Programs\snello`, the directories each system sets aside for a user's programs, with no privilege asked.

**Decided 7: nothing reported, ever.** No telemetry and no version check, so that running `snello` never opens a connection the developer did not ask for.

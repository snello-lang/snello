# Tasks and channels: the runtime

Status: decided and built, in `runtime/c/sched.c`, `chan.c`, `sync.c`, `timer.c`, `net.c`, `lookup.c` and `scope.c`. This note says how a Snello task runs and how a channel works underneath the rules of `03-ownership-across-tasks.md`: the interface the compiler emits, the runtime as it stands, the cancellation model, the decisions that hold, and at the end the history of how each part came to be what it is, with the measurement behind each change. The compiler is written against the interface alone, so every change below changed nothing the compiler emits.

## The problem

C has no model of a task. It has the system's threads, locks and condition variables, and nothing that lets many tasks share one thread. A language whose concurrency is "start a task, talk through channels" needs more than that: tasks must be cheap enough to start by the thousand, a task that waits must not cost a thread, and a channel must hand a value from one task to another without either one reaching the other's memory. None of that is a property of C. It is a property of a runtime written in C: a scheduler is a program that keeps a list of tasks and decides which one the thread runs next. Snello's runtime got that program in two steps, a thread per task first, then the scheduler that replaced it; the history section has the first.

## The interface

Every concurrent construct the compiler emits lowers to one of these calls and nothing else. The emitted code never names a thread, a lock or a condition variable.

| Snello | Runtime call | Meaning |
|---|---|---|
| `spawn f(x, y)` | `sn_spawn(run, args)` | starts a task; `run` is a trampoline the compiler writes for the call site, `args` the arguments moved into a block the task owns and frees |
| `make(chan T)`, `make(chan T, n)` | `sn_chan_make(sizeof T, n, drop, "file:line")` | a new channel with a handle of both ends; `n` is 0 for an unbuffered one; the position is for the deadlock report |
| `ch.Clone()`, a handle dropped, a `chan T` moved where one end is wanted | `sn_chan_clone(ch, dir)`, `sn_chan_drop(&ch, dir)`, `sn_chan_narrow(ch, kept)` | the counts of the ends, by the handle's static direction; the last sending handle gone ends the channel, the last receiving one frees its senders, the last of either frees it |
| `ch <- v` | `sn_chan_send(ch, &v)` | moves `v` into the channel; blocks until a receiver takes it or there is room; drops `v` when no receiving handle remains |
| `<-ch` | `sn_chan_recv(ch, &out)` | moves the next value out, into memory the receiving task owns; false once the channel has ended and is empty, which the compiler turns into `None` |
| `ch.Open()` | `sn_chan_open(ch)` | whether a receiving handle remains |
| `len(ch)`, `cap(ch)` | `sn_chan_len`, `sn_chan_cap` | values waiting, room for values |
| `select { ... }` | `sn_select(cases, n, has_default)` | waits for the first case that can proceed and returns its index; with `default`, returns at once when none can; a send case with no receiver left proceeds by dropping its value |
| `for v := range ch` | `sn_chan_recv` in a loop | until the channel has ended and is empty |

A channel handle is a pointer to the channel, and any number of tasks may hold one, each its own, cloned from another. A value sent is copied bit for bit into the channel and the sender's place is emptied, as any move empties its source; a value received is copied out the same way. The copy is of the value's bytes, not of what it owns: a slice sent on a channel moves its pointer, length and capacity, and the receiver owns the elements from then on. This is what makes "sending moves, receiving owns" true at run time with no bookkeeping at all.

## The runtime as built

The design document decided an M:N work-stealing scheduler, blocking-looking I/O over the system's poller, and no async/await. Two properties of the language make it simpler than its counterparts elsewhere: the compiler knows the layout of every frame and the extent of every borrow, so a task's stack holds nothing the runtime has to find or scan, as a collector would have to; and the `Send` rule means that whatever a task owns is reachable from no other task, so the scheduler may run a task on any thread and move it between threads freely.

### Tasks and workers

A task is a coroutine, not a thread: a stack of its own and a saved set of callee-saved registers. Switching from one task to another is `sn_switch`, twenty instructions of inline assembly per processor, arm64 and x86-64, with no system call; the frame it saves is 160 bytes on arm64 and 64 on x86-64, more on Windows, where it also carries the stack's bounds for the thread's information block. A task's state is one atomic word changed by compare-and-swap, running, runnable, parking, parked, preempted, yielded or done, with a pending wake as a bit, so that a wake and a park race on one word and neither is lost.

N worker threads, one per core with the main thread among them, run M tasks. Each worker keeps a ring of 256 runnable tasks its own thread alone writes at the tail and every taker takes from by a compare-and-swap of the head, stealers taking half; a full ring sends half to the inject queue. A spawning loop can outrun its workers, most of all on a machine whose cores other programs share, and each task it makes holds its record and its stack until a worker runs it, so a spawn that overflows its ring into an inject queue already holding a full ring per worker has the spawner step aside, behind the tasks waiting, until the workers have run the queue back under that mark, looking again each time it runs, since a worker runs the tasks that stepped aside early once in a while. The tasks queued stay within two full rings per worker, and an overflow's half ring for each spawner past the mark, whatever the machine's load; the common spawn, whose workers keep up, never looks. The cap is Snello's own: work stealing's analysis bounds the memory of a scheduler that runs the task it makes before its maker (Blumofe and Leiserson, 1999), which costs every spawn a switch, and a spawn here goes on while its workers keep up and pays only once they fall behind. The cost of the cap falls on such a spawner: tasks that compute without a wait hold their workers until each is preempted, so a spawner that made more than the cap of them goes on at the pace the workers take them up. The workers' records are the system's zero pages, room for the most the monitor may grow them to, resident only as each worker started writes its own. A worker's record is on cache lines of its own, since the words its thread writes as tasks move must share no line with a neighbour's. Each worker has a `runnext` slot, one atomic word: a task woken by the running task runs next on the same worker, before its queue, so two tasks handing values back and forth stay one switch apart on one thread; the slot's task runs first at most three times in a row, so that the tasks queued behind two that trade messages are not starved. The inject queue holds the tasks woken by a thread that is not a worker, the timers' or a resolver's, and the tasks a full ring overflowed; the displaced queue behind it holds the tasks taken off their workers by preemption and the spawners that stepped aside for the tasks they outran. A worker takes from its slot, then its ring, then the inject queue and the displaced queue, and steals from another's ring when all are empty; once in sixty-one tasks it looks at the inject queue before its own ring, and at the displaced queue first of all, so that no queue is starved by another; sixty-one is a prime, so the look falls on no rhythm of the program's own. The counts the workers write as tasks move, running, queued, idle, spinning and waiting, are each on a line of their own.

A worker out of work spins for up to 50 µs before it sleeps, one spinner at a time, and the spinning adapts, going on while it finds work and stopping for a program that ticks every millisecond or waits on a quiet socket; a worker that finds work wakes one more for the rest. An idle worker sleeps on a word of its own, on a list of the waiting workers under the idle lock; a wake takes the workers it wants off the list under the lock and writes each one's word after the lock is given back. One of the waiting workers is the keeper, which waits until the earliest deadline of any timer wheel and on the sockets' poller, in each system's most exact way, so that no thread serves the timers or the sockets. The main thread's own stack is the main task's: when the main task first parks, the main thread takes a scheduler stack of its own and becomes a worker like the others, and the main task may then resume on any worker.

### Stacks

A task's stack is sized for what the task can use, which the compiler proves from the linked program. After the link, `compiler/emit/stack` reads every function of the binary as the system's disassembler prints it, otool on macOS, objdump on Linux and LLVM's on Windows, its frame from the instructions that move the stack pointer down and its calls, and walks from the runtime's `task_entry` to the deepest path of each spawn; reading the binary rather than the C or the IR counts what inlining and link-time optimization made of the code. Whatever it does not understand makes the task unbounded, never smaller: a recursion, a call through a pointer whose targets it does not know, a jump through a register, a decrement of the stack pointer on a cycle of the function's flow, a frame whose size depends on a value, a call into a shared library other than the C library's. The C library's functions are counted at what each was measured to use on every system the runtime supports and half again, and `testdata/libc.c` measures every one the runtime calls on every system CI runs. The bounds go into a table the program carries, one entry a spawn; the analysis writes each bound it proves into the binary's file, and a failure of the analysis leaves every task unbounded and never fails a build.

The runtime gives a bounded task the smallest of six classes its bound fits, 2 KB to 64 KB, packed with the others of its class in writable mappings of a megabyte, so that a spawn makes no system call and the system backs only the pages a task touches; an unbounded task, and every task over 64 KB, keeps a guarded reservation of 256 KB, whose guard page is a mapping of its own, which Linux counts against `vm.max_map_count`. A panic runs drops, which can be any code, so it never runs on a small stack: `sn_panic` moves to a guarded stack of the task's own, taken on the scheduler's stack and kept until the task ends. The C compiler's stack protector is off and no compiler writes a switch as a jump table, since the analysis cannot follow either. A debug build fills each small stack with a pattern as its task is spawned and stops the program when the task wrote past its bound, so that every debug build of every test checks the analysis. The record of an ended task keeps its stack and goes on its worker's list of the last sixty-four, so that a spawn allocates nothing; a spawn's arguments go in the record, copied there from the spawning function's frame.

### Channels

A channel is a lock, a ring for a buffered channel and none for an unbuffered one, and two queues of waiters, each waiter the task and the value it sends or the place it receives into, kept in the task's frame, so that a wait on one channel, or a `select` of up to eight cases, allocates nothing. The lock over the queues is the runtime's own futex mutex, one word of three states, free, held, and held with contenders perhaps asleep, taken with one compare-and-swap and given back with one exchange; a contender spins for it, four rounds of three microseconds of spin hints and a yield, and then sleeps on the word through the system's wait on an address, Linux's futex and Darwin's `os_sync_wait_on_address`. A buffered channel's ring is a bounded queue its senders and receivers move through without a lock, Vyukov's bounded queue: each place has a stamp, the tail and the head are positions with a lap count, and a sender finds its place free at the tail's stamp, moves the tail on with one compare-and-swap, writes the value and then the stamp; the tail and the head are a cache line apart. The two queues of waiting tasks keep the lock, each with a word that says whether anyone is on it, so an operation that finds no one waiting takes no lock; a wake does the waiting task's operation for it when the ring still allows, so that the task wakes with its operation done. An unbuffered channel keeps its meetings under the lock, a value going from the sender's frame to the receiver's. A `select` tries its cases in a random order without waiting, and with none ready queues a waiter on every case's channel; the waiters share a state the first operation to reach one claims with a compare-and-swap. An operation that takes a waiter writes everything it has to say into the waiter and claims the woken task under the lock, and queues it once it has let the lock go, so that the woken task never finds the lock still held.

A channel is freed by its last handle, and the ends are the handles' too: the count is of each direction in one word, the last sending handle to go ends the channel, the last receiving one wakes the senders waiting, which drop their values. The channel of a task started for a handle has one slot and is made with both handles counted, so the spawn clones nothing.

### Locks

The `sync` package sits on one more runtime object. The lock held alone is the futex mutex above, spinning briefly before a task parks; an `RwLock` adds a readers' count over it, readers counted in and out with one atomic add and a writer that subtracts `max_readers` to hold back new readers and waits for those in; the waits are a semaphore over the lock's queues. A waiting writer holds back the readers that come after it, so a steady stream of readers cannot keep a writer out. A lock is not recursive. The Snello side holds a lock as an `int`, the lock's address, so taking a lock reaches it with no table between. The library reaches the runtime through ten functions it declares without a body:

| `sync` | Runtime call | Meaning |
|---|---|---|
| `NewMutex`, `NewWaitGroup` | `sn_sync_newLock() int64` | a new lock; its handle, never 0, is what the library holds |
| `NewRwLock` | `sn_sync_newRwLock() int64` | a new lock that also counts readers |
| `Mutex.Drop`, `RwLock.Drop`, the last `WaitGroup` handle's drop | `sn_sync_freeLock(h)` | the lock is freed |
| `Lock`, `Write` | `sn_sync_lock(h)`, `sn_sync_unlock(h)` | held by one task, which waits for every holder before it |
| `Read` | `sn_sync_lockShared(h)`, `sn_sync_unlockShared(h)` | held by any number of readers at once, who wait while a writer holds the lock or waits for it; a writer waits for them |
| `WaitGroup.Add`, `Done` | `sn_sync_count(h, n)` | the count changes under the lock; reaching zero wakes the waiters, going below it panics |
| `WaitGroup.Wait` | `sn_sync_wait(h)` | until the count is zero |
| `Arc.Clone`, `Arc.Drop` | `sn_sync_atomicAdd(n, d)` | one atomic add on the cell's count, no lock |

### Waits and wakes

A task that must wait, on a channel, a lock, a timer or a socket, parks: it switches to its worker's scheduler, which runs the next task, and whoever wakes it puts it back on a queue. A wake has two halves, a claim that makes a parked task runnable or keeps the wake for a task still running, and the queuing, so that a lock is held across no queue. A wake from a thread that holds no lock the task takes after its wait, a timer that fires, a worker looking at the poller, a resolver's thread, goes through a handoff, `sn_handoff`: the waker says waking before its claim reads the task and woken once it is done with it, and a task a waker took out leaves its wait only once it says woken, since a task that leaves its wait without parking can end and be freed before a waker has read its state. A debug build keeps a worker's last 1,024 ended tasks unfreed and stops the program when a wake reaches one, so that a waker that skips the handoff fails loudly.

### Timers

The timers are a hierarchical timing wheel per worker, Varghese and Lauck's structure, ten levels of sixty-four slots over ticks of 256 ns, so that a timer starts and stops in a few instructions whatever else is pending. A timer goes in the wheel of the worker that starts it, so that starting one touches no other worker's lines. No thread serves them: a worker fires its own wheel's timers before it takes its next task, so that the task a timer wakes runs next on the thread that fired it, looks at the other wheels once in sixty-one tasks, the keeper sleeps until the earliest deadline of any wheel, and the monitor fires what is due when every worker is busy. A `Sleep` parks its task on an entry; an `After` or a `Tick` is an entry holding a handle on its channel, which it offers the time into when it fires, and the entry is taken out the moment the program drops its own last handle, so that a `select` whose other case wins leaves no `After` behind. The deadlines are on the monotonic clock, so setting the wall clock moves no timer.

### Sockets and lookups

The poller, kqueue on Darwin, epoll on Linux and a completion port on Windows, has no thread. A socket is registered once, when it is made, for reading and writing, edge-triggered, with a word for each direction holding nothing, ready, or the task waiting, changed by compare-and-swap, so a wait takes no lock and no system call. A worker that runs out of tasks looks at the poller without waiting, after its own queue and before it steals, runs the first task an event made runnable, and of the rest puts as many on the inject queue as workers wait for work, with a worker woken for each, and the others on its own ring; the keeper waits in the poller too, and the monitor looks at it when every worker is busy. Each direction of a socket has a deadline: a timer in a wheel that a new deadline moves rather than adds to, and the task puts itself in the word and then reads the deadline, the timer marks the deadline and then reads the word, both sequentially consistent, so no task waits past its deadline. A host name is looked up by the system's resolver on a pool of threads of `lookup.c`'s while the task parks, since the resolver blocks for as long as the name servers take; a task waiting on a lookup or a socket is a wake promised from outside the workers, which the deadlock detector counts.

### Preemption

A task runs until it parks, ends or is preempted. When a worker has been on one task for ten milliseconds while a task is queued, the monitor thread, which looks at the workers every one to ten milliseconds, takes the task off the worker: it sends the worker's thread `SIGURG`, unused and ignored by default, and on Windows suspends the thread and rewrites its context. The handler runs on a signal stack of the worker's, so that a task's small stack never holds a signal frame; it takes the interrupted context the kernel saved whole, every register and the vector unit's state as the kernel keeps it for its own return, copies it into a block the monitor keeps ready for the worker, and returns into a landing of the task's, a function on a stack in that block, which marks the task preempted and switches to the scheduler as a park does. The task goes on the displaced queue, and resumes on whichever worker takes it: its landing resumes, raises the signal at itself, and the handler puts the saved context in the place of the live one, so that the kernel's return restores the task where it was interrupted, on its own stack, with its `errno`, and the block goes back to the worker; on Windows the landing restores the context itself, `RtlRestoreContext`, with the stack's bounds put back in the thread's block. On x86-64 macOS a thread's context has one of two forms: the AVX form, and the AVX-512 form, which the system gives a thread at its first use of a 512-bit register and every thread started after one has had it, and which holds the first's fields at their places and the 512-bit state after them. A task is preempted on a thread of either form and resumes on a thread of either: a landing whose task was saved in the AVX-512 form uses a 512-bit register before it raises the signal, so that the frame the handler is given takes that form, and a task saved in the AVX form and resumed in a frame of the AVX-512 form has its 512-bit state put back as zero, its initial state, which the thread it was saved on had never left. Any other form is not saved, and the task is left as it is. The handler copies a context with a loop of its own, never the C library's, whose string functions may use a 512-bit register and change the thread's form while the kernel's frame is of the other, since the kernel's return reads the frame by the thread's form. An earlier form preempted a task only on a thread of the first form it saw, and once threads of both forms ran, those of the other were never preempted, and the monitor started a thread beside them. A landing begins as a called function does, on x86-64 with the direction flag clear, which both calling conventions require at a function's entry and the interrupted code need not have had. No instruction is added to the program's code and nothing to a switch: a preemption costs the signal and two copies, a few microseconds, paid only by a task that has held a core that long.

One check decides whether the interrupted point is safe: a task is interrupted only in code Snello's compiler wrote. The program counter lies in the code section, a text section of its own, `sn_code` by the name each system's format gives it, `.sn_code` in an ELF binary, which both backends write every function of the program into, the LLVM backend by the section each definition names and the C backend by opening its unit, `SN_OPEN_CODE`; The mark is clang's, a pragma that names a unit's text section, and gcc has none: a program built through the C backend by gcc has no open code, so its tasks hold their workers as before a task could be preempted. Code outside the section is never interrupted, whatever its thread holds: the C library, where a task preempted inside `malloc` would hold its lock on a thread that then runs other tasks, and which Windows links into the program's own text; the C side of a package, which is compiled to native code, so that it is written into no function of the program, and may keep what it likes by its thread; and the runtime itself, every function of it as it is compiled: a package's C calls the runtime's functions, to build a slice or a string, with whatever it holds still held, and a sort or a map's growth interrupted under it would move it to another thread all the same. An optimizing link writes the functions of the runtime a program calls into the program's own, and there they are the program's code, reached from the program alone; it never writes one that holds a lock, reads the thread's own state or switches, since each of those is marked `SN_HELD`, which writes it into a section of its own, `sn_held`, and into no caller. The runtime learns the section's place once, as the scheduler starts: from the loader on macOS, `getsectiondata`; on Windows from a function before and one after it, which the linker lays out by the sections' names, checked by a function known to be between them; and on Linux from the program's own file, `/proc/self/exe`, its section headers, held to the code the loader mapped, since the marks a linker gives a section there would have the link keep every function in it. A Linux program that cannot read its file so, with no `/proc` mounted, a file it may run and not read, or its section headers stripped, has no section and preempts no task. The rule fails closed: code that nothing opened holds its worker as a call into C does, at the cost of a thread and never of memory, and so does a program whose section cannot be found. An earlier form took the program's whole text but the held section, and failed open: on Windows the C runtime lies in that text, and a task was interrupted inside its `memset`. The allocator's entries, the channels, the locks, the scopes, the timers, the sockets, the file calls, the processes, the scheduler and the random sources are held; the rest, a sort, a map, a string, a number's text, are held by no mark and closed as they stand, so a task in a long sort holds its worker until the sort returns, and the monitor starts a thread beside it. `TestPreemptedOnlyInOpenCode` holds the rule on every system: tasks computing in closed code are never preempted, and the main task still runs. A point that is not safe is left as it is, and the monitor tries again at its next look; a worker still on the same task after three looks is blocked in a system call or a bound function, which no signal frees, and the monitor starts a thread for it, up to sixteen a core, which takes the queued task. A program's own C calls may see `EINTR` where they did not; the runtime's own calls loop on it.

### Windows

A task's stack is a `VirtualAlloc` reservation with a guard page of no access, and the switch saves and restores the stack's bounds in the thread's information block, which Windows reads when it probes a large frame and when it unwinds. The poller is a completion port, each socket polled through AFD for the direction a task is about to wait on, so that the readiness model and every socket call stay as they are. The keeper waits on the port itself. A preemption there asks the system for the thread's extended context: `GetEnabledXStateFeatures` says which wide vector state the system keeps, the upper halves of the 256-bit registers and the 512-bit registers with their masks, `InitializeContext` gives the context's size and lays it out in room of the task's block, and `SetXStateFeaturesMask` asks for that state with the registers, which `CONTEXT_FULL` alone leaves out. A task holds values there when its code was built for a processor that has those registers or was written with them, and a task resumed with only their low halves has a stale upper half in each. The first form of the rule above found it, with the C runtime's own code: linked into the program on Windows, it was interrupted inside its `memset`, which fills through the widest registers the processor has, and a debug build's painted stack came back with sixteen bytes of zero at the foot of a stack, the second half of a store of thirty-two. The C runtime is closed code now, and the state is kept for the code that is open. `TestPreemptedKeepsVectorRegisters` holds every system to it: a task keeps a pattern in every vector register, at the widest form the system keeps, across its preemptions. The context is asked for with `CONTEXT_EXCEPTION_REQUEST`, and a thread the system reports inside a system call or an exception is left as it is, since Windows does not put back whole a context set there; and the worker's task is read only after the context, since `SuspendThread` only asks for the suspension and `GetThreadContext` waits for it. The landing resumes through `RtlRestoreContext`, from a copy of the worker's own made by `CopyContext`, so that the block is free before its landing stack is left. `12-platforms.md` has the reasons.

### Three rules

Each was added by a review after a failure. **A task reads the thread's state through a call, in the held section.** A task may resume on another thread after any switch, and a compiler may compute the address of a thread-local once and keep it across a call; glibc's is a register read and an add, so the first version's tasks read and wrote the thread they had left and crashed on Linux, which macOS, whose thread-locals go through a call, never showed. Every read a task makes of a thread-local, the scheduler's own and `errno` alike, goes through a function the compiler can neither inline nor merge, and since preemption may move a task at any instruction, that function is in the held section, which no preemption lands in, so that the thread cannot change between the read and the last use. **A wait parks until its own condition holds.** A wake can outlive the wait it was meant for: a select's second channel may wake the task after the select's park returned and before it unlinked. Every wait therefore parks in a loop on its own condition. **A guarded stack is two mappings.** Linux counts the guard page's mapping against `vm.max_map_count`, 65530 by default; a hundred thousand unbounded tasks need twice that, and a spawn past the limit panics naming it; a task with a bound takes no mapping of its own.

## Cancellation and deadlines

Status: implemented, in `runtime/c/scope.c`, the waits of `chan.c`, `timer.c`, `net.c` and `lookup.c`, and `std/task`; the library's side is decided 17 of `05-standard-library.md`, and chapter 33 of the book teaches it.

### The problem

A task could be stopped only by hand. A stop channel ended when its last sending handle was dropped, as the worker pool's does; a group's `Done` ended when a member failed; and a socket had `SetDeadline` and `DialTimeout`. Three things were missing. A task blocked in `conn.Read` could not be woken by a stop channel at all, since the read waits on the socket and no channel is in its wait. A stop reached only the tasks and calls that were each handed the channel, and a function that was not handed it could not be stopped. And no deadline covered an operation of several calls: "two seconds for this request" was a socket deadline set again before every read and write, and a `Sleep` or a channel wait between them was not covered at all.

The answer had to come before the library grew. Go added `context.Context` in Go 1.7, after its library, which then needed `DialContext` beside `Dial`, `QueryContext` beside `Query` and `CommandContext` beside `Command`, two forms of every call that blocks, and still has calls that take no context, `net.Conn.Read` among them. Snello's library is small enough that each blocking call can be written once, around the answer.

### The model: attached to the task, not passed

Two models exist. **Passed**: cancellation is a value, a token, handed by hand to every function that may block and checked by that function: Go's `Context` and C#'s `CancellationToken`. **Attached**: cancellation belongs to the task and the scope it runs in, and every call that waits checks the running task: Swift's structured concurrency (SE-0304), Kotlin's coroutines (a `Job` per coroutine, `withTimeout`), Java's structured concurrency (JEP 453 through JEP 525) over interruption, Python's `asyncio.timeout` and `TaskGroup`, and Trio's cancel scopes, which N. J. Smith's *Timeouts and cancellation for humans* (2018) argues for against the token. **Snello attaches it to the task.** The comparison, run on each (the observed table follows):

- **Explicitness.** The passed token's one strength is that a signature says a function can be cancelled. Its price is the converse: a function that does not take the token, or takes it and calls one that does not, stops cancellation there, silently, and nothing in the program says so; a 200 ms deadline over a helper that sleeps a second without the context sleeps the second. Attached cancellation reaches every call that waits, whoever wrote the function, and a reader learns which calls can be cancelled from one rule, every call that waits, not from each signature.
- **Second forms.** A passed token is a parameter, so every blocking call needs a form that takes it, and a library written before it needs a second form of each. Attached cancellation adds no parameter: `Read`, `Dial` and `Sleep` keep their signatures.
- **What it can wake.** A token is checked where code checks it; a call that blocks in the system or the runtime without looking at it, Go's `conn.Read`, is not woken, and the program arranges for a socket deadline or closes the connection from another goroutine (`context.AfterFunc`). The runtime here owns every wait, so it wakes each one.
- **The bag of values.** `Context` also carries `Value(key any) any`, an untyped map down the call tree, which the type checker cannot see; request-scoped data stays a parameter in Snello. Typed task-local values, as Java's `ScopedValue` (JEP 446) and Swift's `@TaskLocal`, are weighed only when a program needs them, apart from cancellation.
- **Cost.** A Go receive that honours a context is a `select` over the channel and `ctx.Done()`, two channels locked and queued on every wait; attached cancellation costs a task with no scope one branch per wait, and a task in a scope the scope's lock once, at its first wait, and one look at its scope at each wake, below.
- **Porting Go code.** A port deletes the `ctx` parameters and the `select` cases on `ctx.Done()`, and writes each `WithTimeout` as `task.Within`; the mapping is at the end of this section. What a port can no longer do is cancel one call and not the next in the same task without a scope around it, which `Within` is.

### What the others do, observed

Each case was run as a program, on an Apple M1 with Go 1.27, Swift 6.4, Java 23 with its preview, .NET 10, Python 3.14's `asyncio` and Trio 0.35; the times are from one run, and the deadline or the cancel came at 200 ms.

| | A helper not written for it sleeps 1 s under a 200 ms deadline | A socket read whose peer never sends | A blocked channel or queue receive | A deadline of 1 s inside one of 200 ms | A child that computes 600 ms without looking |
|---|---|---|---|---|---|
| Go, `Context` | not cut: 1001 ms | not woken by the context; woken by a socket deadline, or by `AfterFunc` closing the connection | `<-ch` stays blocked; a `select` on `ctx.Done()` wakes | 200 ms wins | waited for, 600 ms |
| C#, `CancellationToken` | not cut: 1083 ms; `WaitAsync` abandons the wait and leaves the task running | `ReadAsync(buf, token)` wakes, 217 ms, the socket usable | `ReadAsync(token)` throws; without the token it stays pending | 200 ms wins only through a linked source; an unlinked 1 s token runs to 1002 ms | `WhenAll` waits, 613 ms |
| Swift, task groups | `Task.sleep` cut, 213 ms; a blocking `nanosleep` not | not woken by cancellation; a cancellation handler that shuts the socket down wakes it | an `AsyncStream` loop ends normally, with nothing received | 200 ms wins | waited for, 600 ms |
| Java, `StructuredTaskScope` | `Thread.sleep` interrupted, 222 ms | woken on a virtual thread, 210 ms, and the socket closed by the interrupt | `take` throws `InterruptedException` | 200 ms wins, by the interrupt; the deadline is not inherited | `close` waits, 604 ms |
| Python, `asyncio` | cut, 201 ms; a blocking `time.sleep` not | woken, 200 ms, the socket usable | `get` throws | 200 ms wins | waited for, 600 ms |
| Trio | cut, 201 ms | woken, 202 ms, the socket usable | `receive` throws, the channel usable | 200 ms wins | waited for, 600 ms |

Three findings decide the model. Every passed token loses cancellation silently where a function does not pass it on, Go's 1001 ms and C#'s 1083 ms, and an unlinked token in C# widens a deadline. Where the runtime owns the wait, attached cancellation reaches it, and where it does not, Swift's `nanosleep` and `read`, Python's `time.sleep`, it does not: Snello's runtime owns every wait a task makes. And everyone waits for a child that does not look, so waiting for it is not a cost of this model. The cost a Go program pays for the cancellable receive is measured too: an unbuffered ping-pong whose receives are each a `select` with `ctx.Done()` takes 376 ns a round trip against 250 for plain receives, 1.5 times, with eight processors, and 307 against 211 with one.

### The scope

A scope is a region of a program's work that is cancelled together and may have a deadline. There are two ways to make one, and no scope value to pass around:

- **`task.Within(d, body)` runs `body` with a deadline `d` from now**, and returns its result, `Some(v)`, or `None` when the body was cut short: when the deadline passed, or the scope around it was cancelled, while it ran. A value the body returns after it was cut short is dropped, so that a total summed from a channel the cancellation ended is never taken for the whole one. It is Kotlin's `withTimeoutOrNull` and Trio's `move_on_after`. The body is a closure, which borrows the caller's frame for the call, as every closure handed to a function does.

  ```go
  page := task.Within(2 * time.Second, func() Result<Page, io.Error> {
  	c := net.Dial(host, 443)?          // the dial, the write and the read share the two seconds
  	c.WriteString(request)?
  	return readPage(mut c)             // readPage was written with no word of deadlines
  }) ?? Err(io.NewError("get", host, "timed out", io.TimedOut))
  ```

- **`task.Group` is a scope**: `task.NewGroup()` makes it under the scope the function runs in, `g.Add(h)` puts the task behind the handle under it, `g.Cancel()` cancels it, and the first member to panic cancels it too, so that the others stop, which `Done` asked them to do by hand before and which is now done for them. `Wait` still returns once every member has ended.

**A task inherits the scope it is started in.** `spawn f(x)`, as a statement or for a handle, starts the task in the spawning task's scope: the deadline and the cancellation of every scope around the spawn reach it, so "two seconds for this request" covers the tasks the request starts. A task started for a handle is a scope of its own under that one, so that `g.Add(h)` puts the task under the group with every task it has started since, whenever it started them: a task cannot slip out of a group in the moment between its spawn and the `Add`.

**A deadline only narrows.** A scope's deadline is the earlier of its own and the one around it: `task.Within(10 * time.Second, ...)` inside a scope with one second left still has one second, as `context.WithTimeout` on a parent with less time keeps the parent's, and as a nested `asyncio.timeout` does. No call widens a deadline it inherited.

**The main task is in no scope**, and nothing cancels it; a task started outside any scope is in none either. Catching a signal, which may come to cancel the main task's work, is its own design.

### What a cancelled call does

Cancellation lands where a task waits, and each call that waits says it in the form it already has for "nothing more will come", so that no call gains a parameter or a result:

| The call | Cancelled while it waits, or called once cancelled |
|---|---|
| A library call that returns `Result`: `Read`, `Write`, `Accept`, `Dial`, `LookupHost`, and every call built on them, `io.Copy`, `bufio` | `Err` of an `io.Error` of Kind `io.Cancelled`, or of Kind `io.TimedOut` when a deadline passed, the Kind a socket's deadline already gives; a write reports the bytes it had written, as on a deadline |
| A receive, `<-ch`, `for range ch` | `None`, as from a channel that has ended: the loop ends |
| A send, `ch <- v` | drops the value and goes on, as a send with no receiver left does |
| `select` | each case sees its channel as ended: a receive case is ready with `None`, a send case drops its value; one is taken as among ready cases. A `select` with `default` does not wait and is not affected |
| `time.Sleep` | returns at once |
| `h.Join()`, `g.Wait()`, `wg.Wait()`, a lock's `Lock` | not affected: they wait, below |

A call that does not need to wait does not look: a send to a channel with room, a receive of a value waiting, a `Read` of bytes already buffered by the system. The hot path of a channel operation reads nothing new, and a loop that drains a full channel drains it.

**`task.Cancelled()` says whether the running task's work has been cancelled**, by a `Cancel`, a panic in its group or a deadline. A task whose receive returned `None` asks it to tell a cancellation from the end of the channel, and a task that computes without waiting asks it between rounds, as Swift's `Task.isCancelled` and Kotlin's `isActive` are asked. There is no `task.Done()` channel: every wait already wakes, so a `select` needs no case for it, and a channel for a flag would be a second way to ask the one question. `Group.Done()` goes for the same reason: a group's failure now cancels its members.

**Waiting for tasks is not cancelled.** `Join`, a group's `Wait` and a `WaitGroup`'s `Wait` wait for tasks that are cancelled with the waiter, since a task inherits its scope, and they return once those tasks have stopped. Returning sooner would leave the tasks running with no one to wait for them, which structured concurrency exists to prevent, and would lose the result `Join` hands over, whose handle it takes. Trio's nursery, Swift's task group and Java's `StructuredTaskScope.close` wait the same way. A lock is held for a few instructions and is not a place to stop, as neither Go's, Java's `lock` nor Swift's actors make it one.

**A task that ignores cancellation runs on.** Cancellation is asked for and never forced: there is no kill, as a handle has none, since a task stopped at an arbitrary instruction would leave a lock's value half changed and its owned values undropped. A task that never waits and never asks `task.Cancelled()` runs to its end, and what waits for it waits that long; `Within` returns when its body returns, `None` then, and the deadlock report still names a task that waits on nothing that can come.

**A task that must outlive its scope** is not started in it: the work is sent on a channel to a task started outside, as a server sends a log line to its writer. There is no shield and no detached spawn, Trio's `shield` and Go's `context.WithoutCancel`; Smith calls the shield a smell in the essay that proposed it, and a program that shows the need will be weighed for it.

### The runtime

A scope is a record the runtime allocates, counted: the scope it was made under, which it holds, and for a task's own scope the group that took it in, which it holds too; its state, live, cancelled or timed out; the tasks in it and the scopes under it, in lists under its lock; and its deadline's timer, in the wheel the sleeps and the socket deadlines use. A task holds the scope it is in, in its record; the main task's is none, and a task in none is the program's, whose root scope an interrupt the program did not ask for cancels (`05-standard-library.md`, section 6): it keeps no scope in its record, so a spawn in none pays nothing and a spawn for a handle keeps its lazy word, but its state is read from the root, its first wait a cancel may end puts it in the root's list, and every scope made in none is linked under the root, so that a cancel of the root reaches every task and scope of the program. A group that takes a running task out of none takes it out of the root's list under the root's lock, the one lock taken under a group's, and the task's own enlisting reads the handle's word under that lock, so the two cannot both list it.

- **A spawn** puts the task in the spawning task's scope, when there is one, with one atomic add on the scope's count and no lock, and a task started in a cancelled scope starts cancelled; a spawn in no scope reads one word and pays nothing else. A task goes in its scope's list, the one a cancel wakes, only at its first wait a cancel may end, under the scope's lock and before it reads the scope's state, so that a cancel either finds it in the list or marked the scope before the read: a task that never waits needs no wake, and the tasks of a scope that compute and end never take its lock. A spawn for a handle makes no scope: its channel has one word, which holds the task, tagged, until the task first starts a task, enters a scope or makes a group, each of which makes the task's own scope then with one compare-and-swap on the word, or until a group takes the handle; a task that ends with none leaves the mark ended there, which a late `Add` reads. A task a group takes before it has started anything goes into the group's scope itself, as a task started in it would, put in the list by the `Add`, and woken by it when the group is cancelled already, since it may be parked in a wait no cancel reached. A spawn for a handle in a scope makes the task's scope at the spawn, since it is to be under that one. The handle's channel is made with both handles counted, the task's and the handle's, so the spawn clones nothing: a spawn for a handle costs 164 ns against 188 before.
- **A cancel marks and wakes; the task takes its own wait back.** A cancel marks the scope with one compare-and-swap, and under its lock wakes each task in it with the scheduler's plain wake and marks and holds each scope under it, then walks into those in turn once it has let the lock go: a loop over the scopes it holds, never a recursion, since a recursion on a task's path makes the stack analysis leave every task unbounded, which the first version did, and which cost a wave of sleeps a tenth on Linux until the walks were loops; a release of a scope's last hold is a loop over the scopes it held for the same reason. A wait a cancel may end, woken before its waker came, looks at the state of its task's scope, and finding it cancelled takes the wait back with the very claim its waker would make, so the two cannot both win: a channel wait, plain or of a `select`, with the compare-and-swap of the wait's state, and then takes its waiters off their queues; a sleep by taking its timer out of its wheel under the wheel's lock, unless the firing took it first; a socket wait by the compare-and-swap that takes the task out of the socket's word, as after any park; a name lookup by taking itself out of the lookup's word, leaving the answer to the resolver's thread, which drops it. The loads are relaxed: the cancel's wake and the park's compare-and-swap order the mark before the look. Every cancelled path is out of line and cold, so that the waits compile as they did: inlined by the link-time optimizer into a channel's receive, they made every receive save more registers, and a pipeline of buffered channels ran a quarter slower. A deadline is the scope's timer, which cancels it as timed out when it fires; the timer holds the scope and fires with its wheel's lock let go, since the walk takes the scopes' locks and may let a scope's last hold go, and the `Within` that leaves takes the timer out and lets the timer's hold go when it did, leaving it to the firing when the firing came first. A walk that reaches a scope whose count is already zero, its last holder unlinking it, marks it and does not hold it: nothing is in it, and a hold taken then would free it twice. Two `Add`s link a task's scope under a group in turn, under one lock of the runtime's, so that two racing cannot link two scopes under each other's groups and make a circle no release frees.
- **A handle's receive is not cancelled**, by the channel's kind: `Join` and a group's `Wait` wait for tasks cancelled with the waiter, and keep their results.
- **A member's panic cancels its group** from the task's entry, as `sn_catch` returns: it marks the handle's channel failed and cancels the group the channel's word names, and a group that takes the handle after reads the mark and does the same, each writing before it reads, so that one sees the other; the group records the first handle to fail, which `Wait` reports.
- **Memory safe, no collector.** A scope is freed by its last holder, a task that leaves it as it ends, a group dropped, a handle's channel freed or a `Within` that returns; a task in its scope's list leaves it under the scope's lock before it is done, so a walk holding that lock never reaches an ended task, and the wake goes through the task's state, which a waker never reads once the task has ended. A scope holds the scopes above it and never one below, so the counts form no cycle, and `Add` refuses to put a scope under a group that is under it. No value crosses a task through a scope, so the rules of `03-ownership-across-tasks.md` are untouched, and nothing is traced or collected.

### What it costs

Measured on the 8-core arm64 Mac and in the arm64 Linux image against main, the medians of nine runs, and no row behind: a spawn 160 ns against 157 (Linux 153 against 151), a spawn for a handle 164 against 188 (171 against 222), the switch 79 against 78 (87 against 86), a `select` 93 against 92 (98 against 97), eight senders into one ring 203 ms against 211 (382 against 370, within that row's swing from run to run), a pipeline of buffered channels 30.6 ms against 30.9 (28.6 against 28.6), a wave of 512 sleeping tasks 353 µs against 353 (392 against 428), a group of ten thousand members 342 ns a member against 391 (350 against 401), behind Go's 159 for a goroutine counted by a `WaitGroup`, a lighter construct with no result channel, as it was before this change, and a socket round trip 18.5 µs against 20.2 (5.4 against 5.4). A program that makes no scope pays one word read at each spawn and at each wake of a wait that can be cancelled. A task in a scope pays an atomic add at its spawn and its end, the scope's lock once, at its first wait, and the look at its scope at each wake; a `Within` allocates its scope and arms a timer, as `context.WithTimeout` allocates its context and its timer. The comparison is Go's `select` over a channel and `ctx.Done()`, measured above at 1.5 times a plain receive, which a Go program pays on every wait it wants cancelled.

| `context.WithTimeout(ctx, d)`, `defer cancel()` | `task.Within(d, func() T { ... })` |

### Considered and not taken

- **Go's `Context`**, for the reasons above: a parameter on every function that may block, two forms of every call, cancellation lost silently where a function does not pass it on, and calls that cannot be reached.
- **A cancelled receive that is an error rather than `None`**, as Kotlin's `receive` throws and Java's `take` is interrupted: a receive's result is `T?`, so an error would be a second result type for every receive in every program. `None` is what Swift's `AsyncStream` gives a cancelled iteration. Its known fault, that the end of a stream and a cancellation look alike, is answered by `Within`, which drops a value its body returned once cut short, and by `task.Cancelled()`.
- **A `task.Done()` channel for `select`**, as `ctx.Done()` is used: every wait already wakes; see above.
- **Cancellation as a point on every call, waiting or not**, Trio's checkpoints: it makes every channel operation read the task's state on its hot path, and a call that completes without waiting has done no harm by completing.
- **A scope value passed to the spawn, `scope.spawn(...)`**, as Kotlin's `launch` and Java's `fork`: a spawn is the keyword, which moves the task's values in, and a task inherits the scope it is started in; `Add` is where a group takes a task in, as before.
- **A kill.** See above.

## Decisions

- **A channel is freed by its last handle** (replacing the `Copy` handle of rule 3 of `03-ownership-across-tasks.md`, because a `Copy` handle has no last copy, so a program making a channel per request, or per `time.After`, kept every one until it exited). A handle is owned: moved by assignment, by a call, by a capture and by a send, as a string is, and `ch.Clone()` makes another handle on the same channel with one atomic add on its count. The operations borrow the handle: `ch <- v`, `<-ch`, `len`, `cap`, `for range ch` and a `select` case read it through a `ref`, so a function that only sends or receives takes a `ref chan<- T` or `ref <-chan T`. The ends of the channel are the handles' too: the last sending handle to go ends the channel, which `close` did and no one may do now, the last receiving one wakes the senders waiting, which drop their values, and a `chan T` moved where one end is wanted gives the other up. A pending `time.After` holds a sending handle of its own until it fires; a `Tick` holds one for as long as it ticks.
- **A `WaitGroup` is freed by its last handle** too: an owned handle, `Clone`, dropped through the `sync.Arc` it holds around the counter and its lock.
- **The program ends when `main` returns**, whatever other tasks are doing; they stop with it. A program that must wait for its tasks says so, with a channel or a `sync.WaitGroup`. In a debug build the leak report is skipped when a task is still running at the end, with a note on standard error, since a block owned by a running task is not a leak; the debug build waits up to 200 ms for the count to reach zero before deciding.
- **A program in which no task can ever run again stops**, as Go's does, with `fatal error: all tasks are asleep - deadlock!` and status 2. The scheduler sees it: every worker idle, nothing on a queue, and no wake promised from outside the workers, a timer in a wheel, a socket the poller watches or a lookup under way.
- **A panic in a task started by a `spawn` statement ends the program**, as it does in the main task: the message is printed, the guarded values of the panicking task are dropped innermost first, and the program exits with status 2; the other tasks' values are not dropped, since they are on other threads in the middle of their work. A task started by `spawn` as an expression runs its call under a mark, and its handle, a `task.Handle<T>` over a channel of one slot, receives `Ok` with the result or `Err` with the panic. Guarding every owned value, so that a contained panic frees the plain memory of the frames it abandons, was measured and not taken: the JSON rows of `bench/` took twice as long. A channel handle is guarded, as a value with a `Drop` method is, since a handle a panic abandoned would keep the channel open for every other handle.
- **A closure given to `spawn` owns its environment**: the compiler copies the moved captures into a block the task owns and frees when it ends, beside the arguments.
- **The debug allocator is locked**, one mutex over its block list, counts and quarantine; the release allocator keeps a cache per thread, used in the held section.
- **A task is preempted, never killed.** Preemption moves a task between workers with its registers; cancellation, below, is asked for at every wait and never forced, since a task stopped for good at an arbitrary instruction would leave a lock's value half changed and its owned values undropped.

## What it costs

- A value is copied twice on its way through a channel, in and out of the buffer; a large value is sent behind a pointer, `*T`, which is `Send` whenever `T` is and costs one word.
- A task's stack is bounded by the analysis of the linked binary, which the build runs once after the link, a few hundred milliseconds for a large program; a build whose analysis fails keeps every task on a large stack and says nothing.
- A function of the runtime in the held section is written into no caller, a call where the link-time optimizer might have written its body; measured on the bench table within its spread.

## What it gains

- The compiler is done with concurrency once it emits the interface; the scheduler is runtime work alone, checked against the same example programs.
- Programs are written once, as blocking code, and run as event-driven code, with every wait cancellable and no task able to keep a core from the rest.

## Precedent

Snello's scheduler is its own, decided by what Snello's ownership makes possible: `Send` and the compiler's knowledge of every frame mean a task's stack holds nothing a runtime must find, so tasks run on small stacks bounded by the analysis of the linked binary, move between threads freely, and are preempted by moving their registers alone. It is built from the published techniques its parts name, each measured here: work stealing (Blumofe and Leiserson, "Scheduling Multithreaded Computations by Work Stealing", 1999), hierarchical timing wheels (Varghese and Lauck, 1987), Vyukov's bounded queue for a buffered channel, and the futex for a lock that parks. Go's runtime is the one Snello is measured against, since its tasks and channels are what Snello's are compared with: the bench table compares the two row by row, and the history below records each measurement, the rows where Go led included. Where the precedents stand, as comparisons: preemption divides them by where the cost falls, BEAM counting reductions into every call, OCaml 5 polling at every loop's back edge and GHC at every heap check, each paying in every loop, Go and .NET interrupting a thread by a signal or a suspension and paying only when they do, which Snello does too, and Java's virtual threads, Tokio and Swift's cooperative pool not preempting at all and documenting the starvation. Erlang's BEAM and Pony run one scheduler per core over mailboxes. Step one here, a thread per task, is how most of these began.

## History

Each entry is one change to the runtime as built, in the order it was made: what was measured, what changed, and what it measured after, on the 8-core arm64 Mac and in the arm64 Linux image unless it says otherwise. The entries are the record of why each constant and each shape above is what it is.

1. **A thread per task.** `sn_spawn` started a detached system thread with a stack of 256 KB; a channel was a mutex, a ring, a `closed` flag, a hand-off slot and a list of waiting tasks, each task with a condition variable of its own, and `select` locked its channels in address order and waited on the task's signal. Short enough to be obviously right, which the scheduler was then checked against; starting a task was a system call, switching a kernel context switch, and a task that blocked in a system call blocked a thread.
2. **Many tasks on few threads.** Coroutines with stacks reserved by `mmap`, one worker thread per core with the main thread among them, rings and stealing, and the channel's wait signal replaced by a park. The timers moved out of the poller's thread into wheels the workers keep, since the poller's thread would otherwise have been woken for every new deadline. Name lookups went to a pool of resolver threads. A worker's record was aligned to the cache line after a change elsewhere moved the array and a spawn ran 5% slower for no change on its path: aligned, 152 ns where it was 175.
3. **Channels as `hchan`** (after an audit measured channels 7 to 19 times slower than Go's and locks behind them): the lock-and-waiters shape above, an operation that finds a waiter doing that waiter's half, and the `runnext` slot. The monitor thread came with it, after the `parallel` program printed `false` on a CI runner: the task a running task woke sat in a slot no idle worker took once every idle worker was asleep, two seconds in the `handoff` program; the monitor moves a slot's task to the inject queue within two milliseconds while hand-offs are being left and within ten otherwise. Measured against Go: a ping-pong and sixty-four senders into one channel level, a buffered pipeline ahead.
4. **The scheduler's own costs** (after a measurement put a spawn at six times Go's and a profile put nine tenths of it in three contended locks and a wake per push): a push wakes a worker only when none spins and hands the spin to the worker it signals, as Go's `wakep` does; the ring of 256 slots its own thread writes; a cache of 32 stacks per worker; the task's state as one atomic word. A spawn went from 1,105 ns to about 390, and a switch from 138 to 121, under Go's 125.
5. **The timing wheels** (after a measurement put a timer's start and stop at 1.4 times Go's, eight tasks starting timers at once at 11 times, and a sleep of a millisecond taking 26 while every core traded messages): the wheels above in place of a heap under one lock; the keeper; the slot's turn limit of three and the inject queue's turn once in sixty-one, since the millisecond that took 26 was fairness, two tasks trading messages keeping their worker between them. Measured: a timer's start and stop 89 ns to Go's 101, a sleep of 10 µs 11.7 µs to 15.0, a millisecond under every core's traffic 1.00 ms to 1.01, a switch 109 ns where it was 115.
6. **Sockets without a poller thread** (after a measurement found 50,000 echoes over a local socket 1.4 times slower than Go and Rust, and later the batched take of the inject queue made them a sixteenth slower on Linux): the `pollDesc` words, the worker that looks at the poller itself and runs the first task an event made runnable, the keeper in the poller, the spinning worker. The echoes 311 ms on Linux against Go's 293, where they took 524, and 1.13 s on macOS against Go's 1.10.
7. **The futex lock** (after a measurement put eight tasks sending a million integers each into one channel at 1.8 times Go's time on macOS and 4.3 on Linux, with the difference in the kernel, the system's lock putting every contender but one to sleep): the runtime's own mutex above, its spin rounds measured in time rather than pauses since Intel's pause takes up to 140 cycles, and the woken task no longer taking the lock on its way out, through the handoff. Go's spin-bit lock was ported and measured too, twice the time, and not kept. The eight senders at 460 ms against 717 before and Go's 360 on macOS; in the Linux image 574 against 1,810 and Go's 420.
8. **The spawn** (after a profile of forty rounds of a hundred thousand tasks each sending once put the spawning thread a third in the spawn itself, a fifth in taking a stack, an eighth in waking an idle worker): per-worker counts, the record of an ended task kept with its stack, the arguments in the record, the idle workers on a list under a word each. Tried and not kept, each measured: one spinner at a time on the lock, rings of 1,024, spin rounds of 30 to 16,000 pauses, fewer workers. A spawn alone at 97 ns against Go's 116; with a send 215 ns against Go's 175, the one row then behind.
9. **The ring** (after the spawn with a send stayed at 215 ns against Go's 175, with the workers half their time on the channel's lock): the lock-free ring above, and the wake that does the waiting task's operation for it, after eight senders woken to push for themselves found the place taken again as often as not. The spawn with a send at 157 ns against Go's 175, the drain of a hundred thousand values at 6 ns a receive against 25, the eight senders at 150 ms against Go's 360.

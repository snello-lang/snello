# Tasks and channels: the runtime

Status: decided; step two implemented in `runtime/c/sched.c`, `timer.c` and `net.c`, as the section says, with two differences and the monitor thread recorded there. This note says how a Snello task runs and how a channel works underneath the rules of `03-ownership-across-tasks.md`, in two steps: a thread per task first, and the scheduler that replaced it. The compiler is written against an interface that both implement, so the step from one to the other changes nothing the compiler emits.

## The problem

C has no model of a task. It has the system's threads, locks and condition variables, and nothing that lets many tasks share one thread. A language whose concurrency is "start a task, talk through channels" needs more than that: tasks must be cheap enough to start by the thousand, a task that waits must not cost a thread, and a channel must hand a value from one task to another without either one reaching the other's memory.

None of that is a property of C. It is a property of a runtime written in C, as it is a property of a runtime written in any language: a scheduler is a program that keeps a list of tasks and decides which one the thread runs next. Snello's runtime gets that program in two steps, and the first is deliberately the simplest one that is correct.

## The interface

Every concurrent construct the compiler emits lowers to one of these calls and nothing else. The emitted code never names a thread, a lock or a condition variable.

| Snello | Runtime call | Meaning |
|---|---|---|
| `spawn f(x, y)` | `sn_spawn(run, args)` | starts a task; `run` is a trampoline the compiler writes for the call site, `args` the arguments moved into a block the task owns and frees |
| `make(chan T)`, `make(chan T, n)` | `sn_chan_make(sizeof T, n)` | a new channel; `n` is 0 for an unbuffered one |
| `ch <- v` | `sn_chan_send(ch, &v)` | moves `v` into the channel; blocks until a receiver takes it or there is room; panics on a closed channel |
| `<-ch` | `sn_chan_recv(ch, &out)` | moves the next value out, into memory the receiving task owns; false once the channel is closed and empty, which the compiler turns into `None` |
| `close(ch)` | `sn_chan_close(ch)` | no more sends; panics when closed twice |
| `len(ch)`, `cap(ch)` | `sn_chan_len`, `sn_chan_cap` | values waiting, room for values |
| `select { ... }` | `sn_select(cases, n, has_default)` | waits for the first case that can proceed and returns its index; with `default`, returns at once when none can |
| `for v := range ch` | `sn_chan_recv` in a loop | until the channel is closed and empty |

A channel handle is a pointer to the channel, and any number of tasks may hold one, each its own, cloned from another. A value sent is copied bit for bit into the channel and the sender's place is emptied, as any move empties its source; a value received is copied out the same way. The copy is of the value's bytes, not of what it owns: a slice sent on a channel moves its pointer, length and capacity, and the receiver owns the elements from then on. This is what makes "sending moves, receiving owns" true at run time with no bookkeeping at all.

## Step one: a thread per task

`sn_spawn` starts a system thread, detached, with a stack of 256 KB rather than the system's default of several megabytes, so that thousands of tasks fit in memory. The task runs the trampoline, which calls the function with the moved arguments, frees the argument block, and ends.

A channel is a struct holding a mutex, a ring buffer of `cap` elements of `elem` bytes, a `closed` flag, for an unbuffered channel a one-element hand-off slot, and a list of the tasks waiting on it. A task that must wait, because the buffer is full or empty or the hand-off slot is taken, has one wake signal of its own, a condition variable in this step, puts itself on the channel's list, releases the channel and waits on its signal; every send, receive and close on the channel wakes the tasks on the list, and each one wakes, takes the channel's lock again and rechecks. A send on an unbuffered channel puts the value in the slot and waits until a receiver has taken it, so the sender does not continue before the hand-off, which is what makes an unbuffered channel a synchronization point and not a buffer of one; a channel closed while a sender waits on it panics in that sender, since no receiver need ever come and the alternative is a task that waits forever. A send on a closed channel, and a second close, panic too. A thread can wait on one condition at a time, which is why the signal belongs to the task and not to the channel: it is the one shape that lets a task wait on several channels at once.

`select` is that same wait over several channels. It locks the channels it names in increasing address order, so that two selects over the same channels cannot deadlock, and looks for a case that can proceed: a receive when a value waits or the channel is closed, a send when there is room, which on an unbuffered channel means a receiver is waiting on it, since a select must not commit to a send that no one will take; every channel counts the tasks waiting to receive from it for that. The count is a promise only of a receiver waiting at that moment: when that receiver is itself a select that wakes and finds another of its cases ready too, it may take that one, and the sender then waits for the next receiver. Step two's wait lists hand the value to the receiver directly and close that gap. If none can, it puts the task on the list of every channel named, releases them all, waits on the task's signal, and tries again from the start. A plain send or receive is a select of one case. When several cases can proceed it picks one at random, since always taking the first in source order would let a busy channel starve the others; a `select` is the one place in the language where the program does not say which of two ready things happens first, and the runtime must not make that choice systematically. With a `default` it returns without waiting.

As rebuilt (after an audit measured channels 7 to 19 times slower than Go's and locks behind them): a channel is Go's `hchan`. It holds a lock, a ring for a buffered channel and none for an unbuffered one, and two queues of waiters, Go's `sudog`: the task and the value it sends or the place it receives into, in the task's frame. An operation that finds a waiter does that waiter's half too, copying the value straight from the sender or into the receiver, and wakes that one task, which has nothing left to do; a receive on a full buffered channel with a sender waiting takes the oldest value and puts the sender's in behind it; only a close wakes every waiter. A `select` tries its cases in a random order without waiting, and with none ready queues a waiter on every case's channel; the waiters share a state the first operation to reach one claims with a compare-and-swap, and a waiter of a select already claimed is dropped where it is met, so the count of receivers and its gap are gone. The lock is the system's fastest, `os_unfair_lock` on Darwin, whose `pthread` mutex hands off through the kernel, and glibc's futex mutex on Linux; no task parks holding it. The scheduler gives each worker Go's `runnext`: a task woken by a running task runs next on the same worker, before its queue, so two tasks handing values back and forth stay one switch apart on one thread instead of waking another thread for every hand-off; an idle worker takes a task left in another's slot for a millisecond, since tasks are not preempted. Rebuilt after the `parallel` program printed `false` on a CI runner: the task a running task wakes was taken from the slot only by an idle worker that had seen it there before it slept, and once every idle worker was asleep, which the slot's own economy makes the common case, nothing woke one, so the task waited for the running task to end, two seconds in the `handoff` program on eight cores. A monitor thread now watches while any worker is busy and sleeps while every worker is idle, as Go's sysmon does, since only a running task fills a slot, woken by the first worker to leave idle; it moves a task left in a slot longer than a millisecond to the inject queue, which wakes a worker, within two milliseconds while hand-offs are being left and within about ten otherwise, since it backs off from a millisecond to ten between looks that find nothing, so that a program computing or blocked in a read costs a hundred wakes a second rather than a thousand. Go's runtime has no such thread for its slot: it wakes a worker for every hand-off and lets that worker take the slot after a few microseconds, which is the thread per hand-off the slot here saves. Two tasks trading a lock, one of them never parking, now go a step per look instead of stopping, which is what `parallel` exercises. Measured against Go's channels: a ping-pong over an unbuffered channel and sixty-four senders into one buffered channel are level with Go's, and a buffered pipeline is ahead of it.

What this step costs: a task is a thread, so starting one is a system call and switching between two is a kernel context switch, microseconds rather than nanoseconds; the number of tasks is bounded by the system's thread limit, tens of thousands, not millions; and a task that blocks in a system call, reading a file or a socket, blocks a thread. For the twenty example programs and for the race tests none of this matters, and the implementation is short enough to be obviously right, which is what the scheduler is then checked against.

## Step two: many tasks on few threads

The design document decided this in its runtime section: an M:N work-stealing scheduler, blocking-looking I/O over kqueue, epoll or io_uring, and no async/await. In the terms of this note:

- **A task is a coroutine, not a thread.** It owns a stack, reserved with `mmap` and committed by the system lazily as it is touched, so a reservation of a megabyte costs nothing until used, and a saved set of callee-saved registers. Switching from one task to another saves those registers and the stack pointer and restores the next task's: some twenty instructions of assembly per architecture, with no system call. Stacks come from a pool and go back to it when a task ends.
- **N worker threads run M tasks.** One worker per core, each with a queue of runnable tasks; a worker whose queue is empty steals from another's. This is the shape every runtime of this kind has converged on.
- **A channel parks a task instead of blocking a thread.** The channel keeps its lock and its list of waiting tasks from step one; what changes is the task's wake signal. A receive on an empty channel puts the current task on the list and switches to the next runnable task instead of waiting on a condition; the send that later arrives takes the waiter off the list and puts it back on a run queue instead of signalling. `select` registers the task on every channel it names, as it did, and is woken by the first.
- **I/O parks the same way.** A read that would block registers the descriptor with the poller and parks the task; the worker runs others; the poller's event puts the task back. The program is written as blocking code and runs as event-driven code, which is the promise behind leaving async/await out.
- **Timers** are a timing wheel per worker, which the workers fire between their tasks, and are what `time.Sleep`, `time.After` and `time.Tick` sit on. A `Sleep` parks its task on an entry; an `After` or a `Tick` is an entry that puts the time in its channel when it fires, with a send that never waits, `sn_chan_offer`, and a `Tick` goes back in its wheel for its next tick on the period, so no task waits for either (after the review of the standard library measured a pending `After` as a whole task: 1.2 GB for a hundred thousand of them, against Go's 10 MB). The entry holds a handle on its channel, and the channel knows its entry while it is in a wheel: when the program drops the last handle but the timer's, the entry is taken out and that handle, the last, frees the channel at once, so a `select` whose other case wins leaves no `After` behind until its deadline, as Go's runtime has done since 1.23; a `Tick` whose channel no one holds stops the same way, and the timer offering into a channel only it holds drops it instead. At the end of the program the pending entries give their handles back before a debug build counts the blocks. In step one they were tasks that slept and sent. A deadline past the largest time is the largest time, so the longest `Duration` waits rather than wrapping round. The deadlines are on the monotonic clock, which the system never sets back, so setting the wall clock moves no timer. What a timer puts in a channel is a whole `time.Time`, its wall clock and its monotonic reading, which the runtime builds field for field as package `time` declares it.

As built: the context switch is twenty instructions of inline assembly per processor, arm64 and x86-64, in `sched.c`; a stack is a reservation of 256 KB with a guard page, kept when freed; the workers are one per core with the main thread among them, each with a queue of its own, stealing half of another's when its own is empty and waiting on a condition when every queue is empty; a task runs until it parks or ends, with no preemption, so a task that never waits keeps its worker. Two differences from the sketch above: the timers are not in the poller, since its thread would otherwise have to be woken for every new deadline, but in wheels the workers keep, as the paragraph after this one says; and the main task may resume on any worker after its first park, since the program keeps nothing per thread but what the runtime keeps per task. The poller is `net.c`: kqueue on Darwin and epoll on Linux, one thread, over the sockets of the `net` package; file reads and writes still block the worker, which the twenty programs do not notice. A host name is looked up by the system's resolver, which blocks for as long as the name servers take, so neither on a worker nor on the poller's thread, which every socket's events go through, but on a pool of threads of `lookup.c`'s while the task parks, as `05-standard-library.md` decides (15); a task waiting on a lookup is a wake promised from outside the workers, which the deadlock detector counts, as it counts one waiting on a socket. A wake from a thread that holds no lock the task takes after its wait, a timer that fires, the poller's thread, a resolver's, goes through a handoff, the sleeping task's flag of the timers made one mechanism (`sn_handoff` in `internal.h`): the waker says waking before its claim reads the task and woken once it is done with it, and a task a waker took out leaves its wait only once it says woken (after the review of names in `net` reproduced, with the waker and the task each held back by a pause standing for the system's scheduler, the poller's thread and a resolver's waking a task that had gone on and been freed; a socket's task goes on without its wake when a kept wake ends its park, and a lookup's when the answer is there before it parks). A channel's or a lock's waker needs none, since its task takes the lock the waker holds before it goes on. A debug build keeps a worker's last 1,024 ended tasks unfreed and stops the program when a wake reaches one, so that a waker that skips the handoff fails loudly rather than writing freed memory: the reproduction above, with a lookup's task leaving without waiting, stops with `fatal error: a wake reached a task that has ended` on every run. The timers' `wheels`, read by every worker on every timer, are on a cache line of their own, and each count the workers write as tasks move, `running`, `queued`, `nexts`, `outside`, `injected`, `idle`, `spinning` and `waiting`, on one of its own, as Go pads its scheduler's: the link order had put the wheels on the line of the run-next count, written on every switch, and a sleep cost a tenth more for a file the program never called; the counts grouped on one line cost the same tenth, since the idle workers' counts and the busy workers' then shared it; a line each made 500,000 sleeps of 20 µs over a thousand tasks 52 ms against 56 before, Go's 40. As rebuilt (after a measurement found 50,000 echoes over a local socket 1.4 times slower than Go and Rust): a socket is registered once, when it is made, for reading and writing, edge-triggered, with Go's `pollDesc`, a word for each direction holding nothing, ready, or the task waiting, changed by compare-and-swap, so a wait takes no lock and no system call, and one that comes after its event does not park. The cost that remained was a second thread woken per event: the poller's thread wakes, and then wakes a worker to run the task. As Go's runtime keeps an M spinning, a worker that runs out of tasks now spins for up to 50 µs on an inject queue before it sleeps, Go's global run queue, where the poller's thread puts the tasks it wakes, and runs one with no thread woken; one worker spins at a time, a push or an inject while it spins wakes no other, and one that finds a task wakes a worker for the rest. The spinning adapts, as an adaptive mutex's does: it goes on while spins find tasks or sleeps end within the window, and stops for a program that ticks every millisecond or waits on a quiet socket, which spends no more CPU than before. Work the workers make for one another does not go through the inject queue, so a spinner never takes a task another worker is about to run, which made 64 producers feeding one channel a fifth slower when it did. The echoes are now faster than Go's, 0.84 s against 0.91, and level with it under a 1 GB transfer; Go's design goes one step further, an idle worker blocking in the poller itself. A socket's deadlines are Go's `pollDesc` deadlines: each direction has one, and a timer in a wheel that a new deadline moves rather than adds to; when it fires it marks the deadline passed and takes out the task waiting in the word. The task puts itself in the word and then reads the deadline, and the timer marks the deadline and then reads the word, both sequentially consistent, so no task waits past its deadline. A closed socket takes its timers out, so that none fires on the next socket with its number. A channel is never touched after its handle is given up (after a false deadlock on a CI runner): the drop of a channel whose After or Tick is in a wheel decides under the wheel's lock whether its handle was the last but the timer's, since the other holder may free the channel the moment the count comes down, and the timers' thread of that day once read the timer of a channel already freed and reused for the next After, which it then took out unfired. As rebuilt again (after a measurement put a spawn at six times Go's and the profile put nine tenths of it in three contended locks and a wake per push): a push wakes a worker only when none spins, and the wake hands the spin to the worker it signals before that worker runs, as Go's `wakep` counts the M it starts as spinning, so the pushes until it runs wake no other, the spins handed out counted under the idle lock so that a broadcast hands none; the spinner watches every queue and, once it finds work, wakes one more worker for what is left; a worker's queue is Go's `runq`, a ring of 256 slots its own thread alone writes at the tail and every taker takes from by a compare-and-swap of the head, stealers taking half, a full ring sending half to the inject queue; each worker keeps a cache of 32 stacks its thread alone touches, refilled from and flushed to the pool of 256 half a cache at a time; and a task's mutex, state and woken flag are one atomic word changed by compare-and-swap with the pending wake as a bit, as Go's `casgstatus` keeps a goroutine's status. A spawn went from 1,105 ns to about 390, and a switch from 138 to 121, under Go's 125.

As rebuilt once more, for the timers (after a measurement put a timer's start and stop at 1.4 times Go's, eight tasks starting timers at once at 11 times, and a 50 µs sleep at 1.2 times, and found a sleep of a millisecond taking 26 while every core traded messages): the timers are in `timer.c`, a hierarchical timing wheel per worker, Varghese and Lauck's structure in the form Tokio gives it, ten levels of sixty-four slots over ticks of 256 ns, so that a timer starts and stops in a few instructions whatever else is pending, where the heap it replaced moved an entry along a path as long as the logarithm of their count under one lock every timer shared. A timer goes in the wheel of the worker that starts it, as Go's timers go on the P that starts them, and a channel's or a socket deadline's remembers the wheel chosen the first time one was started on it, so that the workers running tasks that sleep write no line they share and whoever stops a timer finds its wheel without reading the timer. No thread serves them: a worker fires its own wheel's timers before it takes its next task, so that the task a timer wakes runs next on the thread that fired it with no other thread woken, looks at the other wheels once in sixty-one tasks, and when it has nothing to run fires every wheel before it spins and while it spins; one of the workers waiting for work is the keeper, which sleeps until the earliest deadline of any wheel and no longer, in each system's most exact way (a kqueue timer marked critical on Darwin, where a condition's timed wait returns a quarter late; a condition on the monotonic clock with the thread's timer slack set to nothing on Linux, where the default slack adds 50 µs to every wait), and the monitor fires what is due when every worker is busy. The millisecond that took 26 was fairness, not timers: a task woken by the running task goes in the worker's run-next slot and ran before the queue however often, so two tasks trading messages kept their worker between them; the slot's task now runs first at most three times in a row, as Tokio's does, and the inject queue is looked at before the worker's own once in sixty-one tasks, as Go's global queue is. Measured on the eight cores of this machine against Go: a timer's start and stop 89 ns to Go's 101, and 20 to 61 from eight tasks at once; a sleep of 10 µs 11.7 µs to 15.0; of 200 µs 235 to 233; of a millisecond 1.04 ms to 1.26; the millisecond under every core's traffic 1.00 ms to 1.01; a 1 ms ticker's tick 1.0001 ms to 1.0004; and a task's switch 109 ns where it was 115. The one row behind: 512 tasks each sleeping 10 µs, where the sleeps take 54 µs to Go's 39, since a sleep's turn through park, wake and switch costs about 105 ns here to Go's 85.

As rebuilt for the stacks (after a measurement put a spawn at twice Go's, and the profile put most of what was left in two costs every guarded stack pays: the system call that makes it writable, and the first touch of its top page): a task's stack is sized for what the task can use, which the compiler proves from the linked program. Go grows a goroutine's stack from 2 KB by copying it, which needs the compiler's map of every pointer into every frame, and C keeps the addresses of locals where no runtime can find them, so the C backend rules copying out; Rust's segmented stacks, which grew a stack by a linked segment instead of a copy, were dropped before its first stable release, for the cost of a call at a segment's edge and of every call into C. What remains is to know the depth before the task runs. After the link, `compiler/emit/stack` reads every function of the binary as the system's disassembler prints it, otool on macOS and objdump on Linux, its frame from the instructions that move the stack pointer down and its calls, and walks from the runtime's `task_entry`, whose call through a pointer is each spawn's `sn_task_K_run`, to the deepest path; reading the binary rather than the C or the IR counts what inlining and link-time optimization made of the code. A call or a branch into the middle of another function, which gcc makes when two functions end in the same message and exit, is counted as a call of the whole function, which is never less, since that code moves the stack pointer down only by the function's own decrements and calls only its calls. Two local functions of one name, which the disassemblers print alike, are read as one, the worse of the two, which is never less either; the runtime keeps every static function's name to one file, as `TestStaticNamesUnique` holds it, since a lock's spin read as the scheduler's, and a socket's preparation read as the scheduler's start, gave tasks a deeper bound than their code, and left the net programs on gcc unbounded. Whatever it does not understand makes the task unbounded, never smaller: a recursion, a call through a pointer whose targets it does not know, a jump through a register, a frame whose size depends on a value, a write to the stack pointer of a kind it does not recognize, a call into a shared library other than the C library's. The calls the runtime makes through pointers the program gave it are known by their names, which both backends take from `lower`: a channel's and a map's element drops, a map's key hash and equality, a package variable's initializer. The C library's functions are counted at what each was measured to use on macOS on arm64 and Linux on arm64 and x86-64, with gcc and clang, and half again; `testdata/libc.c` measures every one the runtime calls, down its heavier paths, and the package's test runs it on every system CI runs, so that a C library that deepens a function fails a test before it shortens a stack. Linux links bind every import as the program starts, `-z now`, so that no first call runs the dynamic linker's resolver on a task's stack, which macOS's chained fixups do already, and the analysis reads a binary that binds lazily as unbounded at every call into the library. The bounds go into a table the program carries, `sn_stack_bounds`, one entry a spawn, every entry unbounded as the backend writes it; the analysis writes each bound it proves into the binary's file, beside it and renamed over it, signed again on macOS, and a spawn passes its entry to `sn_spawn`. A failure of the analysis leaves the binary as linked, every task unbounded, and never fails a build.

The runtime gives a bounded task the smallest of six classes its bound fits, 2 KB to 64 KB, packed with the others of its class in writable mappings of a megabyte, so that a spawn makes no system call and the system backs only the pages a task touches; an unbounded task, and every task over 64 KB, keeps the guarded reservation of 256 KB. A panic runs drops, which can be any code, so it never runs on a small stack: `sn_panic` moves to a guarded stack of the task's own, taken on the scheduler's stack and kept until the task ends, through `sn_on_stack`, and jumps to a mark from the task's own stack once back, so that the drops count against no bound and the jump goes up the stack, as glibc's checking `longjmp` requires. The scheduler's start, and the main thread's first park, which makes its scheduler context, run through `sn_on_stack` as well, on the caller's own stack: a task reaches them, since a task spawns and parks as the main task does, but never runs them, since it runs only once both are done, and a spawn and a channel's send that counted them were bound at 2.7 KB, in the class of 4 KB, where they are now 1.8 KB, in the class of 2 KB, and a burst of spawns touches half the memory. The C compiler's stack protector is off, `-fno-stack-protector`, as Go and Rust have no such check: a Snello program checks every index, and the protector's failure path, deeper than anything the runtime calls, set the bound of nearly every task on macOS, where Apple's clang turns it on by default. A debug build fills each small stack with a pattern as its task is spawned and stops the program, `fatal error: a task's stack went N bytes deep`, when the task wrote past its bound, so that every debug build of every test checks the analysis; the backends' tests also fail a program whose spawn loses its bound, which no output would show. Of the spawns of the programs the backends' tests share, every one is bounded but those that call a closure they were given, through `Once.Do` and `testing.Catch`, which keep a guarded stack. Bounding the stacks made a spawn cheap enough that a burst of them outran the workers, and the measurement that followed found the scheduler's own costs under it, each changed after Go's or Rust's answer and kept for what it measured: a worker whose queue is empty takes a share of the inject queue onto its ring under one lock, as Go's `globrunqget` does, where it took one task a lock and every worker queued on that lock during a burst; on Darwin, an idle worker is signalled after the idle lock is given back, so that it does not wake to wait for the lock, and on Linux under it, measured: the signal after the lock made 50,000 echoes over a socket a sixteenth slower there; and a channel's count of handles is a cache line from its lock and its ring, which every send writes, 8%. Measured and left out: the lock of a channel's queues waited on a hundred turns before its thread sleeps in it, as Rust's futex mutex spins and Go's runtime lock does, since `os_unfair_lock` does not spin: on Darwin it made a spawn 5% cheaper and a switch between two tasks 2% dearer, whether it read a flag before it tried the lock or tried first, and on Linux a switch a seventh dearer, so the lock stays the system's alone. For no gain: a task's record kept with its stack for the next spawn, as Go keeps a dead goroutine; counts of running tasks per worker; the spin claimed before the idle lock; several workers spinning at once, as Go's do; the idle lock spun before it sleeps; and the counter's timebase read once on Darwin. Measured against `main` before it and against Go, each the median of eleven runs on macOS on arm64 and on Linux on arm64, the losing rows first: a spawn costs 282 ns on macOS and 357 on Linux, against Go's 185 and 245, where it cost 365 and 521; a switch between two tasks 152 ns on Linux, where it cost 150, against Go's 103, and 110 on macOS against Go's 123; 1,000 tasks sleeping 20 µs 500 times each take 49 ms on macOS against Go's 40, where they took 52, and 53 on Linux, as before, against Go's 78; a hundred thousand tasks started to wait on one channel take 68 ms on Linux against Go's 57, where they took 284, and 29 on macOS against Go's 61, where they took 246.

As rebuilt for the sockets (after the batched take of the inject queue made 50,000 echoes over local sockets a sixteenth slower on Linux than before it, and `perf` found the program doing less work than before and waiting longer): the poller has no thread. The cost under the echoes was that the thread that heard of an event was not the one that ran its task: the poller's thread woke a worker, and that worker, taking a share of the inject queue onto its ring, ran several sockets' tasks in turn while the others slept; queued at once with a worker woken for each, the echoes were two fifths faster on Linux and a twentieth slower on Darwin, where the system's socket calls keep six of the eight cores busy in the kernel and every sleep and wake of a thread takes from them. Go's design answers both, and Snello now has it: a worker that runs out of tasks looks at the poller without waiting, after its own queue and the inject queue and before it steals, runs the first task an event made runnable, and of the rest puts as many on the inject queue as workers wait for work, with a worker woken for each, and the others on its own ring, which is empty, as Go's `injectglist` puts the rest on its P's queue, so that the thread that hears of an event runs its task, and the tasks of one look do not spread over every busy worker; the spinning worker looks each time it reads the clock. The idle worker that keeps the timers also watches the sockets, as Go's blocking `netpoll` waits until the next timer: it waits in a set of its own, the timers' deadline, a wake, and the poller as one descriptor, readable while it holds events, a kqueue in a kqueue on Darwin and an epoll in an epoll on Linux, where the deadline is a timerfd at an absolute time of `CLOCK_MONOTONIC`, which takes no timer slack, so that a sleep is as exact as the condition's timed wait it replaces and no worker looking at the poller takes the keeper's wake or deadline. A worker becomes the keeper when a timer is pending or a task waits on a socket, and a keeper that watches the sockets alone waits with no deadline, which a timer started meanwhile wakes as it wakes any keeper; one that leaves the wait for the sockets looks at the poller as a worker, and before it runs a task wakes another to watch. While every worker runs tasks that do not let go, none looks and none waits, and the monitor looks at the poller when no one has since its last look, as Go's sysmon polls the network after 10 ms, which `TestSocketsWithEveryWorkerBusy` holds it to. No one looks while no task waits on a socket, so a program without sockets makes no call into the poller. A worker signalled out of its wait is counted on its way until it is back, so that no wake signals it again: two of every three signals of the echoes on Darwin had gone to workers already woken. The handoff, the promises the deadlock detector counts, the deadlines and the stack bounds stand as they were: a task taken out of a socket's word is counted kept once it is queued or its worker runs it, and the one call this adds to a task's stack, the eventfd's `write` that wakes the keeper on Linux, is in the C library allowance. The echoes take 311 ms on Linux against Go's 293, where they took 524, and 1.13 s on macOS, as before, against Go's 1.10; with a deadline set before every read, as a server sets one per request, 319 ms on Linux against Go's 301, where they took 415, and 1.13 s on macOS against Go's 1.09, where they took 1.14.

Three rules the review of the first version added, each from a failure. **A task reads the thread's state through a call.** A task may resume on another thread after any switch, and a compiler may compute the address of a thread-local once and keep it across a call; glibc's is a register read and an add, so on Linux the first version's tasks read and wrote the thread they had left and crashed, which macOS, whose thread-locals go through a call the compiler does not merge, never showed. Every read a task makes of a thread-local, the scheduler's own and `errno` in the socket loops alike, goes through a function the compiler can neither inline nor merge. **A wait parks until its own condition holds.** A wake can outlive the wait it was meant for: a select's second channel may wake the task after the select's park returned and before it unlinked. Every wait therefore parks in a loop on its own condition, and a sleep on a flag the timer sets after waking it, so that the timer never wakes a task that has stopped waiting for it. **A guarded stack is two mappings.** The guard page below each guarded stack is a mapping of its own, and Linux counts mappings against `vm.max_map_count`, 65530 by default; a hundred thousand unbounded tasks need twice that, which a system raises or lowers as it chooses, and a spawn past the limit panics naming it. A task with a bound takes no mapping of its own: its stack is part of a megabyte shared with its class. What the benchmarks say about the constants is in `01-language-design.md`.

Two properties of the language make this scheduler simpler than its counterparts elsewhere. The compiler knows the layout of every frame and the extent of every borrow, so a task's stack holds nothing the runtime has to find or scan, as a collector would have to. And the `Send` rule means that whatever a task owns is reachable from no other task, so the scheduler may run a task on any thread and move it between threads freely, without a memory model question at every step.

## Locks and counts

The `sync` package (`05-standard-library.md`, decision 5) sits on one more runtime object, which the same two steps implement: a lock, with a count and a list of waiting tasks. As rebuilt, the lock held alone is Rust's `std::sync::Mutex`, a futex mutex of one word, 0 free, 1 held, 2 held with tasks perhaps waiting, taken with one compare-and-swap and given back with one exchange, spinning briefly before a task parks; an `RwLock`, made by `sn_sync_newRwLock`, adds Go's `RWMutex` over it, readers counted in and out with one atomic add and a writer that subtracts `max_readers` to hold back new readers and waits on a semaphore for those in; the waits are Go's runtime semaphore over the lock's queues. Measured against Go's and Rust's: an uncontended `Mutex` is ahead of Go's, and eight tasks contending on one are level with Rust's and ahead of Go's. The library reaches it through ten functions it declares without a body, and nothing else in the program does.

| `sync` | Runtime call | Meaning |
|---|---|---|
| `NewMutex`, `NewWaitGroup` | `sn_sync_newLock() int64` | a new lock; its handle, never 0, is what the library holds |
| `NewRwLock` | `sn_sync_newRwLock() int64` | a new lock that also counts readers, Go's `RWMutex` |
| `Mutex.Drop`, `RwLock.Drop`, the last `WaitGroup` handle's drop | `sn_sync_freeLock(h)` | the lock is freed |
| `Lock`, `Write` | `sn_sync_lock(h)`, `sn_sync_unlock(h)` | held by one task, which waits for every holder before it |
| `Read` | `sn_sync_lockShared(h)`, `sn_sync_unlockShared(h)` | held by any number of readers at once, who wait while a writer holds the lock or waits for it; a writer waits for them |
| `WaitGroup.Add`, `Done` | `sn_sync_count(h, n)` | the count changes under the lock; reaching zero wakes the waiters, going below it panics |
| `WaitGroup.Wait` | `sn_sync_wait(h)` | until the count is zero |
| `Arc.Clone`, `Arc.Drop` | `sn_sync_atomicAdd(n, d)` | one atomic add on the cell's count, no lock |

The Snello side holds a lock as an `int`, as it holds a file descriptor, and the structure of a lock stays the runtime's: the handle is the lock's address, so taking a lock reaches it with no table between and no lock but its own, and zero, which no lock has, is never a handle, since a handle comes only from the function that makes its lock (the library's handles have no zero value). Step one kept the locks in a table it grew under a lock of its own and handed out indices; every lock operation of the program then went through that one lock, so eight tasks each taking a lock of their own a million times took 880 ms where one task took 25, and with the handle as the address they take 72 (after the review of the standard library measured it). Each lock is a mutex of the system's, a count of readers, a flag for the writer, the wait group's count, and the list of waiting tasks of the channels' kind: a task that must wait, because the lock is held or the count is not yet zero, links itself on the list, releases the lock and waits on its own signal, and every release, and every change of the count, wakes the list. That is the channel's wait exactly, which is the point: step two parks a task on a lock as it parks one on a channel, by changing what the signal is and nothing else. A writer takes the lock when no reader and no writer holds it, a reader when no writer holds it and none waits for it: a waiting writer holds back the readers that come after it, as Go's `RWMutex` does, so a steady stream of readers cannot keep a writer out (step one let readers in ahead of a waiting writer, and the review measured a writer kept waiting 956 ms where Go's waits 3). A lock is not recursive: a task that locks what it holds, or reads again what it reads while a writer waits, waits forever, as in Go, and when nothing else can run the program stops with the deadlock message below.

## Decisions that hold for both steps

- **A channel is freed by its last handle** (replacing the `Copy` handle of rule 3 of `03-ownership-across-tasks.md`, because a `Copy` handle has no last copy, so a program making a channel per request, or per `time.After`, kept every one until it exited). A handle is owned: moved by assignment, by a call, by a capture and by a send, as a string is, and `ch.Clone()` makes another handle on the same channel with one atomic add on its count. A handle's drop takes one away; the last frees the buffer, dropping the values still in it, and the channel's lock. The operations borrow the handle: `ch <- v`, `<-ch`, `close(ch)`, `len`, `cap`, `for range ch` and a `select` case read it through a `ref`, so a loop sends on one handle as often as it likes, and a function that only sends or receives takes a `ref chan<- T` or `ref <-chan T`, to which a `ref chan T` converts. What it costs is an atomic add where a channel is handed to another task, `spawn produce(jobs.Clone())`, and an atomic subtract where a handle dies, the pattern Rust uses for a channel's sending end; a call within one task, through a `ref`, costs nothing. The other way, counting every copy of a `Copy` handle in the compiler as Swift does, pays an add and a subtract on every pass of the handle and was not taken. Closing stays explicit: the last handle going does not close the channel, since no one is left to see it. A pending `time.After` holds a handle of its own until it fires; a `Tick` holds one for as long as it ticks.
- **A `WaitGroup` is freed by its last handle** too: it is an owned handle, `Clone`, and dropped through the `sync.Arc` it holds around the counter and its lock, so a task gets its own with `wg.Clone()` before the spawn and the last handle frees both. `Add`, `Done` and `Wait` borrow the handle.
- **The program ends when `main` returns**, whatever other tasks are doing; they stop with it. A program that must wait for its tasks says so, with a channel or a `sync.WaitGroup`. In a debug build the leak report counts blocks, and a task still running at the end may own some; the report is therefore skipped, with a note on standard error naming the number of tasks still running, since a block owned by a running task is not a leak. A task that has sent its last word is often still ending when `main` returns, so the debug build waits up to 200 ms for the count to reach zero before deciding.
- **A program in which no task can ever run again stops**, as Go's does, with `fatal error: all tasks are asleep - deadlock!` and status 2 (step one waited forever). The scheduler sees it: every worker idle, so every task parked and the main task among them, nothing on a queue, and no wake promised from outside the workers, which is a timer in a wheel or a socket the poller watches. Those count as promised until their wake has reached its task, and when the last is gone an idle worker looks again, so a program waiting on a timer or a socket is never stopped; a pending `After` or a running `Tick` keeps a program waiting rather than stopped, as in Go.
- **A panic in any task ends the program**, as it does in the main task: the message is printed, the guarded values of the panicking task are dropped innermost first, and the program exits with status 2. The other tasks' values are not dropped; they are on other threads, in the middle of whatever they were doing, and cannot be unwound from here. The guard stack is therefore per thread.
- **A closure given to `spawn` owns its environment.** For every other closure the environment lives in the frame of the function that wrote it, since such a closure is a borrow; a spawned closure outlives that frame, so the compiler copies the moved captures into a block the task owns and frees when it ends, beside the arguments.
- **The debug allocator is locked.** Its block list, counts and quarantine are shared by every task; one mutex covers them. The release allocator is the system's, which is already safe.
- **The stack of a task in step one is 256 KB.** A recursion deeper than that ends the program with the system's stack fault rather than a Snello message; the lazily committed reservations of step two remove the limit for practical purposes.

## What it costs

- Step one makes a task expensive, as above; the examples do not notice, a server would.
- `select` locking every channel it names serializes selects over shared channels; with few channels per select, which is every real use, this is a handful of uncontended locks.
- A value is copied twice on its way through a channel, in and out of the buffer; a large value is sent behind a pointer, `*T`, which is `Send` whenever `T` is and costs one word.

## What it gains

- The compiler is done with concurrency once it emits the interface; the scheduler is runtime work alone, checked against the same example programs.
- The two steps share the channel structure, its list of waiting tasks, the lock discipline of `select`, and every decision above, so step two is a change of how a task waits, not of what a channel is.
- Programs are written once, as blocking code, and get the scheduler's speed when it arrives without a change.

## Precedent

Go's runtime is the closest ancestor: goroutines on an M:N scheduler with work stealing, channels with wait queues, a netpoller for I/O, all written in Go and assembly over the system's threads. Step two is that design without the garbage collector's stack scanning, which `Send` and the compiler's knowledge of frames make unnecessary. Erlang's BEAM and Pony run one scheduler per core over mailboxes, the actor shape of the actor example made the whole model; Java's virtual threads and Tokio's executor are the same scheduler shape under different surfaces. Step one is how every one of these began: Go 1.0 ran on a scheduler with a single global lock, and shipped.

# Packages and modules

Status: implemented. Built: the module file, the three places an import is found, a required module's own file, the cycle message, the refusals of section 4 and the standard library's privileges held back from a package of the program's own, with `snello build FILE` finding the module above the file; a package of several files, through `token.FileSet` and `types.Config.CheckFiles`; and `snello build DIR`, with `check` and `emit` taking a directory the same way, through `importer.LoadProgram` and the backends' `EmitFiles`, with `examples/packaged/` in the run suite of both backends. Revised: no module name, an import names a directory under the root or a required name, `snm_` for a package's symbols (decisions 1 and 3). Section 6, a package's C, with the module file's `link` line: the checker's list of what crosses, `types.checkBinding`; the importer's C files and its refusal of a bound package with no `.c` file; the header `emit/c.Header` writes and the build of a package's C in both backends; `examples/bound/` in the run suite of both. The language version, the module file's `snello` line (decision 6): read and checked against the compiler's in every module reached, by `importer.ParseModFile`; warned of when the module a command builds, checks or tests has none, by the commands; and written by `snello init`, through `importer.WriteModFile`. Section 7, a file for one platform: `platform.Target.Builds` reads a file's name, and the importer chooses the files of every package by the target's, a standard package's, a test's and a package's C side included, through `importer.Chosen`; `examples/bound/sysname` in the run suite of both backends. Section 9, a dependency required by version from a git repository: `importer.ParseModFile` reads the line; `importer.Module.Resolve`, which the loaders run after `FindModule`, fetches each module into the module cache through `git`, selects one version of each repository, checks every module's hash against its record and `snello.lock`, and writes the file; `importer.HashDir` is the `h1:` hash; `snello add`, `remove`, `update`, `deps` and `fetch` change and show the requirements, through `importer.SetRequire`, `DropRequire`, `Rewrite` and `ImportsOf`; `snello doctor` checks for `git`; `TestRunByVersion` runs a program against a local repository's tag through both backends (decision 8).

A Snello program is one file today, and an import resolves only against the standard library the compiler embeds, so no library can exist outside this repository. This note gives Snello Go's shape for code outside one file: a directory of files is a package, a module file names the directory tree a program's own packages live in, and an import path is found in the standard library, in the module, or through a `require` line that names a directory on disk or, section 9, a git repository at a version. No registry: what one would add is a stage of its own.

## The precedents

- **Go** makes the files of one directory one package, names a module in `go.mod` and resolves an import path under the module path to a directory under the module's; `replace` points a path at a directory. The standard library is found first, and a path whose first element has no dot is reserved for it.
- **Rust** makes a crate the unit, with modules inside it declared in the source and a `Cargo.toml` naming its dependencies, which Cargo fetches and builds. The crate is a bigger unit than a package and the module tree is written in the code, which is more to learn than Go's rule that the directory is the package.
- **Zig** has no package manager in the language at all; a dependency is a path given to the build. Snello follows Go, as everywhere else, and keeps Zig's modesty about what a build needs: a directory.

## 1. A directory is a package

Every `.snello` file in one directory belongs to one package, and the files see each other's top-level declarations, as Go's do. Each file begins with the same package clause; a directory whose files disagree is refused with Go's message, `found packages shapes (area.snello) and shape (shape.snello) in shapes`. A name declared in two files of one package is a redeclaration, reported as one in one file is, with the other file named: `Area redeclared in this block; other declaration at shape.snello:12:6`. Imports are per file, as in Go: a file sees the packages it imports, not the ones its neighbours do.

The package's name is what its package clause says, and the import path's last element is expected to match it, as Go expects; a program may rename the package at the import, `import s "shapes"`, as it may today. A method is declared in the package of its receiver's type, as in Go; a method on a type of another package is refused with Go's message, `cannot define new methods on non-local type shapes.Circle`.

A package of the program's own is checked under the rules a program is checked under today. What the checker allows only to the standard library stays the standard library's: a function without a body, `...ref any` and `any`, `local`, a slice of borrows, and the lowered names of `fmt`, `rc` and `sync`. A package of the program's own gets each with the message a program gets today, `missing function body`, unless it binds C as section 6 says. The checker learns which kind of package it is checking from the Config it is checked under, as Go's compiler learns from its `-std` flag that it is compiling the standard library, where today it reads it from the import path being empty.

## 2. The main package

The main package is the one that declares `func main()`, under any package clause, as today: the examples name theirs after what they show, and `package main` is the name a Go reader expects. The first wording of this rule asked for `package main`, which `snello build` never required, and a slice that required it refused every example. `snello build DIR` builds the main package of a directory, every `.snello` file in it, and names the binary after the directory, as `go build` names it after the directory's last element. `snello build FILE` is unchanged: the one file is the whole main package, as `go run hello.go` compiles the one file named, and a second file beside it is not read. `snello check` and `snello emit` take a file or a directory the same way; `snello lex` and `snello parse` read one file. A build or an emit of a package with no `main` function is refused with `go build`'s words, `function main is undeclared in package shapes`; `snello check` takes any package, as `go vet` does, so a library is checked on its own.

The main package is never imported. An import path that resolves to a directory whose package is `main` is refused as Go refuses it: `import "cmd/tool" is a program, not an importable package`. A package of another name that declares `main` is still importable, and its `main` is an ordinary function there, as it is in Go.

## 3. The module file

A module is a directory tree of packages, marked by a file `snello.mod` at its root. Its first job is to say where the root is; its first directive says which version of the language the module is written for, and the rest is one line per dependency:

```
snello 0.1.0

require regexp ../regexp
```

The file has three directives. `snello VERSION` names the version of the language the module is written for, as decision 6 sets out: a release of the compiler refuses a module written for a later one, and reads a file without the line as written for the first, with a warning. `require NAME DIR` says that the import path `NAME`, and every path under it, is found in the directory `DIR`, relative to the module file's directory or absolute; `require NAME URL VERSION` says that it is found in the git repository at `URL`, at the tag of `VERSION`, which section 9 fetches and locks. One line per dependency, the name one element, since the rest of a path names a directory under the dependency, and a name required twice is refused. `link NAME` names a system library the module's packages need, `link m`, one line per library, which section 6 explains; a flag or a path is refused, since the line names what `-l` names and nothing else. A `//` comment runs to the end of its line. Nothing else is in the file: no module name, no `go` directive, no `replace`, since a `require` line already names a directory, which is what Go's `replace` makes of a requirement, and no hashes, which the lock file beside it holds (section 9). A directive the file does not have, or a line that is not one, is refused with its line: `snello.mod:3: unknown directive "exclude"`; Go's `module` and `go` lines are directives the file does not have, refused as every other is, as `go.mod` refuses Cargo's `edition` with `unknown directive: edition`.

The module has no name because an import does not need one (decision 1): a program imports a package by the name of its directory under the root, `import "shapes"`, and a dependency by the name its `require` line gives, `import "regexp"` and `import "regexp/syntax"`. Go's module path, `example.com/app`, repeated in every import, is the one piece of Go's shape Snello leaves out; it exists for a registry that serves modules by their path, which is a stage of its own, and a dependency fetched then will still be imported by the name its line gives, as a Cargo dependency is used by its name whatever its source.

A name that is a standard package's cannot be required, `snello.mod:1: strings is a standard package`, and a directory of the root that holds a package under a standard package's name is refused when the module is read, `the directory strings shadows the standard package strings; rename it`, since the standard library answers an import first and the directory could never be reached.

The module a program belongs to is the one marked by the nearest `snello.mod` in the program's directory or above it, as Go finds `go.mod`. A program with no module file above it, every program under `examples/` today, imports the standard library alone, as it does now. A module file is read by every command that loads a program, and written by two. `snello new DIR` makes a directory that must not exist and starts a module in it, the module file, a program and its test, as `cargo new` does; one that exists is refused, `snello new: hello already exists`, as Cargo refuses it with `destination … already exists`, and its parent must exist, so that `new` makes one directory and leaves a module whole or nothing. `snello init [DIR]` starts a module in the current directory or `DIR`, a directory that exists: it writes `snello.mod` holding the version line of the compiler that runs it, `snello 0.1.0`, and nothing else, and refuses a directory that has one already, with the file's absolute path, as `go mod init` refuses with `go: /path/go.mod already exists` and `cargo init` with `` `cargo init` cannot be run on existing Cargo packages ``; anything else under the file's name, a directory or a link to nothing, is refused as in the way. A module under another module's tree is the nearest file up from a program, as the rest of this section says, so `init` does not look above the directory.

## 4. How an import path is found

A file imports a path, and the importer answers it from three places, in this order, taking the first that has it:

1. **The standard library**, embedded in the compiler. `fmt` is always `fmt`; a module cannot shadow a standard package, and section 3 refuses a directory or a require line that would try.
2. **The module's directories.** A path names the directory at that place under the module's root: `shapes` is `shapes/` and `cycle/a` is `cycle/a/`. The directory must hold a `.snello` file: `no package at shapes/ for import shapes`.
3. **The `require` lines.** A path whose first element is a required name names the directory the line gives, or a directory under it for the rest of the path: with `require regexp ../regexp`, the import `regexp` is the directory `../regexp` and `regexp/syntax` is `../regexp/syntax`. A required directory may have a `snello.mod` of its own, whose `require` lines are followed for its own imports, so a library can depend on a library; it may have none, when it is a directory of packages and nothing more. A required module's own imports are answered within it, its directories and its require lines, and the package is named by the module's id, the require name that first reached the module, and its directory under it: the dependency's `import "util"` is the package `regexp/util`, so that the program's `util` and the dependency's are two packages with two symbol prefixes, and a module a dependency requires is named through both, `regexp/syntax/x` (after a review found the two loaded as one). A module file deeper in either tree is not looked for.

A path that both a directory of the module and a require line answer is refused as ambiguous, `import "twin" is both a directory of the module and under the required twin`. A path none of the three answers is refused at the import, with the places searched: `package other is not in the standard library, in the module's directories or in its require lines`, or, with no module file, `package nosuch is not in the standard library, and no snello.mod above the program marks a module`. An import path is a path as Go defines one: elements separated by `/`, none empty, none `.` or `..`; a relative path is refused, `malformed import path "./shapes": a relative path; name the package by its directory under the module`.

An import cycle is refused with the cycle written out, at the import that closes it: `import cycle: cycle/a imports cycle/b imports cycle/a`. The standard library's own message takes the same form.

## 5. One program, one compilation

A package of the program's own is loaded as the standard library's are today: parsed, checked once into the program's `types.Info`, and compiled with the program by whichever backend runs, into the one C file or the one IR module, each of its top-level names qualified by its import path in the backend's symbol, so the module is linked as the program is and link-time optimization sees it whole. Nothing of this changes for a package of the program's own but the space: a standard package's symbols are `sn_<path>_<Name>` with `/` written as `__` (`07-lowering.md`), the names the runtime defines, and a package of the program's own takes the same form in a space of its own, `snm_<path>_<Name>`, which the runtime never uses, so a package may have any name without meeting the runtime's: `shapes.Area` is `snm_shapes_Area` and `cycle/a.A` is `snm_cycle__a_A` (the first form put both in `sn_` and needed a dot in every module path to keep them apart). A path may carry a dot or a dash no C identifier may, `my-lib`, and each is written as `_`; two paths that would share a prefix this way, `a.b` and `a_b`, are refused by the backends, `import paths a.b and a_b would share one symbol prefix`, since no real program meets it.

A package of several files is several compilation units of one package, so every pass that takes a file and its syntax takes a list of them. A position must then say which file it is in: `token.Pos` is a byte offset in one file today, and gains a base per file through a `token.FileSet`, as `go/token`'s does, so a position anywhere in the program resolves to its file, line and column, and the checker and the backends report an error in a second file with that file's name. The parser fills a file the set made; `parser.ParseFile` keeps its signature for one file on its own.

## 6. A package's C

The standard library reaches the runtime through functions declared without a body, which the runtime defines in C under the derived symbol, and the runtime is compiled with the program. A library outside the compiler that wraps a C library, as Rust's crates do through `extern "C"` blocks and `-sys` crates, needs the same two things: a declaration without a body bound to a C symbol, and C compiled and linked with the program. Both come the way Go has them, with nothing added to the language: no pragma, no `import "C"`, no `extern` block.

**The declaration.** A function without a body in a package of the program's own is a binding to C, as a Go function without a body is implemented elsewhere, and its symbol is the one every function of the package gets, section 5: `cbrt` in the package `mathx` is `snm_mathx_cbrt`, which the C side defines under that name. The symbol is never renamed, so binding a library's own function is a shim of one line in the package's C, `double snm_mathx_cbrt(double x) { return cbrt(x); }`, as `cgo` writes one for every call. The main package keeps the refusal, `missing function body`: a program binds C through a package or not at all, so that the C side of a program is always a directory a reader can find. The other privileges of the standard library stay the compiler's, decision 2: `any`, `...ref any`, `local`, a slice of borrows and the lowered names, each of which exists for one standard package.

**What crosses.** The C form of every Snello value is what `runtime/c/snello.h` defines for the standard library, so the C signature is derived from the Snello one and written nowhere twice. A bound function may take and return: the numbers, `int` and `uint` as `int64_t` and `uint64_t`, the sized integers and `byte` as their C sizes, `f64` and `f32` as `double` and `float`, and `bool`; `ref string` as `sn_string` and `ref []byte` as `sn_slice_u8`, each a view of the bytes, pointer and length, that C reads during the call and must not keep; `mut []byte` as `sn_slice_u8 *`, a buffer C fills within its capacity and whose length it sets, as `bufio`'s `copyBytes` fills one; and a `mut` number or `bool` as a pointer to it, `int64_t *`, the out-parameter by which C reports a count, an error code or a yes. A C library's handle crosses as an `int`, the next paragraph. Anything else is refused at the declaration with the type named, `cannot cross to C: map[string]int, in parameter counts`: a pointer, a struct by value, a slice of anything but bytes, a map, an owned `string` or `[]byte`, an option, a result, a tuple, a closure, a trait value or a type parameter. The list is short so that the ABI is the runtime's own and nothing is marshalled; a library that needs more writes the conversion in Snello around the binding, as a `-sys` crate's user writes it in Rust.

**The handle.** A C library hands back a pointer the program must keep and later close. It crosses as an `int`, the pointer's value, which Snello never reads, and the package wraps it in a struct of its own with a `Drop` method that calls the bound `close`, `func Open(start int) *Tally { return &Tally{handle: open(start)} }`, so a handle dropped is a library closed, and the struct is made and freed by the program as any value is. The first design had C make the struct's block with `sn_alloc` and hand back the owned pointer; a review found that a struct with a `Drop` method carries a flag the compiler sets when the value is made, which the C side cannot know to set, so the drop never ran. Keeping the struct on the Snello side costs nothing and leaves the C author no internal field to fill. What the C side does with its own memory is the library author's responsibility, as it is inside Rust's `unsafe`.

**The C side.** The `.c` and `.h` files in the package's directory are compiled with the program, as `cgo` compiles the C files of a package: the build copies them into the build directory beside the runtime's files, under a directory named by the package's symbol prefix so that two packages' `util.c` do not meet, compiles each with the runtime's flags, the checks' flags in a debug build, and links the objects with the program's and the runtime's. The compiler writes a header for the package into that directory, named after the package, `mathx.snello.h`: it includes `snello.h` and declares the prototype of every bound function, derived from the Snello signatures, and the package's C includes it, so that the C compiler checks each definition against its declaration, as `cgo`'s generated export header lets it; a definition with the wrong types is then a compile error at the C side, not an undefined call. A package may not ship a file of that name, and a package with a `.h` file and no `.c` file is refused as one with none. The package's C includes `snello.h` and its own headers; the runtime's other files are within reach of the include path and are not for it. The LLVM backend already declares a function without a body from its signature and calls it under C's convention, as it calls the runtime; the C backend writes the same prototype into the program's C file, where today it relies on `snello.h` for the standard library's.

**A system library.** `link m` in the module file, the module's own or a required module's, is `-lm` at the link of every program that imports a package of the module: a library the system's linker finds, as Go's `#cgo LDFLAGS: -lm` names one. No search path and no other flag crosses the module file in this design; a library installed elsewhere is a decision for when one is needed, with Go's `pkg-config` directive as the precedent. The compiler never runs a build script.

**What the C side must promise.** It keeps no view past the call, since the bytes belong to the caller; it calls nothing of the program back, since no Snello function has a C symbol a library may rely on and the runtime's state is the worker's; and a bound call blocks the worker thread it runs on until it returns, as a file read does today, so a library that waits on a device is a library that holds a worker. These are written in chapter 15, the book's chapter on binding C, and they are the whole of the contract: the compiler checks the types, and the author keeps the rest.

**The pieces.** The checker allows a missing body in a library package and checks each parameter and result against the list, with the message above. The importer records a package's C files beside its Snello files, and the module file's `link` lines. Both backends' builds take the C files and the libraries, write the package's header, and compile and link them. `examples/bound/` is the proof in the run suite of both backends: a package with its own `.c` and a handle with `Drop`, which the program sees given back; and `mathx`, binding `cbrt` through `link m` in a shim of one line.

## 7. A file for one platform

A package that does one thing differently on each system, a library binding C whose calls differ between systems, writes a file for each, and the file's name says which platform it is for, as Go's does: `poll_linux.snello` is built only for Linux, `poll_arm64.snello` only for an arm64 processor, and `poll_darwin_arm64.snello` only for macOS on arm64. No attribute inside a file chooses: the platform is in the name, so a listing of the directory shows which file is for which platform before any file is opened.

**The rule** is go/build's, read the same way. The extension is cut at the first dot, then everything up to the first `_`, then a last element `test`; what is left is read from its end. Two last elements that are a system and a processor, `_linux_amd64`, are for that platform alone; a last element that is a system, `_linux`, is for that system on any processor, and one that is a processor, `_arm64`, for that processor on any system; `_unix` stands where a system does for every Unix, `_unix` and `_unix_arm64`; any other name is for every platform. A name with no `_`, or whose platform word is its first element, `linux.snello`, is for every platform, as Go has had it since 1.4, so that a system named later does not change what an existing file means. A test file is chosen the same way, `poll_linux_test.snello`, and so is a package's C side, `shim_linux.c` and `shim_darwin.h`, as go/build chooses a cgo package's C files by their names.

**Where it applies.** Every directory a package is read from: the program's own, `snello build DIR`, a package of the module, a package of a required module, and the standard library's, whose packages may hold such files as any package may; the runtime's C is not a package, and keeps choosing inside its files. The platform is the one the program is built for, the host's unless `-target` names another (`07-lowering.md`, building for another platform), which the importer is given as a `platform.Target`, Go's `GOOS` and `GOARCH`. A file named on the command line, `snello build tool_linux.snello` on macOS, is built as named, as `go run tool_linux.go` builds it on macOS: a file named is the whole program, chosen by whoever named it. A file whose name begins with a dot or an underscore, an editor's lock, `.#poll.snello`, or a file set aside, `_old.snello`, is no file of the package, as go/build passes such names over, and the rule never reads it.

**The words.** A name is read against the list of systems and processors Go knows, internal/syslist, which is the vocabulary a reader brings: `linux`, `darwin`, `windows`, `freebsd`, `amd64`, `arm64`, `riscv64` and the rest. Snello builds for three systems, `darwin`, `linux` and `windows`, and two processors, `amd64` and `arm64`, the six platforms the runtime supports; a file named for any other, `poll_freebsd.snello`, is built for no target, and left out as a file for another platform is. So one package holds the files of every system, those of a system Snello comes to build for later among them, and a library written for FreeBSD before Snello builds for it compiles unchanged on the others, as it does with Go, with Rust's `cfg(windows)` and with Swift's `#if os(Windows)`. A last word that is no platform's is part of the name, `string_builder.snello`, and a misspelt system is no platform's either, `poll_linx.snello`, built for every platform, as Go builds `poll_linx.go`; a list of words cannot tell a misspelling from a word. The first design refused a name for a system Snello does not build for, so that its author would learn that no build compiles it; a review set that aside as no compiler's practice, and as a cost to every library that carries files for a system before Snello supports it, a C library copied into a package with a file per processor first of all.

**A directory with nothing for the platform** is refused, as go build refuses one: `every .snello file in DIR is for another platform than darwin/arm64`, where Go says `build constraints exclude all Go files in DIR`. A directory holding only another platform's files is not a package on this one, and an import of it would otherwise read as a mistyped path.

**One group of systems, `unix`.** With Windows, code that Linux and macOS share and Windows does not would otherwise be written twice, once in `_linux` and once in `_darwin`. A file named `poll_unix.snello` or `shim_unix.c` is built for every Unix, the systems of Go's list that are one, Linux and macOS among Snello's targets, and not for Windows; it takes a processor as a system does, `poll_unix_arm64.snello`. Each language that runs on both kinds of system names the family: Rust's `target_family = "unix"`, `#[cfg(unix)]`, and Python's `os.name == 'posix'`; C has no reliable one, since `__unix__` is not defined on macOS. Go names it in a build line alone and builds a file named `_unix.go` on Windows too, since files of that name were written before Go took `unix` as a constraint and would have changed meaning; Snello has no build line and no such files, so the file's name says it. No other group is named: a file for every system is the file with no platform word. The checker checks the files the platform builds and no others, as Go's does: `snello check -target linux/amd64` checks a Linux file from a Mac, and CI builds on each system it runs on.

**The precedents**, run as programs. Go 1.27 on macOS, with `a_linux.go`, `b_freebsd.go` and `c_linx.go` in a package: `go list` with `GOOS=linux` builds `a_linux.go` and `c_linx.go` and leaves `b_freebsd.go` out; `go build` of a directory holding only `a_linux.go` says `build constraints exclude all Go files in DIR`; `go run main_linux.go` runs it. Rust chooses with `#[cfg(target_os = "linux")]` on an item or a module, Swift with `#if os(Linux)` around code, Zig with a comptime test of `builtin.os.tag`: each a condition inside a file, which a reader evaluates to know what a file holds, and which Go's build lines also allow. Snello keeps Go's file names and leaves out the build line, so that what a file is for is its name and nothing in it.

**Memory safety.** The rule chooses files and nothing else: every file chosen is checked by the same checker, borrow rules included, and no runtime or collector is involved.

## 8. What is not here

- **A registry and ranges.** A dependency by version is a git repository's tag, section 9; a registry that serves modules by name, a version range such as Cargo's `^0.2`, and a checksum database are stages of their own, after `regexp` has shown what a library outside the compiler needs. Raising a requirement is `snello update`, section 9.
- **Vendoring.** None, by decision: a dependency by version is fetched into the module cache by the build that needs it and checked against the lock file on every build, so a program's dependencies just work, and no copy of them is kept beside the program, as Go's `go mod vendor` and Cargo's `cargo vendor` keep one, to fall out of step with the lock file. A program that must build with no network fills the module cache once. A file is chosen for a platform by its name alone, section 7, and no build tag chooses. Test files and `snello test` are `09-testing.md`'s.
- **Nested modules and workspaces.** A `snello.mod` under another's tree is not looked for; the nearest file up from the program is the module, and the rest are ignored.

## 9. Dependencies by version

A module published for others lives in a git repository, and a program that uses it names the repository and a version: `require regexp https://github.com/snello-lang/regexp 0.2.0`. The precedents are Go's modules, Cargo's git dependencies and the Swift Package Manager; Snello keeps what they agree on, a module cache, a lock file and a hash of each module, and goes past each where it is weak, which the end of this section sets out. A dependency is fetched by the build that needs it and just works: there is no command to run first and no copy of it kept beside the program (section 8).

**The line.** `require NAME URL VERSION`, four words, beside the three of `require NAME DIR`, which keeps its meaning: a directory is not fetched and not locked, as Cargo's `path` dependency is neither. `URL` is a git repository's address with its scheme, `https://` or `ssh://` with a host, or `file:///` with an absolute path for a repository on the machine's own disk, as Cargo's `git` key takes it, and written one way, so that one repository is one module and one line of the lock file: printable ASCII, the host in lower case, no `/` at its end, no empty, `.` or `..` element in its path, no query and no fragment. A URL that carries a password is refused, since the lock file and every message would show it; git's own credentials hold it. A line that breaks a rule is refused at its line, naming the rule, `snello.mod:4: a repository is named by its URL, https://host/path, and "https://Example.com/re" has a host in upper case: write it in lower case`. `VERSION` is a SemVer version written as the `snello` line writes one, `0.2.0`, with no build metadata, which orders nothing, and it names the repository's tag `v0.2.0`, the form most tags on the forges take, with a pre-release, `0.2.0-rc.1`, naming `v0.2.0-rc.1`. A branch or a commit is not a version and is never taken, even a branch named as the tag is: what a program builds against is a release its author tagged.

**The module cache.** A module fetched by version is kept in the module cache, the directory `SNELLO_MODCACHE` names, else `snello-modules` in the user's cache directory, apart from Snello's build cache, so that clearing the build cache, which chapter 32 tells a user may be removed at any time, never makes a build offline fail for its modules. Each module at each version is one directory, `<host>/<path>@<version>`, with each upper-case letter written as `!` and the letter in lower case, so that two repositories whose names differ only by case are two directories on a file system that folds case, and any other character outside letters, digits, `.`, `-`, `_` and `/` written as `!` and its byte in hexadecimal, which begins with a digit where a letter's form begins with a letter; a `file:///` repository is under `file/` and its path, and a URL whose directory would not lie under the cache is refused, whatever its form. The directory holds the files of the tag's tree, regular files and directories only: no `.git`, and no symbolic link, whose target could lie outside the module and outside its hash. Beside it, a file named for it with `.h1` after records the commit the tag named and the hash of the files when they entered the cache, and is written last, so that its presence is what marks the module whole; a record whose directory is gone is no module, and the module is fetched again.

The files are not made read-only, as Go makes its cache's: every build hashes them again, so an editor that changes a file in a dependency changes nothing a build uses, and the cache can be removed, whole or a module at a time, by any tool, where Go's needs `go clean -modcache` or a change of permissions first.

**The fetch.** A module is fetched by `git`, which the build runs as it is on the path, with the user's own configuration, so that a private repository the user can clone is one the build can fetch. A fetch makes a bare repository of its own in a work directory at the cache's root, whose path stays short whatever the module's escaped path runs to, since git on Windows writes no path past 260 characters, and fetches into it the tag alone, by its full reference, `git fetch --depth 1 --no-tags -- URL +refs/tags/v0.2.0:refs/tags/v0.2.0`, so that a branch of the tag's name is never taken; reads the commit the tag names; and unpacks the tag's tree from `git archive` into a directory of its own, which is renamed into place once it is hashed. The repository's own attributes are overridden for the archive, `* -text -eol -export-subst -filter -ident -working-tree-encoding` in its `info/attributes`, so that no line ending is converted, as Git for Windows converts on checkout, no `$Format$` is expanded, which writes the date, and no filter of the user's runs, as git-lfs does: a module's files are its commit's blobs, byte for byte, for every user and at every moment, and so is its hash. Git runs with no prompt, `GIT_TERMINAL_PROMPT=0`, and where the user names no ssh of their own with `ssh -o ControlMaster=no -o BatchMode=yes`, so that a fetch never waits on a password it cannot ask for or on a shared ssh connection that holds its output open; and with the variables that point git at a repository of the environment's taken out, `GIT_DIR` and the rest `git rev-parse --local-env-vars` lists, which every git hook sets, so that a build run from a hook fetches the repository it names and not the one the hook runs in. Of two builds that fetch one module at once, the second to rename keeps the first's copy, and refuses when the two found other files, a tag moved between the two fetches; a fetch stopped part way leaves a directory that the next fetch removes once an hour has passed. A build that needs a module the cache lacks and finds no `git`, or a `git` that cannot run, says so, with the install command `snello doctor` names for it, as it says of a missing clang; a fetch that fails names the module and gives git's own words.

**The lock file.** Beside `snello.mod`, the program's module keeps `snello.lock`, one line for every module the program reaches by version, its own dependencies' dependencies among them, sorted by URL and then by version: the URL, the version, the commit its tag named, and the hash of its files:

```
https://github.com/snello-lang/regexp 0.2.0 <the commit's id> h1:<base64 of the SHA-256>
https://github.com/snello-lang/unicode 0.4.1 <the commit's id> h1:<base64 of the SHA-256>
```

The line records both what the precedents record one of. The hash is of the module's files, the `h1:` form Go keeps (`golang.org/x/mod/sumdb/dirhash`, `Hash1`): SHA-256 over a listing of every file's SHA-256 and its path, in order of path, written in base64. A hash of the content holds whatever the repository's history does and is SHA-256 where a commit id is SHA-1 in most repositories; it lists each file under the module's directory alone, where Go's lists it under the module's path and version, so a fork or a mirror of the same files hashes the same. The commit is what Cargo's `Cargo.lock` and the Swift Package Manager's `Package.resolved` record, and what Go's `go.sum` lacks: with it, a tag that moved is named by the two commits it named, which a reader can look up in the repository, where Go names two hashes no tool can explain.

The file is written by the build, as Cargo writes `Cargo.lock` and the Swift Package Manager `Package.resolved`, and not by a command of its own, as Go's `go mod tidy` writes `go.sum`: a module required by a new line is fetched and locked by the first build that needs it, a line no longer reached is dropped, and the file is rewritten only when its records change, so that a checkout that wrote its line endings otherwise, as Git for Windows does, is not rewritten by every build. It is read from the program's module alone: a dependency's own `snello.lock` is not read, as Go reads no dependency's `go.sum` and Cargo no dependency's `Cargo.lock`, since the program's file already holds every module it reaches. The file is meant to be committed, for an application and a library alike, so that every checkout builds what the author built. A program that requires nothing by version has none, and one that stops requiring by version has its file removed.

**The cache heals, the lock file holds.** The lock file is what the program holds to; the cache is a copy that can be fetched again. Every build hashes each module's files and compares them with the record of its entry into the cache and with the lock file. A cached copy whose files changed, or whose record the lock file does not agree with, as when a teammate's lock records a tag fetched after its author moved it and this machine fetched it before, is discarded and fetched again; only a module that, fetched anew, still disagrees with the lock file stops the build, naming both commits, both hashes and what to do:

```
snello.lock: https://github.com/snello-lang/regexp 0.2.0 was locked at commit 3f2a9c1d0b47, h1:5dHb…, and the tag v0.2.0 now names commit 8e01d77a52c9, h1:Qm7c…:
the tag was moved to other code, or the repository rewritten; if the change is meant, remove the line and build again
```

One commit whose files, fetched anew, hash otherwise than the lock file says, which only two commits sharing one id make, since the fetch converts nothing, is refused naming the commit and both hashes, with `remove the line only if you trust the repository`. Nothing is built from a tag other than the one the lock file records: Go refuses, but names only two hashes, and the Swift Package Manager refuses; Cargo, which builds the locked commit whatever the tag says now, is the precedent set aside, since a program built from a tag its author has since replaced is a program no one can rebuild from the tag. Hashing a module's files on every build is what Go leaves to `go mod verify`, run by hand; it costs little: the whole standard library, 70 files and 838 KB, hashes in 2.9 ms on an 8-core arm64 Mac, where a build takes seconds.

**One version of each module.** A program reaches each repository at one version. When two modules require one repository at two versions, the build takes the highest of them, the minimal version selection of Cox's "Minimal Version Selection" (2018): every requirement is a lowest version its module was built and tested against, so the highest of the lowest is the oldest version every module accepts, and the result depends on the requirements alone, not on what the repository holds today or the order the build reads them in, which is what lets a lock file record it and a second machine select it again. A module is the same module across the versions that share its first number other than zero, as Cargo's and npm's caret reads SemVer: across minor and patch versions of one major from `1.0.0`; across patch versions of one minor before it, since SemVer lets a minor release break what a `0.x` release promised; and at one patch version before `0.1.0`, `0.0.3` and `0.0.4` being two modules. Go's selection reads every `v0` as one, which SemVer does not promise. After the selection, every requirement the program makes and every requirement a selected module makes is checked against the version selected for its repository, and one across that line, `1.4.0` against `2.0.0`, or `0.2.0` against `0.3.0`, is refused, naming both and who requires each: `https://github.com/snello-lang/regexp is required at 0.2.0 by https://github.com/x/scan 1.0.0 and at 0.3.0 by the program; a program builds against one`. A version that lost the selection is never built, so what it requires is nothing to the program: a library that raised a dependency of its own in a later release does not fail a program built against that release. Every version reached is still locked, the one the program builds against and the ones read for their requirements, so that the selection is made again from the same files on every machine. A requirement made by a module of the program's own reached by a directory is named by that module's file, so the message points at the line to change. Two majors of one repository in one program are refused, where Go allows them as two modules by putting `/v2` in the import path and Cargo by building both; a later decision can allow them without breaking a module file. A repository reached both by version and by a `require NAME DIR` line is two modules, the directory and the fetched copy, as decision 5 has it of two directories.

**Inside a fetched module.** A module fetched by version is read as any required module is, section 4, with its own `require` lines followed, but one that names what its author's disk alone holds is refused: a `require NAME DIR` line, `https://github.com/x/scan 1.0.0 requires lexer by a directory, ../lexer, which a module fetched by version cannot reach`, as Go ignores a dependency's `replace` and Cargo refuses to publish a crate with a `path` dependency that has no version; and, in a module fetched from a host, a `file:///` repository. A module fetched from this machine's own disk may require another repository on it, which this machine reaches. A fetched module's `snello` line is checked as every module's is, decision 6, with its URL and version in place of its path.

**Offline.** A build that finds every module it reaches by version in the cache, at the commit and the hash the lock file records, runs no `git` and needs no network, as Cargo's `--offline` and Go's `GOFLAGS=-mod=mod GOPROXY=off` build from their caches; there is no flag, since the network is only ever touched for a module the cache does not hold. A build offline that needs a module the cache lacks fails at the fetch, naming the module and git's error. The module cache is asked for only when a module is required by version, so a program that requires nothing by version builds where no cache directory can be named.

**The commands.** Five commands change and show a module's dependencies, so that a developer never edits a require line by hand to get one right: `snello add NAME URL [VERSION]` requires a repository's latest release, its highest tag `vX.Y.Z` with no pre-release, or the version named, and changes the version of a line already requiring the name from that URL; `snello remove NAME...` drops requirements, refused while any file of the module, a test file among them, imports the name, naming each import; `snello update [NAME...]` raises what the module requires by version to the latest release compatible with it, which shares its first number other than zero, and with `-major` to the latest whatever its major; `snello deps` lists each module reached by version, the version selected and who requires which, and `snello deps -why NAME` or `-why URL` the chain from the program; `snello fetch` fills the module cache and the lock file without building. The three that change `snello.mod` check what they are given before asking a repository anything, edit the file's text, keeping its comments, its layout and its line ends, and resolve the edited text as a build does, fetching, selecting and locking, before the file is written, through a file renamed into place; so the module file is never left naming a version that cannot be fetched or a selection that cannot be met, even by a command stopped part way. Cargo's `cargo add`, `cargo remove`, `cargo update` and `cargo tree` and Go's `go get`, `go mod graph` and `go mod why` are the precedents; there is no `tidy`, since the build keeps the lock file itself.

**Where it goes past the precedents.** Each choice above keeps what the three agree on and fixes where one is weak:

- **One lock file, written by the build, one line a module.** Go's `go.sum` holds two lines a version, the module's and its `go.mod`'s, keeps a line no build reaches until `go mod tidy` runs, and stops a build with `missing go.sum entry; to add it: go mod download` that the tool could have added itself. Cargo and the Swift Package Manager write their files from the build, which Snello does, with Go's hash in the line, which theirs lack.
- **The commit and the hash, not one of them.** A moved tag is named by its two commits, which Go cannot say, and the files are held by SHA-256 whatever the history, which Cargo and the Swift Package Manager do not hold.
- **The same hash for every user.** The fetch converts nothing, line endings, `$Format$` or a user's filter, where Go's `git archive` applies a repository's `export-subst` and a user's filters, so a module could hash otherwise on another machine.
- **A cache that heals, checked on every build.** Go checks a module when it downloads it, trusts its cache after, and makes it read-only, so that removing it needs `go clean -modcache`; Cargo trusts its checkout. Snello hashes again each build, fetches again a copy that changed or that the lock file does not agree with, and leaves the files writable, since the hash, not a permission, is what holds them.
- **A moved tag refused, never silently built.** Cargo builds the locked commit whatever the tag says now; Go refuses, but only by two hashes.
- **What a lost version requires counts for nothing.** A requirement is checked against the selected version only when a selected module, or the program, makes it.
- **No version in an import path.** Go puts `/v2` in every import of a second major version; Snello imports a dependency by the name its line gives at every version, and refuses two majors of one repository in one program until a program needs both.
- **Private repositories with no settings.** Go needs `GOPRIVATE`, `GONOSUMDB` or `GOPROXY` set before it fetches a repository its proxy cannot see; Snello fetches every repository with the user's own git, so one the user can clone is one the build can fetch.
- **The tag alone.** Go, when it fetches from a repository directly, clones its history to find the version; Snello fetches the one tag, `--depth 1`, and never a branch of its name.
- **A change all or nothing.** `go get` and `cargo add` write the manifest and then resolve; Snello's commands resolve the edited text first and write the file only when it holds, so a failed or stopped `add` or `update` leaves nothing to undo.
- **A removal that does not break the build.** `cargo remove` and `go get NAME@none` drop a requirement whatever imports it, and the next build fails; `snello remove` refuses while a file under the module imports the name and says where, looking wider than a build reaches, a nested module, a directory under `_` and a file that does not parse among it, so that it may ask for a look but never misses an import.

**Where it is built.** `importer.ParseModFile` reads the line of four words into a `Require` with a URL and a version; a comment begins a word, so that the `//` of a URL is no comment, as `go.mod` reads one. `Module.Resolve` (`versions.go`), which `LoadProgram` and `LoadPackage` run once the module is found, walks the require lines of the program's module and of every module they lead to, fetches each module by version through the module cache (`modcache.go`), checks and heals it, selects one version of each repository, checks the selected modules' requirements and writes `snello.lock`, before any package is read. It reads the file of a module required by a directory for its own requires, and passes over one that does not read, which the import that reaches it reports, decision 6; a fetched module's file must read, since its requirements decide the selection. The importer's `enter` gives a reached module's require lines by version the directories selected. `SetRequire`, `DropRequire`, `Rewrite` and `ImportsOf` (`requires.go`) are what the commands change, and the commands are `cmd/snello/deps.go`, with `ReleaseVersions` (`modcache.go`) listing a repository's releases through `git ls-remote`. `snello doctor` checks for `git`, which a build needs only for a module required by version, so its failure does not fail the doctor. Chapter 35 of the book is the guide for a user and a maintainer.

## Decisions

**Decided 1: the directory is the package, and the module file is Go's `go.mod` without versions.** The alternative, a package declared in the source as Rust's `mod` tree is, was set aside because a Go developer must read a Snello program without a glossary, and Go's rule needs none: the files beside you are your package. The module file keeps Go's two words, `module` and `require`, and no third, so that a reader of `go.mod` reads `snello.mod` at sight (decision 4 adds `link`, for what Go says in a comment; the revision below drops `module`); `require` naming a directory rather than a version is the one difference, and it is Go's `replace` under the name a reader meets first. Revised so that there is one way to import and no mistake of Go's: the module file has no `module` line and the module no name, an import names a directory under the root or a required name, and `require` names a dependency rather than a path, as a Cargo dependency is named; Go's module path in every import, its dot rule that holds for a fetched module and not a local one, and its `/v2` suffix are what is left out.

**Decided 2: no privilege for a package outside the compiler.** A package of the program's own cannot declare a function without a body or write `...ref any`, beyond what section 6 allows a package that binds C; the standard library keeps its privileges, and a library outside the compiler is built on the core as it is.

**Decided 3 (withdrawn): a dot in the module path's first element.** The rule kept a module path out of the standard library's names and a module's symbols out of the runtime's. With no module path there is nothing to spell: a directory or a require line under a standard package's name is refused outright, and a package of the program's own has a symbol space of its own, `snm_`, so the runtime's names are never met.

**Decided 4: C through a package, with the runtime's ABI and one more word in the module file.** A package of the program's own binds C as the standard library does, a function without a body under the derived symbol with the C types `snello.h` already gives Snello's values, rather than through a pragma or an `extern` block, since the language gains nothing and the standard library has shown the shape works. The types that cross are the few the runtime passes already, so nothing is marshalled, a handle is an int the package wraps, and a library that needs more converts in Snello. The module file gains `link NAME` for a system library, the one word beside `require`: Go names a library in a `#cgo` comment, Rust in an attribute or a build script and Zig in its build program, and Snello has none of the three, so the module file, which already says where a dependency is, is the smallest place that can say what it links.

**Decided 5: a module is its directory, whatever route reaches it.** A module has no name, decision 1, so the importer had named a required module's packages by the route of require names that reached them, `b/d/util` for the `d` that `b` requires. A test of a diamond, two dependencies requiring one third, showed the cost: the third was loaded once per route, its one type became two, and a value of it could not pass from one dependency to the other, `cannot use a value of type util.Thing as util.Thing`. Every real dependency graph has diamonds, so the identity of a module cannot be its route. It is its directory: the importer keys the modules it has reached by the directory's one spelling, absolute with symbolic links resolved, and the first require line to reach a directory gives the module its id, the require's name, under which every package of the module is named from then on, `d/util`, whichever require line and whichever name reaches it later. Two different modules reached under one name are told apart by a numeral after a `~`, `d~2`, a character an import path may not hold, so the id names no directory and no require; the backends' check of symbol prefixes still refuses the one collision the mapping to a C symbol could make. A module's packages carry that module's `link` lines, not the importing module's, which the route-named importer had wrong. When a registry comes, section 8, the identity becomes the name and version it is published under, and this id becomes that name; the imports inside a module do not change.

**Decided 6: the module names the version of Snello it is written for.** A module file says which release of Snello its packages are written for, `snello 0.1.0`, so that a later release can change a rule for the modules that name it and keep every older module compiling as it was written: what Go's `go 1.27.4` line does for a module and Rust's `edition` for a crate. The line costs nothing before 1.0 and could only be added as a breaking change after it, which is why it comes now.

- **The line is a Semantic Versioning 2.0 version**, the scheme Snello's releases are numbered by: `snello MAJOR.MINOR.PATCH`, with a pre-release after a hyphen and build metadata after a plus as SemVer allows, `snello 0.2.0-rc.1`, and each number in decimal with no leading zero (semver.org, items 2, 9 and 10). It names the oldest release that compiles the module, as Go's line has since Go 1.21: `go mod init` writes the full version of the Go that runs it, `go 1.27.4`, and Go 1.27.4 refuses a module asking for 1.27.5. One way to write each version, so a spelling SemVer does not have is refused with the form and an example, `snello.mod:1: malformed version "0.1": a version is MAJOR.MINOR.PATCH, snello 0.1.0`, which covers `0.1`, `v0.1.0`, `01.2.0` and `0.1.0.0`; a line of no version or of two words after `snello`, with `snello needs one version, snello 0.1.0`; a second `snello` line, as Go refuses a repeated `go` line. The line is the first directive of every module file of the repository, where a reader looks, and the file does not require it there, as `go.mod` does not.
- **Two versions compare by SemVer's precedence** (item 11): major, minor and patch numerically; a pre-release before the release it precedes, `0.2.0-rc.1` before `0.2.0`, and two pre-releases identifier by identifier, numbers numerically and below words, words in ASCII order, a shorter list first when the longer begins with it; build metadata never. A number compares by its count of digits and then digit by digit, which is numeric order since no number has a leading zero, so a version of any length compares without being read into an integer that could overflow.
- **The compiler's version** is the SemVer version of the release being built, `0.1.0` today: a constant of the package `compiler/version`, `version.Current`, set at the start of each release's work, as Go's `internal/goversion.Version` is raised at the start of every release cycle. `snello version` prints it with what else the binary says of itself, `snello 0.1.0 (8477985) stable darwin/arm64`: the commit, read from the build information Go records, marked `-dirty` when the tree had changes, as `git describe --dirty` marks it, and left out when the build recorded none, as a binary built outside a checkout or with stamping off has none; the channel, which a release build stamps in with the linker's `-X`, and which a build from source, stamped with none, names `devel`, keeping the version, as a development build of Go says `devel go1.28-…` and a nightly Rust `1.94.0-nightly`; and the system and processor. The version a module is checked against is `version.Current` in every build. The language changes only in a minor release, a patch release fixing the compiler, so a rule tied to a version starts at a minor release, `0.3.0`, and applies to the modules whose line names it or a later version. `snello init` writes `snello` and `version.Current`, through `importer.WriteModFile`, which `init` and `new` both call, so that a module file comes out the same from each.
- **A module written for a later version is refused** where its file is read, before any other line of the file is, since a later release may write a line this compiler does not know and what to say then is that the compiler is too old, as Go reads a `go.mod` it cannot parse again, leniently, for its `go` line; with its file and line and what to do: `snello.mod:1: this module needs snello 0.3.0; this is snello 0.1.0: upgrade the compiler`. The module of the program and every module a `require` line leads to whose package the program imports are checked, so a dependency written for a later release is named by its file; a `require` line no import reaches leads to a file never read for its packages, as an import is what reads them; the selection of versions, section 9, reads the files of the modules the require lines lead to for their own require lines, passing over a module of the program's own whose file does not read, which the import that reaches it reports, and refusing a fetched module's, whose requirements decide the selection. Go 1.21 made the `go` line a requirement (go.dev/issue/57001), where before it compiled on and only noted, after a failed build, that the module required a later Go: Go 1.27 run with `GOTOOLCHAIN=local` on a module asking for 1.99 gives `go: go.mod requires go >= 1.99 (running go 1.27.4; GOTOOLCHAIN=local)`, and with its default it fetches the toolchain asked for, which Snello does not do. Cargo refuses an edition it does not know, and a package whose `rust-version` it does not reach, `rustc 1.98.1 is not supported by the following package: app@0.1.0 requires rustc 1.999`.
- **A module without the line is read as written for the first release, `0.1.0`.** A file without the line was written before the line or by hand, and reading it as the first version means that a new release never changes what it means: the rule both precedents follow, measured here. Go reads a `go.mod` without a `go` line as `go 1.16` (`gover.DefaultGoModVersion`), and a module using a later feature then fails with `requires go1.22 or later (-lang was set to go1.16; check go.mod)`; Cargo reads a manifest without an edition as 2015. A module required by a `require` line, with a module file without the line or with none at all, is read the same way, as Go reads a dependency without a `go` line.
- **The module being built warns when it has no line**, on every command that builds, checks or tests it, on standard error before anything else is written, so a failed build still says it: `warning: /path/snello.mod has no snello line: it is read as snello 0.1.0, the first release; add the line "snello 0.1.0"`. The warning is for the author of the module the command runs in, who can add the line; a module it requires is read without a word, as Cargo warns, on every build, `` warning: Cargo.toml: `package.edition` is unspecified, defaulting to `2015` while the latest is `2024` `` of the package it builds and prints nothing of a path dependency's. A note shown once would need a record kept between runs of which modules were noted, and the compiler keeps none.
- **A program in no module and the standard library are read at the compiler's version**, with no warning: a program with no module file above it has nothing to write a line in, and promises nothing to a later release, as `go run main.go` outside any module reads the toolchain's own version; the standard library is the compiler's and changes with it.
- **What it does today**: nothing but the check, since every rule is the same for every version while `0.1.0` is the only release. **What it is for**: a rule a later release changes, a keyword taken or a default turned, applies to the packages of a module whose line names that release or a later one, the checker told each package's version as Go's type checker is told by its `GoVersion`. Code is checked under the version of the package that declares it, wherever it is used: a generic function's body and a `match T`'s arms, which are checked again for each instance, under its declaring package's version, as code a Rust macro expands keeps the edition of the crate it came from; and a refusal a later rule makes names the version and where it came from, as Go's `(-lang was set to go1.16; check go.mod)` does. Modules of different versions build into one program, as crates of different editions link into one, since the version changes what source means and never how a value is laid out or passed. Before 1.0, nothing is promised between minor versions, so a minor release may change the language for every module; the line is what lets it say which modules were written before the change.
- **Memory safety.** The line changes no rule, so the borrow checker's rules are the same for every module; a rule a later version changes is held to keeping them, as every rule is, and a program mixing modules of two versions is checked as one, each package under its own version's rules, with no runtime and no collector involved.

**Decided 7: a file is for a platform by its name, Go's rule, with `unix` for every Unix.** A package's files for one system or processor are chosen by the last elements of their names, `poll_linux.snello`, `shim_darwin_arm64.c`, as go/build reads them, and a file for every Unix and not Windows by `_unix`, which Go's file names lack, for the program's directory, the module's packages, required modules and the standard library alike, by the platform the program is built for; a file for a platform Snello does not build for is left out as any other platform's is, and a name beginning with a dot or an underscore is no file of the package. No attribute or build line chooses inside a file, Rust's `cfg`, Swift's `#if` and Go's `//go:build` being the alternative set aside, since a reader then evaluates a condition to know what a file holds; the name says it at a listing. The first wording refused a name for a system Snello does not build for, which no other compiler does; it was withdrawn before release for Go's rule, so that a package carries the files of every system.

**Decided 8: a dependency by version is a git tag, locked by the hash of its files, one version a program.** Section 9 has the rules; the choices among the precedents are these. The line names a repository and a SemVer version, which is a tag `vX.Y.Z`, Go's rule, rather than Cargo's free tag or branch, so that a version is always a release and the form is the one Snello's own `snello` line writes. The lock file holds both the commit, which Cargo and the Swift Package Manager record, and a hash of the files, Go's `h1:`, which Go records alone: the commit names a moved tag by what a reader can look up, and the hash holds the files whatever the history does, by SHA-256. The build writes the lock file, as Cargo and the Swift Package Manager do, rather than a command of its own, as Go's `go mod tidy` and `go get` do, since a developer then never meets a build refusing for a lock file the tool could have written; a hash that changed is refused, as Go and the Swift Package Manager refuse it, rather than built from the locked commit, as Cargo does. The highest version required is taken among the compatible ones, those sharing their first number other than zero as Cargo's caret reads SemVer, by Go's minimal version selection, rather than a solver over ranges, as Cargo's and the Swift Package Manager's are, since a solver's answer depends on what the registry holds the day it runs, which is why both need a lock file to build twice alike and Go's selection does not; two majors of one repository are refused rather than built side by side, until a program needs both. The module cache is apart from the build cache, Go's split, so that clearing the one never makes a build offline fail on the other; it heals rather than trusts, a cached copy that changed, or that the lock file does not agree with, fetched again, and its files are left writable, since the hash holds them, where Go makes them read-only and trusts them. The fetch takes the tag by its full reference and converts nothing, so that one commit hashes alike for every user. Memory safety: building only; a fetched module's code is checked as every module's is, with no privilege and no runtime of its own.

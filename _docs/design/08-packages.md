# Packages and modules

Status: implemented. Built: the module file, the three places an import is found, a required module's own file, the cycle message, the refusals of section 4 and the standard library's privileges held back from a package of the program's own, with `snello build FILE` finding the module above the file; a package of several files, through `token.FileSet` and `types.Config.CheckFiles`; and `snello build DIR`, with `check` and `emit` taking a directory the same way, through `importer.LoadProgram` and the backends' `EmitFiles`, with `examples/packaged/` in the run suite of both backends. Revised: no module name, an import names a directory under the root or a required name, `snm_` for a package's symbols (decisions 1 and 3). Section 6, a package's C, with the module file's `link` line: the checker's list of what crosses, `types.checkBinding`; the importer's C files and its refusal of a bound package with no `.c` file; the header `emit/c.Header` writes and the build of a package's C in both backends; `examples/bound/` in the run suite of both. The language version, the module file's `snello` line (decision 6): read and checked against the compiler's in every module reached, by `importer.ParseModFile`; warned of when the module a command builds, checks or tests has none, by the commands; and written by `snello init`, through `importer.WriteModFile`.

A Snello program is one file today, and an import resolves only against the standard library the compiler embeds, so no library can exist outside this repository. This note gives Snello Go's shape for code outside one file: a directory of files is a package, a module file names the directory tree a program's own packages live in, and an import path is found in the standard library, in the module, or through a `require` line that names a directory on disk. No versions of dependencies and no network: what a registry would add is a stage of its own.

## The precedents

- **Go** makes the files of one directory one package, names a module in `go.mod` and resolves an import path under the module path to a directory under the module's; `replace` points a path at a directory. The standard library is found first, and a path whose first element has no dot is reserved for it.
- **Rust** makes a crate the unit, with modules inside it declared in the source and a `Cargo.toml` naming its dependencies, which Cargo fetches and builds. The crate is a bigger unit than a package and the module tree is written in the code, which is more to learn than Go's rule that the directory is the package.
- **Zig** has no package manager in the language at all; a dependency is a path given to the build. Snello follows Go, as everywhere else, and keeps Zig's modesty about what a build needs: a directory.

## 1. A directory is a package

Every `.snello` file in one directory belongs to one package, and the files see each other's top-level declarations, as Go's do. Each file begins with the same package clause; a directory whose files disagree is refused with Go's message, `found packages shapes (area.snello) and shape (shape.snello) in shapes`. A name declared in two files of one package is a redeclaration, reported as one in one file is, with the other file named: `Area redeclared in this block; other declaration at shape.snello:12:6`. Imports are per file, as in Go: a file sees the packages it imports, not the ones its neighbours do.

The package's name is what its package clause says, and the import path's last element is expected to match it, as Go expects; a program may rename the package at the import, `import s "shapes"`, as it may today. A method is declared in the package of its receiver's type, as in Go; a method on a type of another package is refused with Go's message, `cannot define new methods on non-local type shapes.Circle`.

A package of the program's own is checked under the rules a program is checked under today. What the checker allows only to the standard library stays the standard library's: a function without a body, `...ref any` and `any`, `local`, a slice of borrows, and the lowered names of `fmt`, `rc` and `sync`. A package of the program's own gets each with the message a program gets today, `missing function body`, unless it binds C as section 6 says. The checker learns which kind of package it is checking from the Config it is checked under, as Go's compiler learns from its `-std` flag that it is compiling the standard library, where today it reads it from the import path being empty.

## 2. The main package

The main package is the one that declares `func main()`, under any package clause, as today: the examples name theirs after what they show, and `package main` is the name a Go reader expects. The first wording of this rule asked for `package main`, which `snello build` never required, and a slice that required it refused every example. `snello build DIR` builds the main package of a directory, every `.snello` file in it, and names the binary after the directory, as `go build` names it after the directory's last element. `snello build FILE` is unchanged: the one file is the whole main package, as `go run hello.go` compiles the one file named, and a second file beside it is not read. `snello check` and `snello emit` take a file or a directory the same way; `snello lex` and `snello parse` read one file. A build or an emit of a package with no `main` function is refused with `go build`'s words, `function main is undeclared in package shapes`; `snello check` takes any package, as `go vet` does, so a library is checked on its own.

The main package is never imported. An import path that resolves to a directory whose package is `main` is refused as Go refuses it: `import "cmd/tool" is a program, not an importable package`. A package of another name that declares `main` is still importable, and its `main` is an ordinary function there, as it is in Go.

## 3. The module file

A module is a directory tree of packages, marked by a file `snello.mod` at its root. Its first job is to say where the root is; its first directive says which version of the language the module is written for, and the rest is one line per dependency:

```
snello 0.1.0

require regexp ../regexp
```

The file has three directives. `snello VERSION` names the version of the language the module is written for, as decision 6 sets out: a release of the compiler refuses a module written for a later one, and reads a file without the line as written for the first, with a warning. `require NAME DIR` says that the import path `NAME`, and every path under it, is found in the directory `DIR`, relative to the module file's directory or absolute; one line per dependency, the name one element, since the rest of a path names a directory under the dependency, and a name required twice is refused. `link NAME` names a system library the module's packages need, `link m`, one line per library, which section 6 explains; a flag or a path is refused, since the line names what `-l` names and nothing else. A `//` comment runs to the end of its line. Nothing else is in the file: no module name, no versions of dependencies, no `go` directive, no `replace`, since a `require` line already names a directory, which is what Go's `replace` makes of a requirement. A directive the file does not have, or a line that is not one, is refused with its line: `snello.mod:3: unknown directive "exclude"`; Go's `module` and `go` lines are directives the file does not have, refused as every other is, as `go.mod` refuses Cargo's `edition` with `unknown directive: edition`.

The module has no name because an import does not need one (decision 1): a program imports a package by the name of its directory under the root, `import "shapes"`, and a dependency by the name its `require` line gives, `import "regexp"` and `import "regexp/syntax"`. Go's module path, `example.com/app`, repeated in every import, is the one piece of Go's shape Snello leaves out; it exists for a registry that serves modules by their path, which is a stage of its own, and a dependency fetched then will still be imported by the name its line gives, as a Cargo dependency is used by its name whatever its source.

A name that is a standard package's cannot be required, `snello.mod:1: strings is a standard package`, and a directory of the root that holds a package under a standard package's name is refused when the module is read, `the directory strings shadows the standard package strings; rename it`, since the standard library answers an import first and the directory could never be reached.

The module a program belongs to is the one marked by the nearest `snello.mod` in the program's directory or above it, as Go finds `go.mod`. A program with no module file above it, every program under `examples/` today, imports the standard library alone, as it does now. A module file is read by every command that loads a program, and written by two. `snello new DIR` makes a directory that must not exist and starts a module in it, the module file, a program and its test, as `cargo new` does; one that exists is refused, `snello new: hello already exists`, as Cargo refuses it with `destination … already exists`, and its parent must exist, so that `new` makes one directory and leaves a module whole or nothing. `snello init [DIR]` starts a module in the current directory or `DIR`, a directory that exists: it writes `snello.mod` holding the version line of the compiler that runs it, `snello 0.1.0`, and nothing else, and refuses a directory that has one already, with the file's absolute path, as `go mod init` refuses with `go: /path/go.mod already exists` and `cargo init` with `` `cargo init` cannot be run on existing Cargo packages ``; anything else under the file's name, a directory or a link to nothing, is refused as in the way. A module under another module's tree is the nearest file up from a program, as the rest of this section says, so `init` does not look above the directory.

## 4. How an import path is found

A file imports a path, and the importer answers it from three places, in this order, taking the first that has it:

1. **The standard library**, embedded in the compiler. `fmt` is always `fmt`; a module cannot shadow a standard package, and section 3 refuses a directory or a require line that would try.
2. **The module's directories.** A path names the directory at that place under the module's root: `shapes` is `shapes/` and `cycle/a` is `cycle/a/`. The directory must hold a `.snello` file: `no package at shapes/ for import shapes`.
3. **The `require` lines.** A path whose first element is a required name names the directory the line gives, or a directory under it for the rest of the path: with `require regexp ../regexp`, the import `regexp` is the directory `../regexp` and `regexp/syntax` is `../regexp/syntax`. A required directory may have a `snello.mod` of its own, whose `require` lines are followed for its own imports, so a library can depend on a library; it may have none, when it is a directory of packages and nothing more. A required module's own imports are answered within it, its directories and its require lines, and the package is named by the module's id, the require name that first reached the module, and its directory under it: the dependency's `import "util"` is the package `regexp/util`, so that the program's `util` and the dependency's are two packages with two symbol prefixes, and a module a dependency requires is named through both, `regexp/syntax/x` (after a review found the two loaded as one). A module file deeper in either tree is not looked for.

A path that both a directory of the module and a require line answer is refused as ambiguous, `import "twin" is both a directory of the module and under the required twin`. A path none of the three answers is refused at the import, with the places searched: `package other is not in the standard library, in the module's directories or in its require lines`, or, with no module file, `package nosuch is not in the standard library, and no snello.mod above the program marks a module`. An import path is a path as Go defines one: elements separated by `/`, none empty, none `.` or `..`; a relative path is refused, `malformed import path "./shapes": a relative path; name the package by its directory under the module`.

An import cycle is refused with the cycle written out, at the import that closes it: `import cycle: cycle/a imports cycle/b imports cycle/a`. The standard library's own message takes the same form.

## 5. One program, one compilation

A package of the program's own is loaded as the standard library's are today: parsed, checked once into the program's `types.Info`, and compiled with the program by whichever backend runs, into the one C file or the one IR module, each of its top-level names qualified by its import path in the backend's symbol, so the module is linked as the program is and link-time optimization sees it whole. Nothing of this changes for a package of the program's own but the space: a standard package's symbols are `sn_<path>_<Name>` with `/` written as `__` (`07-lowering.md`), the names the runtime defines, and a package of the program's own takes the same form in a space of its own, `snm_<path>_<Name>`, which the runtime never uses, so a package may have any name without meeting the runtime's: `shapes.Area` is `snm_shapes_Area` and `cycle/a.A` is `snm_cycle__a_A` (the first form put both in `sn_` and needed a dot in every module path to keep them apart). A path may carry a dot or a dash no C identifier may, `my-lib`, and each is written as `_`; two paths that would share a prefix this way, `a.b` and `a_b`, are refused by the backends, `import paths a.b and a_b would share one symbol prefix`, since no real program meets it.

A package of several files is several compilation units of one package, so every pass that takes a file and its syntax takes a list of them. A position must then say which file it is in: `token.Pos` is a byte offset in one file today, and gains a base per file through a `token.FileSet`, as `go/token`'s does, so a position anywhere in the program resolves to its file, line and column, and the checker and the backends report an error in a second file with that file's name. The parser fills a file the set made; `parser.ParseFile` keeps its signature for one file on its own.

## 6. A package's C

The standard library reaches the runtime through functions declared without a body, which the runtime defines in C under the derived symbol, and the runtime is compiled with the program. A library outside the compiler that wraps a C library, as Rust's crates do through `extern "C"` blocks and `-sys` crates, needs the same two things: a declaration without a body bound to a C symbol, and C compiled and linked with the program. Both come the way Go has them, with nothing added to the language: no pragma, no `import "C"`, no `extern` block.

**The declaration.** A function without a body in a package of the program's own is a binding to C, as a Go function without a body is implemented elsewhere, and its symbol is the one every function of the package gets, section 5: `cbrt` in the package `mathx` is `snm_mathx_cbrt`, which the C side defines under that name. The symbol is never renamed, so binding a library's own function is a shim of one line in the package's C, `double snm_mathx_cbrt(double x) { return cbrt(x); }`, as `cgo` writes one for every call. The main package keeps the refusal, `missing function body`: a program binds C through a package or not at all, so that the C side of a program is always a directory a reader can find. The other privileges of the standard library stay the compiler's, decision 2: `any`, `...ref any`, `local`, a slice of borrows and the lowered names, each of which exists for one standard package.

**What crosses.** The C form of every Snello value is what `runtime/c/snello.h` defines for the standard library, so the C signature is derived from the Snello one and written nowhere twice. A bound function may take and return: the numbers, `int` and `uint` as `int64_t` and `uint64_t`, the sized integers and `byte` as their C sizes, `f64` and `f32` as `double` and `float`, and `bool`; `ref string` as `sn_string` and `ref []byte` as `sn_slice_u8`, each a view of the bytes, pointer and length, that C reads during the call and must not keep; `mut []byte` as `sn_slice_u8 *`, a buffer C fills within its capacity and whose length it sets, as `bufio`'s `copyBytes` fills one; and a `mut` number or `bool` as a pointer to it, `int64_t *`, the out-parameter by which C reports a count, an error code or a yes. A C library's handle crosses as an `int`, the next paragraph. Anything else is refused at the declaration with the type named, `cannot cross to C: map[string]int, in parameter counts`: a pointer, a struct by value, a slice of anything but bytes, a map, an owned `string` or `[]byte`, an option, a result, a tuple, a closure, a trait value or a type parameter. The list is short so that the ABI is the runtime's own and nothing is marshalled; a library that needs more writes the conversion in Snello around the binding, as a `-sys` crate's user writes it in Rust.

**The handle.** A C library hands back a pointer the program must keep and later close. It crosses as an `int`, the pointer's value, which Snello never reads, and the package wraps it in a struct of its own with a `Drop` method that calls the bound `close`, `func Open(start int) *Tally { return &Tally{handle: open(start)} }`, so a handle dropped is a library closed, and the struct is made and freed by the program as any value is. The first design had C make the struct's block with `sn_alloc` and hand back the owned pointer; a review found that a struct with a `Drop` method carries a flag the compiler sets when the value is made, which the C side cannot know to set, so the drop never ran. Keeping the struct on the Snello side costs nothing and leaves the C author no internal field to fill. What the C side does with its own memory is the library author's responsibility, as it is inside Rust's `unsafe`.

**The C side.** The `.c` and `.h` files in the package's directory are compiled with the program, as `cgo` compiles the C files of a package: the build copies them into the build directory beside the runtime's files, under a directory named by the package's symbol prefix so that two packages' `util.c` do not meet, compiles each with the runtime's flags, the checks' flags in a debug build, and links the objects with the program's and the runtime's. The compiler writes a header for the package into that directory, named after the package, `mathx.snello.h`: it includes `snello.h` and declares the prototype of every bound function, derived from the Snello signatures, and the package's C includes it, so that the C compiler checks each definition against its declaration, as `cgo`'s generated export header lets it; a definition with the wrong types is then a compile error at the C side, not an undefined call. A package may not ship a file of that name, and a package with a `.h` file and no `.c` file is refused as one with none. The package's C includes `snello.h` and its own headers; the runtime's other files are within reach of the include path and are not for it. The LLVM backend already declares a function without a body from its signature and calls it under C's convention, as it calls the runtime; the C backend writes the same prototype into the program's C file, where today it relies on `snello.h` for the standard library's.

**A system library.** `link m` in the module file, the module's own or a required module's, is `-lm` at the link of every program that imports a package of the module: a library the system's linker finds, as Go's `#cgo LDFLAGS: -lm` names one. No search path and no other flag crosses the module file in this design; a library installed elsewhere is a decision for when one is needed, with Go's `pkg-config` directive as the precedent. The compiler never runs a build script.

**What the C side must promise.** It keeps no view past the call, since the bytes belong to the caller; it calls nothing of the program back, since no Snello function has a C symbol a library may rely on and the runtime's state is the worker's; and a bound call blocks the worker thread it runs on until it returns, as a file read does today, so a library that waits on a device is a library that holds a worker. These are written in chapter 15, the book's chapter on binding C, and they are the whole of the contract: the compiler checks the types, and the author keeps the rest.

**The pieces.** The checker allows a missing body in a library package and checks each parameter and result against the list, with the message above. The importer records a package's C files beside its Snello files, and the module file's `link` lines. Both backends' builds take the C files and the libraries, write the package's header, and compile and link them. `examples/bound/` is the proof in the run suite of both backends: a package with its own `.c` and a handle with `Drop`, which the program sees given back; and `mathx`, binding `cbrt` through `link m` in a shim of one line.

## 7. What is not here

- **Dependencies' versions, a registry and fetching.** A dependency is a directory; where it came from is not the compiler's business yet. Go's `go.sum`, Cargo's lock file and the resolution of versions are a stage of their own, after `regexp` has shown what a library outside the compiler needs.
- **Vendoring and build tags.** Not decided. Test files and `snello test` are `09-testing.md`'s.
- **Nested modules and workspaces.** A `snello.mod` under another's tree is not looked for; the nearest file up from the program is the module, and the rest are ignored.

## Decisions

**Decided 1: the directory is the package, and the module file is Go's `go.mod` without versions.** The alternative, a package declared in the source as Rust's `mod` tree is, was set aside because a Go developer must read a Snello program without a glossary, and Go's rule needs none: the files beside you are your package. The module file keeps Go's two words, `module` and `require`, and no third, so that a reader of `go.mod` reads `snello.mod` at sight (decision 4 adds `link`, for what Go says in a comment; the revision below drops `module`); `require` naming a directory rather than a version is the one difference, and it is Go's `replace` under the name a reader meets first. Revised so that there is one way to import and no mistake of Go's: the module file has no `module` line and the module no name, an import names a directory under the root or a required name, and `require` names a dependency rather than a path, as a Cargo dependency is named; Go's module path in every import, its dot rule that holds for a fetched module and not a local one, and its `/v2` suffix are what is left out.

**Decided 2: no privilege for a package outside the compiler.** A package of the program's own cannot declare a function without a body or write `...ref any`, beyond what section 6 allows a package that binds C; the standard library keeps its privileges, and a library outside the compiler is built on the core as it is.

**Decided 3 (withdrawn): a dot in the module path's first element.** The rule kept a module path out of the standard library's names and a module's symbols out of the runtime's. With no module path there is nothing to spell: a directory or a require line under a standard package's name is refused outright, and a package of the program's own has a symbol space of its own, `snm_`, so the runtime's names are never met.

**Decided 4: C through a package, with the runtime's ABI and one more word in the module file.** A package of the program's own binds C as the standard library does, a function without a body under the derived symbol with the C types `snello.h` already gives Snello's values, rather than through a pragma or an `extern` block, since the language gains nothing and the standard library has shown the shape works. The types that cross are the few the runtime passes already, so nothing is marshalled, a handle is an int the package wraps, and a library that needs more converts in Snello. The module file gains `link NAME` for a system library, the one word beside `require`: Go names a library in a `#cgo` comment, Rust in an attribute or a build script and Zig in its build program, and Snello has none of the three, so the module file, which already says where a dependency is, is the smallest place that can say what it links.

**Decided 5: a module is its directory, whatever route reaches it.** A module has no name, decision 1, so the importer had named a required module's packages by the route of require names that reached them, `b/d/util` for the `d` that `b` requires. A test of a diamond, two dependencies requiring one third, showed the cost: the third was loaded once per route, its one type became two, and a value of it could not pass from one dependency to the other, `cannot use a value of type util.Thing as util.Thing`. Every real dependency graph has diamonds, so the identity of a module cannot be its route. It is its directory: the importer keys the modules it has reached by the directory's one spelling, absolute with symbolic links resolved, and the first require line to reach a directory gives the module its id, the require's name, under which every package of the module is named from then on, `d/util`, whichever require line and whichever name reaches it later. Two different modules reached under one name are told apart by a numeral after a `~`, `d~2`, a character an import path may not hold, so the id names no directory and no require; the backends' check of symbol prefixes still refuses the one collision the mapping to a C symbol could make. A module's packages carry that module's `link` lines, not the importing module's, which the route-named importer had wrong. When a registry comes, section 7, the identity becomes the name and version it is published under, and this id becomes that name; the imports inside a module do not change.

**Decided 6: the module names the version of Snello it is written for.** A module file says which release of Snello its packages are written for, `snello 0.1.0`, so that a later release can change a rule for the modules that name it and keep every older module compiling as it was written: what Go's `go 1.27.4` line does for a module and Rust's `edition` for a crate. The line costs nothing before 1.0 and could only be added as a breaking change after it, which is why it comes now.

- **The line is a Semantic Versioning 2.0 version**, the scheme Snello's releases are numbered by: `snello MAJOR.MINOR.PATCH`, with a pre-release after a hyphen and build metadata after a plus as SemVer allows, `snello 0.2.0-rc.1`, and each number in decimal with no leading zero (semver.org, items 2, 9 and 10). It names the oldest release that compiles the module, as Go's line has since Go 1.21: `go mod init` writes the full version of the Go that runs it, `go 1.27.4`, and Go 1.27.4 refuses a module asking for 1.27.5. One way to write each version, so a spelling SemVer does not have is refused with the form and an example, `snello.mod:1: malformed version "0.1": a version is MAJOR.MINOR.PATCH, snello 0.1.0`, which covers `0.1`, `v0.1.0`, `01.2.0` and `0.1.0.0`; a line of no version or of two words after `snello`, with `snello needs one version, snello 0.1.0`; a second `snello` line, as Go refuses a repeated `go` line. The line is the first directive of every module file of the repository, where a reader looks, and the file does not require it there, as `go.mod` does not.
- **Two versions compare by SemVer's precedence** (item 11): major, minor and patch numerically; a pre-release before the release it precedes, `0.2.0-rc.1` before `0.2.0`, and two pre-releases identifier by identifier, numbers numerically and below words, words in ASCII order, a shorter list first when the longer begins with it; build metadata never. A number compares by its count of digits and then digit by digit, which is numeric order since no number has a leading zero, so a version of any length compares without being read into an integer that could overflow.
- **The compiler's version** is the SemVer version of the release being built, `0.1.0` today: a constant of the package `compiler/version`, `version.Current`, set at the start of each release's work, as Go's `internal/goversion.Version` is raised at the start of every release cycle. `snello version` prints it with what else the binary says of itself, `snello 0.1.0 (8477985) stable darwin/arm64`: the commit, read from the build information Go records, marked `-dirty` when the tree had changes, as `git describe --dirty` marks it, and left out when the build recorded none, as a binary built outside a checkout or with stamping off has none; the channel, which a release build stamps in with the linker's `-X`, and which a build from source, stamped with none, names `devel`, keeping the version, as a development build of Go says `devel go1.28-…` and a nightly Rust `1.94.0-nightly`; and the system and processor. The version a module is checked against is `version.Current` in every build. The language changes only in a minor release, a patch release fixing the compiler, so a rule tied to a version starts at a minor release, `0.3.0`, and applies to the modules whose line names it or a later version. `snello init` writes `snello` and `version.Current`, through `importer.WriteModFile`, which `init` and `new` both call, so that a module file comes out the same from each.
- **A module written for a later version is refused** where its file is read, before any other line of the file is, since a later release may write a line this compiler does not know and what to say then is that the compiler is too old, as Go reads a `go.mod` it cannot parse again, leniently, for its `go` line; with its file and line and what to do: `snello.mod:1: this module needs snello 0.3.0; this is snello 0.1.0: upgrade the compiler`. The module of the program and every module a `require` line leads to whose package the program imports are checked, so a dependency written for a later release is named by its file; a `require` line no import reaches leads to a file never read, as an import is what reads it. Go 1.21 made the `go` line a requirement (go.dev/issue/57001), where before it compiled on and only noted, after a failed build, that the module required a later Go: Go 1.27 run with `GOTOOLCHAIN=local` on a module asking for 1.99 gives `go: go.mod requires go >= 1.99 (running go 1.27.4; GOTOOLCHAIN=local)`, and with its default it fetches the toolchain asked for, which Snello does not do. Cargo refuses an edition it does not know, and a package whose `rust-version` it does not reach, `rustc 1.98.1 is not supported by the following package: app@0.1.0 requires rustc 1.999`.
- **A module without the line is read as written for the first release, `0.1.0`.** A file without the line was written before the line or by hand, and reading it as the first version means that a new release never changes what it means: the rule both precedents follow, measured here. Go reads a `go.mod` without a `go` line as `go 1.16` (`gover.DefaultGoModVersion`), and a module using a later feature then fails with `requires go1.22 or later (-lang was set to go1.16; check go.mod)`; Cargo reads a manifest without an edition as 2015. A module required by a `require` line, with a module file without the line or with none at all, is read the same way, as Go reads a dependency without a `go` line.
- **The module being built warns when it has no line**, on every command that builds, checks or tests it, on standard error before anything else is written, so a failed build still says it: `warning: /path/snello.mod has no snello line: it is read as snello 0.1.0, the first release; add the line "snello 0.1.0"`. The warning is for the author of the module the command runs in, who can add the line; a module it requires is read without a word, as Cargo warns, on every build, `` warning: Cargo.toml: `package.edition` is unspecified, defaulting to `2015` while the latest is `2024` `` of the package it builds and prints nothing of a path dependency's. A note shown once would need a record kept between runs of which modules were noted, and the compiler keeps none.
- **A program in no module and the standard library are read at the compiler's version**, with no warning: a program with no module file above it has nothing to write a line in, and promises nothing to a later release, as `go run main.go` outside any module reads the toolchain's own version; the standard library is the compiler's and changes with it.
- **What it does today**: nothing but the check, since every rule is the same for every version while `0.1.0` is the only release. **What it is for**: a rule a later release changes, a keyword taken or a default turned, applies to the packages of a module whose line names that release or a later one, the checker told each package's version as Go's type checker is told by its `GoVersion`. Code is checked under the version of the package that declares it, wherever it is used: a generic function's body and a `match T`'s arms, which are checked again for each instance, under its declaring package's version, as code a Rust macro expands keeps the edition of the crate it came from; and a refusal a later rule makes names the version and where it came from, as Go's `(-lang was set to go1.16; check go.mod)` does. Modules of different versions build into one program, as crates of different editions link into one, since the version changes what source means and never how a value is laid out or passed. Before 1.0, nothing is promised between minor versions, so a minor release may change the language for every module; the line is what lets it say which modules were written before the change.
- **Memory safety.** The line changes no rule, so the borrow checker's rules are the same for every module; a rule a later version changes is held to keeping them, as every rule is, and a program mixing modules of two versions is checked as one, each package under its own version's rules, with no runtime and no collector involved.

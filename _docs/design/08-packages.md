# Packages and modules

Status: designed 2026-11-05 for task 5.3 of `../specs/stage-5-libraries-performance.md`. Built the same day: the module file, the three places an import is found, a required module's own file, the cycle message, the refusals of section 4 and the standard library's privileges held back from a package of the program's own, with `snello build FILE` finding the module above the file. Built 2026-11-06: a package of several files, through `token.FileSet` and `types.Config.CheckFiles`; and `snello build DIR`, with `check` and `emit` taking a directory the same way, through `importer.LoadProgram` and the backends' `EmitFiles`, with `examples/run/packaged/` in the run suite of both backends. Revised 2026-11-06: no module name, an import names a directory under the root or a required name, `snm_` for a package's symbols (decisions 1 and 3). Section 6, a package's C, designed 2026-11-06 for task 5.5 and built the same day, the module file's `link` line on 2026-11-07: the checker's list of what crosses, `types.checkBinding`; the importer's C files and its refusal of a bound package with no `.c` file; the header `emit/c.Header` writes and the build of a package's C in both backends; `examples/run/bound/` in the run suite of both.

A Snello program is one file today, and an import resolves only against the standard library the compiler embeds, so no library can exist outside this repository. This note gives Snello Go's shape for code outside one file: a directory of files is a package, a module file names the directory tree a program's own packages live in, and an import path is found in the standard library, in the module, or through a `require` line that names a directory on disk. No versions and no network: what a registry would add is a stage of its own.

## The precedents

- **Go** makes the files of one directory one package, names a module in `go.mod` and resolves an import path under the module path to a directory under the module's; `replace` points a path at a directory. The standard library is found first, and a path whose first element has no dot is reserved for it.
- **Rust** makes a crate the unit, with modules inside it declared in the source and a `Cargo.toml` naming its dependencies, which Cargo fetches and builds. The crate is a bigger unit than a package and the module tree is written in the code, which is more to learn than Go's rule that the directory is the package.
- **Zig** has no package manager in the language at all; a dependency is a path given to the build. Snello follows Go, as everywhere else, and keeps Zig's modesty about what a build needs: a directory.

## 1. A directory is a package

Every `.snello` file in one directory belongs to one package, and the files see each other's top-level declarations, as Go's do. Each file begins with the same package clause; a directory whose files disagree is refused with Go's message, `found packages shapes (area.snello) and shape (shape.snello) in shapes`. A name declared in two files of one package is a redeclaration, reported as one in one file is, with the other file named: `Area redeclared in this block; other declaration at shape.snello:12:6`. Imports are per file, as in Go: a file sees the packages it imports, not the ones its neighbours do.

The package's name is what its package clause says, and the import path's last element is expected to match it, as Go expects; a program may rename the package at the import, `import s "shapes"`, as it may today. A method is declared in the package of its receiver's type, as in Go; a method on a type of another package is refused with Go's message, `cannot define new methods on non-local type shapes.Circle`.

A package of the program's own is checked under the rules a program is checked under today. What the checker allows only to the standard library stays the standard library's: a function without a body, `...ref any` and `any`, `local`, a slice of borrows, and the lowered names of `fmt`, `rc` and `sync`. A package of the program's own gets each with the message a program gets today, `missing function body`, until task 5.5 decides what crosses to C. The checker learns which kind of package it is checking from the Config it is checked under, as Go's compiler learns from its `-std` flag that it is compiling the standard library, where today it reads it from the import path being empty.

## 2. The main package

The main package is the one that declares `func main()`, under any package clause, as today: the examples name theirs after what they show, and `package main` is the name a Go reader expects. The first wording of this rule asked for `package main`, which `snello build` never required, and a slice that required it refused every example; corrected 2026-11-06. `snello build DIR` builds the main package of a directory, every `.snello` file in it, and names the binary after the directory, as `go build` names it after the directory's last element. `snello build FILE` is unchanged: the one file is the whole main package, as `go run hello.go` compiles the one file named, and a second file beside it is not read. `snello check` and `snello emit` take a file or a directory the same way; `snello lex` and `snello parse` read one file. A build or an emit of a package with no `main` function is refused with `go build`'s words, `function main is undeclared in package shapes`; `snello check` takes any package, as `go vet` does, so a library is checked on its own (2026-11-06).

The main package is never imported. An import path that resolves to a directory whose package is `main` is refused as Go refuses it: `import "cmd/tool" is a program, not an importable package`. A package of another name that declares `main` is still importable, and its `main` is an ordinary function there, as it is in Go.

## 3. The module file

A module is a directory tree of packages, marked by a file `snello.mod` at its root. The file may be empty: its first job is to say where the root is. What else it holds is one line per dependency:

```
require regexp ../regexp
```

The file has two directives. `require NAME DIR` says that the import path `NAME`, and every path under it, is found in the directory `DIR`, relative to the module file's directory or absolute; one line per dependency, the name one element, since the rest of a path names a directory under the dependency, and a name required twice is refused. `link NAME` names a system library the module's packages need, `link m`, one line per library, which section 6 explains (built 2026-11-07); a flag or a path is refused, since the line names what `-l` names and nothing else. A `//` comment runs to the end of its line. Nothing else is in the file: no module name, no versions, no `go` directive, no `replace`, since a `require` line already names a directory, which is what Go's `replace` makes of a requirement. A directive the file does not have, or a line that is not one, is refused with its line: `snello.mod:3: unknown directive "exclude"`; Go's `module` line is refused with what takes its place, `a module has no name: the file marks the root, and an import names a directory under it`.

The module has no name because an import does not need one (revised 2026-11-06, decision 1): a program imports a package by the name of its directory under the root, `import "shapes"`, and a dependency by the name its `require` line gives, `import "regexp"` and `import "regexp/syntax"`. Go's module path, `example.com/app`, repeated in every import, is the one piece of Go's shape Snello leaves out; it exists for a registry that serves modules by their path, which is a stage of its own, and a dependency fetched then will still be imported by the name its line gives, as a Cargo dependency is used by its name whatever its source.

A name that is a standard package's cannot be required, `snello.mod:1: strings is a standard package`, and a directory of the root that holds a package under a standard package's name is refused when the module is read, `the directory strings shadows the standard package strings; rename it`, since the standard library answers an import first and the directory could never be reached.

The module a program belongs to is the one marked by the nearest `snello.mod` in the program's directory or above it, as Go finds `go.mod`. A program with no module file above it, every program under `examples/` today, imports the standard library alone, as it does now. A module file is only read; `snello` never writes one.

## 4. How an import path is found

A file imports a path, and the importer answers it from three places, in this order, taking the first that has it:

1. **The standard library**, embedded in the compiler. `fmt` is always `fmt`; a module cannot shadow a standard package, and section 3 refuses a directory or a require line that would try.
2. **The module's directories.** A path names the directory at that place under the module's root: `shapes` is `shapes/` and `cycle/a` is `cycle/a/`. The directory must hold a `.snello` file: `no package at shapes/ for import shapes`.
3. **The `require` lines.** A path whose first element is a required name names the directory the line gives, or a directory under it for the rest of the path: with `require regexp ../regexp`, the import `regexp` is the directory `../regexp` and `regexp/syntax` is `../regexp/syntax`. A required directory may have a `snello.mod` of its own, whose `require` lines are followed for its own imports, so a library can depend on a library; it may have none, when it is a directory of packages and nothing more. A required module's own imports are answered within it, its directories and its require lines, and the package is named by the require that reached it: the dependency's `import "util"` is the package `regexp/util`, so that the program's `util` and the dependency's are two packages with two symbol prefixes, and a module a dependency requires is named through both, `regexp/syntax/x` (2026-11-07, after a review found the two loaded as one). A module file deeper in either tree is not looked for.

A path that both a directory of the module and a require line answer is refused as ambiguous, `import "twin" is both a directory of the module and under the required twin`. A path none of the three answers is refused at the import, with the places searched: `package other is not in the standard library, in the module's directories or in its require lines`, or, with no module file, `package nosuch is not in the standard library, and no snello.mod above the program marks a module`. An import path is a path as Go defines one: elements separated by `/`, none empty, none `.` or `..`; a relative path is refused, `malformed import path "./shapes": a relative path; name the package by its directory under the module`.

An import cycle is refused with the cycle written out, at the import that closes it: `import cycle: cycle/a imports cycle/b imports cycle/a`. The standard library's own message takes the same form.

## 5. One program, one compilation

A package of the program's own is loaded as the standard library's are today: parsed, checked once into the program's `types.Info`, and compiled with the program by whichever backend runs, into the one C file or the one IR module, each of its top-level names qualified by its import path in the backend's symbol, so the module is linked as the program is and link-time optimization sees it whole. Nothing of this changes for a package of the program's own but the space: a standard package's symbols are `sn_<path>_<Name>` with `/` written as `__` (`07-lowering.md`), the names the runtime defines, and a package of the program's own takes the same form in a space of its own, `snm_<path>_<Name>`, which the runtime never uses, so a package may have any name without meeting the runtime's: `shapes.Area` is `snm_shapes_Area` and `cycle/a.A` is `snm_cycle__a_A` (revised 2026-11-06; the first form put both in `sn_` and needed a dot in every module path to keep them apart). A path may carry a dot or a dash no C identifier may, `my-lib`, and each is written as `_`; two paths that would share a prefix this way, `a.b` and `a_b`, are refused by the backends, `import paths a.b and a_b would share one symbol prefix`, since no real program meets it.

A package of several files is several compilation units of one package, so every pass that takes a file and its syntax takes a list of them. A position must then say which file it is in: `token.Pos` is a byte offset in one file today, and gains a base per file through a `token.FileSet`, as `go/token`'s does, so a position anywhere in the program resolves to its file, line and column, and the checker and the backends report an error in a second file with that file's name. The parser fills a file the set made; `parser.ParseFile` keeps its signature for one file on its own.

## 6. A package's C

Designed 2026-11-06 for task 5.5. The standard library reaches the runtime through functions declared without a body, which the runtime defines in C under the derived symbol, and the runtime is compiled with the program. A library outside the compiler that wraps a C library, as Rust's crates do through `extern "C"` blocks and `-sys` crates, needs the same two things: a declaration without a body bound to a C symbol, and C compiled and linked with the program. Both come the way Go has them, with nothing added to the language: no pragma, no `import "C"`, no `extern` block.

**The declaration.** A function without a body in a package of the program's own is a binding to C, as a Go function without a body is implemented elsewhere, and its symbol is the one every function of the package gets, section 5: `cbrt` in the package `mathx` is `snm_mathx_cbrt`, which the C side defines under that name. The symbol is never renamed, so binding a library's own function is a shim of one line in the package's C, `double snm_mathx_cbrt(double x) { return cbrt(x); }`, as `cgo` writes one for every call. The main package keeps the refusal, `missing function body`: a program binds C through a package or not at all, so that the C side of a program is always a directory a reader can find. The other privileges of the standard library stay the compiler's, decision 2: `any`, `...ref any`, `local`, a slice of borrows and the lowered names, each of which exists for one standard package.

**What crosses.** The C form of every Snello value is what `runtime/c/snello.h` defines for the standard library, so the C signature is derived from the Snello one and written nowhere twice. A bound function may take and return: the numbers, `int` and `uint` as `int64_t` and `uint64_t`, the sized integers and `byte` as their C sizes, `f64` and `f32` as `double` and `float`, and `bool`; `ref string` as `sn_string` and `ref []byte` as `sn_slice_u8`, each a view of the bytes, pointer and length, that C reads during the call and must not keep; `mut []byte` as `sn_slice_u8 *`, a buffer C fills within its capacity and whose length it sets, as `bufio`'s `copyBytes` fills one; and a `mut` number or `bool` as a pointer to it, `int64_t *`, the out-parameter by which C reports a count, an error code or a yes. A C library's handle crosses as an `int`, the next paragraph. Anything else is refused at the declaration with the type named, `cannot cross to C: map[string]int, in parameter counts`: a pointer, a struct by value, a slice of anything but bytes, a map, an owned `string` or `[]byte`, an option, a result, a tuple, a closure, a trait value or a type parameter. The list is short so that the ABI is the runtime's own and nothing is marshalled; a library that needs more writes the conversion in Snello around the binding, as a `-sys` crate's user writes it in Rust.

**The handle.** A C library hands back a pointer the program must keep and later close. It crosses as an `int`, the pointer's value, which Snello never reads, and the package wraps it in a struct of its own with a `Drop` method that calls the bound `close`, `func Open(start int) *Tally { return &Tally{handle: open(start)} }`, so a handle dropped is a library closed, and the struct is made and freed by the program as any value is. The first design had C make the struct's block with `sn_alloc` and hand back the owned pointer; a review found that a struct with a `Drop` method carries a flag the compiler sets when the value is made, which the C side cannot know to set, so the drop never ran (2026-11-07). Keeping the struct on the Snello side costs nothing and leaves the C author no internal field to fill. What the C side does with its own memory is the library author's responsibility, as it is inside Rust's `unsafe`.

**The C side.** The `.c` and `.h` files in the package's directory are compiled with the program, as `cgo` compiles the C files of a package: the build copies them into the build directory beside the runtime's files, under a directory named by the package's symbol prefix so that two packages' `util.c` do not meet, compiles each with the runtime's flags, the checks' flags in a debug build, and links the objects with the program's and the runtime's. The compiler writes a header for the package into that directory, named after the package, `mathx.snello.h`: it includes `snello.h` and declares the prototype of every bound function, derived from the Snello signatures, and the package's C includes it, so that the C compiler checks each definition against its declaration, as `cgo`'s generated export header lets it; a definition with the wrong types is then a compile error at the C side, not an undefined call. A package may not ship a file of that name, and a package with a `.h` file and no `.c` file is refused as one with none. The package's C includes `snello.h` and its own headers; the runtime's other files are within reach of the include path and are not for it. The LLVM backend already declares a function without a body from its signature and calls it under C's convention, as it calls the runtime; the C backend writes the same prototype into the program's C file, where today it relies on `snello.h` for the standard library's.

**A system library.** `link m` in the module file, the module's own or a required module's, is `-lm` at the link of every program that imports a package of the module: a library the system's linker finds, as Go's `#cgo LDFLAGS: -lm` names one. No search path and no other flag crosses the module file in this design; a library installed elsewhere is a decision for when one is needed, with Go's `pkg-config` directive as the precedent. The compiler never runs a build script.

**What the C side must promise.** It keeps no view past the call, since the bytes belong to the caller; it calls nothing of the program back, since no Snello function has a C symbol a library may rely on and the runtime's state is the worker's; and a bound call blocks the worker thread it runs on until it returns, as a file read does today, so a library that waits on a device is a library that holds a worker. These are written in chapter 15, the book's chapter on binding C, and they are the whole of the contract: the compiler checks the types, and the author keeps the rest.

**The pieces.** The checker allows a missing body in a library package and checks each parameter and result against the list, with the message above. The importer records a package's C files beside its Snello files, and the module file's `link` lines. Both backends' builds take the C files and the libraries, write the package's header, and compile and link them. `examples/run/bound/` is the proof in the run suite of both backends: a package with its own `.c` and a handle with `Drop`, which the program sees given back; and `mathx`, binding `cbrt` through `link m` in a shim of one line.

## 7. What is not here

- **Versions, a registry and fetching.** A dependency is a directory; where it came from is not the compiler's business yet. Go's `go.sum`, Cargo's lock file and the resolution of versions are a stage of their own, after `regexp` has shown what a library outside the compiler needs.
- **Vendoring, build tags, test files.** `_test.snello` and a `snello test` are not decided; `lib/regexp`'s tests in task 5.6 will say what they need.
- **Nested modules and workspaces.** A `snello.mod` under another's tree is not looked for; the nearest file up from the program is the module, and the rest are ignored.

## Decisions

**Decided 1 (2026-11-05): the directory is the package, and the module file is Go's `go.mod` without versions.** The alternative, a package declared in the source as Rust's `mod` tree is, was set aside because a Go developer must read a Snello program without a glossary, and Go's rule needs none: the files beside you are your package. The module file keeps Go's two words, `module` and `require`, and no third, so that a reader of `go.mod` reads `snello.mod` at sight (decision 4 adds `link`, for what Go says in a comment; the revision below drops `module`); `require` naming a directory rather than a version is the one difference, and it is Go's `replace` under the name a reader meets first. Revised 2026-11-06, at the owner's word that there be one way to import and no mistake of Go's: the module file has no `module` line and the module no name, an import names a directory under the root or a required name, and `require` names a dependency rather than a path, as a Cargo dependency is named; Go's module path in every import, its dot rule that holds for a fetched module and not a local one, and its `/v2` suffix are what is left out.

**Decided 2 (2026-11-05): no privilege for a package outside the compiler.** A package of the program's own cannot declare a function without a body or write `...ref any`, since what either means at the boundary to C is task 5.5's question; refusing them now with the program's messages keeps the standard library the only package with a C side, which is what task 5.6 must prove enough.

**Decided 3 (2026-11-05, withdrawn 2026-11-06): a dot in the module path's first element.** The rule kept a module path out of the standard library's names and a module's symbols out of the runtime's. With no module path there is nothing to spell: a directory or a require line under a standard package's name is refused outright, and a package of the program's own has a symbol space of its own, `snm_`, so the runtime's names are never met.

**Decided 4 (2026-11-06): C through a package, with the runtime's ABI and one more word in the module file.** A package of the program's own binds C as the standard library does, a function without a body under the derived symbol with the C types `snello.h` already gives Snello's values, rather than through a pragma or an `extern` block, since the language gains nothing and the standard library has shown the shape works. The types that cross are the few the runtime passes already, so nothing is marshalled, a handle is an int the package wraps, and a library that needs more converts in Snello. The module file gains `link NAME` for a system library, the one word beside `require`: Go names a library in a `#cgo` comment, Rust in an attribute or a build script and Zig in its build program, and Snello has none of the three, so the module file, which already says where a dependency is, is the smallest place that can say what it links.

# Platforms

Status: designed, and partly built. Built: the compiler and its test packages build for Windows; the runtime compiles for `windows/amd64` and `windows/arm64`, through `system.h`, `os_windows.c` and the Windows parts of `sched.c`, `net.c`, `snello.c`, `alloc.c`, `time.c`, `rand.c`, `map.c`, `lookup.c` and `trace.c`, and on Linux and macOS each call of `system.h` is inlined to the call the runtime made before, so the code of those calls is what it was; from Linux and macOS both backends build a program for either Windows target, linked by `lld-link`, with its panic's trace table, and the LLVM backend passes values as each platform's convention has them; `path/filepath` and `os` read Windows' paths, and a file named `_unix` is for every Unix (`08-packages.md`); the stack analysis reads a PE binary and bounds a Windows task as it bounds one elsewhere, with the stacks of Windows' system libraries and C runtime, measured on both processors, in a table of their own, which bounds the tasks of `windows/amd64`; `windows/arm64`'s tier-2 job does not block a change, so a figure that grew there would fail no merge, and a task of it that calls into them stays on a guarded stack until the job does. The two Windows CI jobs of section 4 run and pass, `go test ./...`, `make test` and `make check` on both processors, with the tests of what is not built skipped, and an interrupt reaches a Windows program as it reaches one elsewhere, through `os/signal` and the cancel of a program that asked for none; the distributions' job runs a developer's first five minutes on Debian 13, Ubuntu 24.04, Fedora and Arch, in images of their own on both Linux runners, Arch on the x86-64 one alone; Alpine's image of section 2 is not built. `macos-15-intel` runs the suite too, its job not blocking a change until it passes: one of the runtime's probes runs past its deadline there, `TestMonitorMovesStaleSlot`, whose woken task does not run within the 50 ms the probe allows; `TestQueueLockUnderContention`, whose holder yields while it holds the lock, crawled there until a yield on macOS became a sleep of a microsecond (`06-tasks-and-channels.md`). Not yet built: the bounds of a `darwin/amd64` task that calls the C library, which stays on a guarded stack, since otool's listing of x86-64 loses its place at the zero bytes the linker pads between functions (`07-lowering.md`); the frames of a waiting task in `cdb`'s `!tasks`, and `!tasks` at all on arm64, whose SDK debugger has no provider of scripts (section Debugging); and a profiler on Windows.

Before this note, Snello built and ran on Linux and macOS, on amd64 and arm64, and was tested on one of each: Debian 13 in the development image on both processors, and GitHub's macOS arm64 runner. It said nowhere which Linux and which macOS it supported, tested none of the others, and did not build for Windows. This note decides the platforms Snello supports, what each is promised, the oldest version of each system it runs on, and how the runtime and the compiler are ported to Windows.

## 1. Tiers

A platform's tier says what is promised of it, as Rust's target tier policy words it:

- **Tier 1: built and tested on every change.** `go test ./...`, `make test` and `make check` pass on it in CI before a change merges; a failure there blocks the change.
- **Tier 2: built on every change.** The compiler builds programs for it and the build is checked on every change; its tests run where a runner exists, and a failure is fixed before the next release, not before the merge.
- **Tier 3: left to whoever needs it.** The code is there and nobody is promised it works.

| Platform | Tier | Where CI runs it |
|---|---|---|
| `linux/amd64`, glibc | 1 | the suite on Debian 13, the development image, on GitHub's x86-64 Linux runner; a developer's first five minutes on Debian 13, Ubuntu 24.04, Fedora and Arch, each in an image of its own there |
| `linux/arm64`, glibc | 1 | the same on GitHub's arm64 Linux runner, without Arch, which publishes no arm64 image |
| `darwin/arm64` | 1 | GitHub's macOS arm64 runner |
| `darwin/amd64` | 1 | GitHub's Intel macOS runner, `macos-15-intel`, while GitHub offers one; tier 2, built from the arm64 runner, once it does not |
| `windows/amd64` | 1 | GitHub's Windows x86-64 runner |
| `windows/arm64` | 2 | GitHub's `windows-11-arm` runner, its tests run and not blocking |
| `linux/*` with musl | decided by section 2 | Alpine |

The table is the tier each platform holds once its CI job runs and passes; until then a platform is held at the tier its job has reached, and the Status line above says which jobs exist. A platform moves up a tier when its runner passes the tier's checks for a release cycle, and down when it cannot be run, as `darwin/amd64` will when GitHub retires its last Intel Mac, which its retirement of `macos-13` shows will come.

## 2. The oldest version of each system

A release names the oldest version of each system it runs on, and CI tests the oldest the runners and their images offer, as Go names the oldest kernel and macOS its ports run on, and Rust the oldest kernel and glibc of each tier-1 target.

- **Linux: kernel 5.4 and glibc 2.29.** The floor is the newest of the calls the runtime makes: a child's pidfd, `pidfd_open` of 5.3 and `waitid` on one of 5.4, and `posix_spawn_file_actions_addchdir_np` of glibc 2.29, which a child started in a directory of its own needs (`05-standard-library.md`, section 6); the others are older, `getentropy` of glibc 2.25 over the kernel's `getrandom` of 3.17, `epoll_create1` and `eventfd` with their flags of 2.6.27, `accept4` of 2.6.28, the futex wait of 2.6. Go's floor is kernel 3.2 and Rust's kernel 3.2 with glibc 2.17, and Go uses a pidfd where the kernel has one, generally 5.4, falling back to a thread that waits; Snello's floor is the kernel a pidfd needs, since a wait through the poller is the one way it waits, and a program running on an older kernel, Red Hat Enterprise Linux 8 among them, is not a case worth a second path. The oldest C library CI tests is Debian 13's and Ubuntu 24.04's, glibc 2.39, in the images of section 4; the floor is held by the calls the runtime makes, not by a runner.
- **musl.** The runtime has never been built against musl: its thread, scheduler and stack calls are glibc's (`sched_getaffinity`, `MAP_NORESERVE` stacks, the thread attributes it sets). Alpine is added to CI in its own image; if the runtime builds and the suite passes, musl is tier 2, built and tested and not blocking, since its allocator and its thread stacks of 128 KB change the measurements the benchmarks hold; if it does not, the note records what fails and musl is tier 3 until a change makes it pass.
- **macOS: 14.4.** The runtime's waits on an address, `os_sync_wait_on_address`, came in 14.4, and every macOS build names it as its deployment target (`07-lowering.md`, building for another platform). Go's floor is macOS 12, and Rust's 10.12 on Intel and 11 on Apple's processors; Snello's is the version whose primitive its locks and parks are built on, as Go's was raised to the version its runtime's calls need.
- **Windows: Windows 10 and Windows Server 2016**, Go's and Rust's floor: the waits on an address (`WaitOnAddress`) came in Windows 8, the batch dequeue of a completion port (`GetQueuedCompletionStatusEx`) in Vista, and the system's random source Rust and Go use, `ProcessPrng`, in Windows 10. The keeper's high-resolution timer came in Windows 10 1803; on an older system a plain waitable timer takes its place, as in Go, and a deadline then comes on the system's tick.

## 3. The Windows port

Windows is a port of the runtime's system half and of the compiler's link, trace and stack analysis; nothing of the language, the checker or the backends' lowering changes. It targets clang's `*-pc-windows-msvc` triples, as Rust's tier-1 Windows targets do: the program links Microsoft's C runtime statically, `libcmt` with the Universal CRT, so that it needs nothing installed beside it, and the system's own libraries; a debug build's information for Windows' debuggers is to be CodeView in a PDB (Debugging, below). The MinGW targets, `*-w64-windows-gnu`, which Rust keeps at tier 2, are left out: one Windows target is one set of system headers, one linker and one debugger to support, and MSVC's is the one every Windows developer has.

### The toolchain

clang with `--target=x86_64-pc-windows-msvc` or `aarch64-pc-windows-msvc` compiles both backends' output and the runtime, and links through LLVM's COFF linker, `lld-link`, with `-fuse-ld=lld`, against the Windows SDK and the MSVC libraries Visual Studio's Build Tools install, which clang finds by itself on a machine that has them. `cl.exe`, Microsoft's own compiler, is not supported: the runtime is C11 with GNU extensions, inline assembly and `__atomic` builtins, which only clang and gcc compile, and clang ships for Windows as LLVM's official installer and inside Visual Studio. A binary is named with `.exe`, as Windows requires. Windows has no `cc`, so the C compiler a C backend's or a debug build runs is clang there unless `CC` names another, and a gcc is refused, since it builds for MinGW alone. `lld-link` is found beside the clang a build runs, as clang's `-print-prog-name` names it, or on the path, so the linker needs no setting of its own. `snello doctor` on Windows names `winget install LLVM.LLVM` as the fix for a missing clang, as it names `apt` and `brew` elsewhere, and links its link-time optimization probe with `-fuse-ld=lld`, and checks the Build Tools on their own: it builds a program of C that uses the C library, as a build compiles against the SDK's headers and links against the C runtime, and names Visual Studio's Build Tools with the C++ workload as the fix of a build that fails, with what clang said, a header or a library not found; a host whose builds read a sysroot needs none, and the check says so.

Building for Windows from another system needs the Windows SDK and the MSVC libraries, which Microsoft's licence lets a developer download for their own use and not redistribute; a build for Windows elsewhere reads them from the sysroot `SNELLO_SYSROOT_windows_amd64` or `SNELLO_SYSROOT_windows_arm64` names, laid out as the `xwin` tool writes them, as `cargo xwin` builds Rust for Windows from Linux, and a build on Windows reads it too when it is set. A sysroot must hold the libraries of the target's processor, which `xwin --arch x86_64,aarch64 splat` writes for both, and one without them is refused with the command that writes them. It is tier 3: nothing in CI builds that way.

### Threads, locks and the waits on an address

The runtime's build compiles one list of files for every target, so Windows' code is under `#if defined(_WIN32)`: in place, in a file the systems share, or whole, in `os_windows.c`, which takes the place of `os.c`'s calls on Windows and compiles to nothing elsewhere. The system half the rest of the runtime calls is `system.h`: a thread is `CreateThread`; a mutex and a condition are Windows' slim reader-writer lock and condition variable, which are the same primitives `std::sync` uses on Windows; a wait on an address is `WaitOnAddress` and `WakeByAddressSingle`, as Linux's is the futex and macOS's `os_sync_wait_on_address`. A one-time setup, Winsock's start and the environment's copy, is the runtime's own on every system, `sn_once` in `internal.h`, a word the first caller claims while the others sleep on it, and not the system's once, `InitOnceExecuteOnce` or `pthread_once`: those call the setup through a pointer, which the stack analysis cannot follow from a task's code, where the runtime's, inlined, calls it by name. Thread-locals are C11's `_Thread_local`, which clang lowers to Windows' implicit TLS for an executable, and the rule of `06-tasks-and-channels.md` holds as it does elsewhere: a task reads the thread's state through a call the compiler cannot merge, since a task may resume on another thread.

### Task stacks

A guarded stack is a reservation made by `VirtualAlloc`, every page but its guard committed when the stack is taken, as `mmap` and `mprotect` make one writable elsewhere; the small stacks of bounded tasks are packed in committed blocks of a megabyte, as they are elsewhere. Committing a guarded stack whole charges the system's commit limit for it, where Linux's `MAP_NORESERVE` charges nothing, and the system backs only the pages a task touches either way; growing it page by page, as Windows grows a thread's stack through a `PAGE_GUARD` page, would cost a system call on every reuse of a stack to know how far it had grown, for the unbounded tasks alone, since a bounded task's stack is small. A guarded stack the pool has no room for is decommitted, since Windows frees a reservation only whole and a stack is part of a block's. Its guard is a page of no access, as it is on Linux and macOS, where a task that runs into it ends the program with the system's fault: Windows reports a stack overflow, and the process ends. A report of the overflow as a panic, which needs a handler with room of its own on every system, is not part of this port. An unbounded task of a Windows program charges its whole guarded stack, 256 KB, against the commit limit, and a spawn past that limit panics, `cannot reserve a task's stack: the system's commit limit is reached`.

Clang probes a frame larger than a page on Windows through `__chkstk`, which compares the frame with the stack's limit in the thread's information block and touches the pages below it in turn, so the block must hold the bounds of the stack the task is on, which the switch keeps; the stack analysis reads the probe's own code, which moves the stack pointer by 16 bytes on x86-64 and none on arm64, and counts the frame it checks by the size the instruction just before its call puts in its register, `eax`, or `x15` in sixteens, taken from the stack pointer just after it; a function a branch of whose reaches the call or the decrement, as when two paths put two sizes there and meet at the call, is left unbounded.

### The context switch

The switch is `sn_switch` written for the Windows calling conventions, in the form Boost.Context's `jump_x86_64_ms_pe` and `jump_arm64_ms_pe` give it. On x86-64 it saves what the Windows x64 convention makes the callee keep, which is more than System V's: `rbx`, `rbp`, `rdi`, `rsi` and `r12` to `r15`, and the vector registers `xmm6` to `xmm15`, with `MXCSR` and the x87 control word. On arm64 it saves `x19` to `x28`, the frame and link registers and `d8` to `d15`, and never touches `x18`, which Windows reserves for the thread's block. On both it saves and restores three fields of the thread's information block, the bounds of the stack the thread is on: `StackBase`, `StackLimit` and `DeallocationStack`. Windows reads them when it unwinds a frame, when it dispatches an exception and when `__chkstk` probes, and a task runs on a stack the thread did not start with, so each switch writes the stack of the task it resumes into the block of the thread it resumes on, as `SwitchToFiber` does; a fresh task's frame holds its stack's bounds, written when it is made, and `sn_on_stack`, which runs a panic on another stack, sets that stack's bounds for the call and puts the thread's back after. The fibers themselves are not used: a fiber switch also saves and restores the fiber-local storage and the exception chain, which a task does not use, and costs a call into the system. The vector registers are saved unaligned, so that a task's first frame starts as a called function's does, eight bytes past a sixteen-byte boundary with the 32 bytes of home space the convention gives a callee above it; on aligned data the unaligned form costs what the aligned one does. A panic's jump back to its mark is the compiler's own `setjmp`, which saves the frame and the stack pointers and unwinds nothing, and on arm64, where clang has none, a pair of the runtime's own: the C library's `longjmp` on Windows unwinds the frames between by the system's exception handling.

### The poller

Elsewhere the poller is readiness: a socket is non-blocking, a read that would block parks the task, and epoll or kqueue says when to try again. Windows' sockets report completion instead, through an I/O completion port, and the runtime keeps its readiness model through the port: each socket is polled through the AFD driver, the layer under Winsock, with the result delivered to the port, which is how Tokio's `mio`, `wepoll` and libuv's poll handles get readiness on Windows. An AFD poll is one-shot, so a socket is not registered once, as it is with epoll and kqueue: a wait that is about to park arms a poll of its direction, unless one is armed, which completes when the socket is ready or at once when it already is; arming after a call would have blocked, and not again after each completion, is what keeps a socket with unread data from completing a poll in a loop. `mio` and `wepoll` keep one poll a socket, for the union of the events wanted, cancelled and armed again when the interest changes; a poll a direction keeps a socket's readers and writers apart, as its two words are, with no cancel when one of them starts to wait. Each poll is a block of its own from the C library's allocator, which a debug build's count of blocks does not see, freed when the port gives it back. Closing a socket takes its polls out of its descriptor and cancels them, and a poll also asks for the socket's local close, so that none stays pending; each still completes through the port, and the poller, finding it no longer the descriptor's, frees it and wakes no one, since the descriptor may be the next socket's with the number.

The port is the poller: a worker looks at it without waiting, as it looks at epoll, and the idle worker that keeps the timers waits on it with `GetQueuedCompletionStatusEx` for the sockets, for its wake, posted to the port, and for its deadline, a high-resolution waitable timer the system posts to the port through a wait completion packet, as Go's scheduler waits on Windows, since a timed wait on a port counts in the system's ticks of 15.6 ms. Linux and macOS keep the keeper's wake and deadline in a set of the keeper's own, which no worker looking at the sockets takes. A port has no such set, so a worker that takes the keeper's packet posts it again while the keeper waits, and the keeper, when it takes a socket's completion, posts it again for a worker and leaves its wait to look at the sockets as a worker does. On every system, the worker that left the keeper's wait on the poller's events takes them whether or not a task waits on a socket: an event no task waits for only marks its socket ready, and one left in the poller would end every keeper's wait at once, a spin through each sleep. The port lets any number of its threads run at once, as Go makes its port: with the system's default of one running thread per processor, a worker that ever looked at the port counts against it while it runs tasks, and with every worker busy the system would hold the keeper's deadline back. Go's overlapped reads, a completion per read, are the alternative set aside for the sockets: they would change every socket call of `net.c` and the buffer each read lends to the system, for no gain the readiness model lacks. A child's pipes take that model, since a pipe cannot be polled for readiness: this program's end of one is a named pipe opened overlapped and bound to the port, each read or write one operation whose completion the port posts to the task waiting on its record, and a cancel of such an operation waits for its completion after `CancelIoEx`, since the system holds the buffer until then (`05-standard-library.md`, section 6). A child's end comes to the port the same way the keeper's deadline does, by a wait completion packet on its process handle. A host name is looked up by `GetAddrInfoW` on the runtime's lookup threads, as `getaddrinfo` is elsewhere, its name converted to UTF-16, which the narrow call would read in the code page of the system's locale; a failure's text is formatted for each lookup, by `FormatMessageA`, where `gai_strerror` on Windows writes into one buffer every thread shares. Winsock is started once, at the first socket or lookup, whichever comes first.

### Files, the environment and the clock

The `os` package's calls are the system's wide-character calls, `CreateFileW`, `ReadFile`, `FindFirstFileExW` and the rest, with every path and name converted between Snello's UTF-8 and Windows' UTF-16 at the call, in `os_windows.c`, which takes the place of `os.c`'s calls there. A file is opened with the sharing every Windows program expects, read and write and delete, and kept as a descriptor of the C library's, the `int` the rest of the runtime takes for a file on every system. The C library keeps at most 8,192 descriptors, so a program holds at most 8,192 files open at once; a socket is the system's own handle and does not count against them. A file's reads and writes go straight to its handle, `ReadFile` and `WriteFile`, with no lock of the C library's, as Go and Rust read a file on Windows. A Win32 or Winsock failure is reported as the error number the same failure has on the other systems, so that `io.Kind` and the messages read it alike. A variable of the environment is matched with no regard to the case of its name, as Windows matches it. A path takes either separator, `\` and `/`, as Windows does: `path/filepath` writes `\`, reads both and keeps a path's volume in front, and `os` reads a path through it, while the `path` package keeps `/`, as Go's does (`05-standard-library.md`, decided 18). A file's mode is made from its read-only flag, `0444`, `0666` or `0777` for a directory, `0555` for a read-only one, since Windows keeps no permissions and has no umask, and a file made without the owner's write bit is made read-only. So a program that asks whether a file is its owner's alone gets a different answer there, and the `files` example prints what every system keeps of a file, its name and its size. `os.TempDir` is `GetTempPathW`'s, from `TMP`, `TEMP` or the user's profile, and `os.Cores` the processors of the process's affinity mask in its processor group. A path of 248 UTF-16 units or more, which the system's calls refuse unless long paths are enabled, is made absolute and given the prefix `\\?\`, under which the calls take a path of up to 32,767 units, as Go and Rust do; `os.RemoveAll` gives its root that prefix always, so that every path it joins under it, a name ending in a dot or a space among them, is taken as it is. A reparse point that names another file, a symbolic link or a junction, is not a directory even when it names one, as Go reads it, and one of another kind, such as a cloud drive's placeholder, is read as the file it stands for. A standard stream on a console is read and written as the console's own text, UTF-16, through `ReadConsoleW` and `WriteConsoleW`, as Go and Rust do, a write that ends inside a character keeping that character's first bytes for the next write, and a line that starts with Ctrl-Z ending the input; the console's code page, which the program shares with the shell that started it, is left as it is. The arguments are read with `GetCommandLineW` and split by the rules of `CommandLineToArgvW`, the environment with `GetEnvironmentStringsW`. The clock is `QueryPerformanceCounter` for the monotonic time and `GetSystemTimePreciseAsFileTime` for the wall clock; the random source is `ProcessPrng`.

### Interrupts

A program on Windows receives no signals. The terminal's interrupt, Ctrl-C and Ctrl-Break, and the closing of its console reach every process on the console as a control event, which a handler `SetConsoleCtrlHandler` registers answers on a thread of the system's, and which with no handler of the program's ends the process, by the system's default handler, `ExitProcess` with `STATUS_CONTROL_C_EXIT`, Windows' code for a program Ctrl-C ended. The runtime registers one, the counterpart of the thread that waits for `SIGINT` and `SIGTERM` on Linux and macOS (`05-standard-library.md`, section 6): Ctrl-C and Ctrl-Break are `signal.Interrupt`, and the console's close, the logoff and the shutdown `signal.Terminate`, after which the handler never returns, since the system ends the process when it does, within the seconds it allows. A signal no channel asked for cancels the program's scope, and the program, once `main` has returned, ends with `STATUS_CONTROL_C_EXIT`, the code the system's own handler gives; a second interrupt ends it at once with the same. A read of the console that Ctrl-C interrupts succeeds with nothing read and `ERROR_OPERATION_ABORTED`, which is not the end of the input: when the interrupt cancelled the program the read fails as a cancelled read does, and else it is made again, as Rust's standard library makes it; `TestConsole` runs a program on a pseudo console, as a terminal hosts one, and types Ctrl-C at it as a terminal sends it, which ends a pending read where `GenerateConsoleCtrlEvent` would not. Of the command's half: `snello run` exits with a program's code, Ctrl-C's included, and where `snello` ends itself by the signal that reached it while it builds, it exits on Windows, which has no signal to raise, with the code that ending gives elsewhere, 128 and the signal's number. `SIGPIPE`, which the runtime ignores on Linux and macOS, has no counterpart: a write to a closed pipe or socket fails with an error of Kind `io.BrokenPipe` on every system, and a write to the standard output or error whose reader is gone, which ends a program by the signal elsewhere, fails with that error on Windows.

### A panic's trace

The table of a panic's trace is read from the image a first link of the program writes, not from an object: the image keeps its DWARF, `lld-link /debug:dwarf`, which clang writes into each COFF object when asked, `-gdwarf`, so the reader is the one it already is, and the image's addresses are final, where Go's `debug/pe` applies no relocations to a COFF object. The object the link-time optimizer leaves is kept from the same link, `/lldsavetemps:prelink`, for the final one. Only the functions the program's native objects define, that object's or a debug build's own, are given anchors and rows; the C library's functions the link added to the image bound the others' code and have neither, as they have no place in an object's table. The table's own object is written as COFF. A PE binary carries no symbol table by default, and the table's anchors and the stack analysis need the functions' addresses, so the final link keeps one, `lld-link /debug:symtab`, which the trace reads through Go's `debug/pe`; a release build's final link is given no `-g`, so it writes no PDB, and its image keeps no DWARF; a debug build's writes the PDB of section Debugging.

### The stack analysis

The analysis reads a PE binary as it reads ELF and Mach-O, `compiler/emit/stack/pe.go`: its processor from the header, its functions from the symbol table the link keeps, `/debug:symtab`, and its code through LLVM's `llvm-objdump`, or the path's objdump, which on macOS is LLVM's. A call into a library goes through a slot of the table of imports, named `__imp_` and the function's name in the symbol table, directly for a function the headers declare imported, as the SDK's declare every one, or through the thunk the linker writes for one declared plainly: on x86-64 a call or a jump through memory whose slot the disassembler names, or through a register a compiler loaded from the slot once and keeps across calls, as it hoists a function called in a loop; on arm64 a call or a jump through a register loaded from the slot, its page by `adrp` and its offset by `ldr`. A register is the slot's function where every path into the call leaves it so, a forward analysis over the function's blocks, and any other write to it, named or not, or a call that the convention lets change it, makes the call one through a pointer. The table of imports names each slot's library, by the function's name or its ordinal alone. The system's libraries stand where the C library stands elsewhere, `kernel32`, `kernelbase`, `ntdll`, `ws2_32`, `iphlpapi` and the API sets, `api-ms-win-`, and a call into any other makes a task unbounded. The C runtime, the Universal CRT, `libcmt` and `vcruntime`, is linked into the program and calls through pointers it keeps of its own, so a call of one of its functions is counted at the function's measured figure rather than walked; a function the runtime lets be overridden, the linker's function overriding, has its own code under its name and `_$fo_default$`, `memset_$fo_default$`, which a call of `memset` reaches, and is counted as the function; which functions are the runtime's the final link's map says, `/map`, which names the library each symbol came from, so that a function of the program's own named as one of the runtime's, which the link takes over the runtime's, is walked as the program's code. `testdata/libc_windows.c` measures every function of both that the runtime calls, down its heavier paths, on a thread whose stack it paints downward, as the guard page grows it, with the thread's stack limit at the caller's frame for the call, as a small stack's is, so that the stack probe writes the pages it checks; `exit` and `abort` it measures in a child it runs under itself as a debugger, which reads the child's stack as the system reports its end. Their figures are a table of Windows' own, `windowsLibraryStacks`, the most of x86-64 and arm64, never merged with Linux's and macOS's: a socket's call takes a kilobyte or more through Winsock's providers and a hundred bytes on Linux, and one table of both would deepen every Linux task for Windows' sake. Where CI's figure of a function was within Linux's allowance, that allowance, which bounds it, is its entry. Where Windows' figures are measured, an import or a function of the C runtime the table does not hold leaves a task that calls it unbounded, as on every system, the reason naming it, and the C runtime's code is not walked at all, since it calls through pointers of its own; where they are not, every call into either leaves a task unbounded. The runtime's two Windows forms of a move to another stack are counted as `sn_on_stack` is, at the frame they push: `sn_on_stack_bounded`, which sets the stack's bounds in the thread's information block, and `sn_longjmp_regs`, the runtime's own long jump, which a contained panic takes to the mark of the innermost catch still running, an ancestor's frame on the same stack, so no deeper than a path already counted. A PE binary's code is cut into functions after a jump or a return that does not go on, and the padding after it, where no branch of the symbol's code crosses the cut either way, so that each piece holds every way into and out of its code but its calls: the thunk of an import by its ordinal has no symbol, and would otherwise be read as the end of the thunk before it, giving every caller of that one the other's import too. A branch or a call to a symbol and an offset reaches the piece that holds the address, and an address in no piece is the start of no function. A cut assumes that what follows it is reached by no way the listing does not show: a symbol whose code jumps through a register or memory that holds no import, as a table of jumps does, is not cut, both backends compile with jump tables off, and the runtime has no code that only the system's unwinder reaches, an exception's handler; a symbol two functions share is not cut either, and is read by its name, as on every system.

### Debugging

A debug build compiles the program with CodeView beside the DWARF the trace's table is read from, `-gcodeview` and in the LLVM backend's module the `CodeView` flag, and its final link writes a PDB beside the binary, `lld-link /debug:full`, keeping the symbol table, `/debug:symtab`, and dropping the DWARF only the first link's image needs, `/debug:nodwarf`; WinDbg, `cdb` and Visual Studio read it. What Snello's Python script gives lldb and gdb, a value shown as the program writes it, a natvis file gives Windows' debuggers, embedded in the PDB with `/natvis`, as Rust embeds natvis files in the PDBs it writes for the MSVC targets. A natvis visualizer names its type and matches no pattern of a C type's name, so the build writes one for each slice, option, result and enum type the program has, `compiler/emit/natvis`, from the first image's DWARF, with fixed ones for the runtime's string and map: an enum is shown by its case and the case's values, read from the union member the case names. `snello debug` starts `cdb` on Windows, from the path or from where the SDK installs it, as it starts lldb on macOS and gdb on Linux, with `snello.js` loaded, a script of the debugger's own whose `!tasks` lists the tasks' states as the Python script's `tasks` does, printing what its `taskList()` returns, the tasks as data, which `dx Debugger.State.Scripts.snello.Contents.taskList()` shows whole; `cdb` needs its provider of scripts for it, which the SDK's debugger for arm64 ships without, so `!tasks` is not available there. The script reads the runtime's table, and a waiting task's frames it asks the debugger to unwind from the task's saved context, `k =` with the frame pointer, the stack pointer the switch's caller resumes with and the saved return address, since x86-64's frame pointers make no chain on Windows; the table publishes that stack pointer's offset, past the return address on x86-64 and past the switch's frame on arm64, so the script holds no layout of either. That unwind is not shown yet: the debugger's `k` raises an exception on it, which `taskList()` carries in each task's `unwind`, with the command it ran, for whoever takes it up. The standard library's sources are found under the support's directory by the end of their paths, `-srcpath` with the support's directory ahead of the user's own `_NT_SOURCE_PATH`, since `cdb` maps no prefix of a path; it is an option and not the `.srcpath` command, which would take the commands after it on the line as places.

### The LLVM backend's calling convention

The LLVM backend lays out a call as the C compiler does, so that the program and the runtime agree on every value passed. Windows x64 passes an aggregate of 1, 2, 4 or 8 bytes in a register and any other by a pointer to a copy the caller makes, and returns one of more than 8 bytes through a pointer the caller passes, where System V passes up to 16 bytes in two registers; Windows on arm64 follows the AAPCS64 that Linux and macOS do, with its own variadic rule. A scalar narrower than a register, a `bool`, a `u8` or a `u16`, is extended with zeros where the convention requires it and nowhere else: Apple's, on both processors, and System V's x86-64 extend every one, Windows x64 a `bool` alone, and AAPCS64 on Linux and Windows none, where a value declared extended would be read as clean when the C side left its upper bits unset, a mismatch the table found on Linux on arm64 as well. The backend's table of conventions gains Windows', and `TestABIMatchesClang` holds every target's to what clang does for the same C prototypes, the three-word struct and the narrow scalars.

## 5. Memory safety

Nothing of this note changes a rule of the checker: the programs compiled for Windows are checked as every program is, borrow rules included, and the runtime owns every allocation with no collector on every system. The guard of a guarded stack keeps its promise on Windows as on the other systems, a page of no access, so a task that runs past its stack ends the program rather than writing over another's, and a small stack's bound counts the C library's functions as measured on that platform, or leaves the task on a guarded stack where they are not.

## Decisions

**Decided 1: tiers by Rust's policy, with the runners as the measure.** A tier is what CI does with a platform, so a platform's tier is never a promise CI does not keep.

**Decided 2: Windows through the MSVC targets and clang alone.** The Universal CRT, `lld-link` and PDB are what Windows developers and their debuggers use, and clang is the C compiler on Windows when `CC` names none; MinGW and `cl.exe` are left out, the first as a second Windows to support, the second as a compiler that cannot compile the runtime.

**Decided 3: a stack on Windows keeps the thread block's bounds, and its guard is a page of no access, as elsewhere.** Windows reads the thread block's bounds when it probes a large frame and when it unwinds, so each switch writes them, as Boost.Context and `SwitchToFiber` do; a task that runs past its stack ends the program, as it does on Linux and macOS, and a report of it as a panic is left for every system at once.

**Decided 4: the Windows poller is readiness through AFD on a completion port.** It keeps the readiness model every other system's poller and every socket call of the runtime share, as Tokio does on Windows.

**Decided 5: Windows' system libraries are counted as the C library is elsewhere.** A task's call into `kernel32`, `kernelbase`, `ntdll`, `ws2_32`, `iphlpapi` or an API set runs on the task's stack and is counted at the figure `TestCLibraryStack` measures on CI's Windows machines and half again, as a call into the C library is on Linux and macOS, so that Windows keeps the small stacks every other system has. What runs on the task's stack on a user's machine and not on CI's is the margin's to cover: the hooks a security product writes into `ntdll` and the service providers Winsock loads, as a library loaded with `LD_PRELOAD` is on Linux. The other way, Go's on Windows, runs every call into the system on the worker's own stack, switching to it and back for each, so that no figure of the system's is needed at all, for a switch at every call and the runtime's work of wrapping each; it is the way a case of a hook deeper than the margin would call for.

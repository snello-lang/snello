# The standard library

Status: decided 2026-10-18. This note says what the Teak standard library is: which names the language itself knows, where every other name comes from, how the library relates to Go's, and the rules every library signature follows. It exists because the twenty example programs use library names that no other document defines, and the checker in stage 1 is the first code that needs the answers. Three decisions had no precedent to follow; they are marked **decided** below with the reason, and the owner accepted all three with the stage 1 review (2026-10-18). Everything else follows a precedent named in place.

## The precedents

Three languages define the space, and Teak follows Go wherever Go has an answer, as the syntax conventions require.

- **Go** keeps the language's own vocabulary to a few dozen predeclared identifiers, `len`, `make`, `append`, `error` and the basic types, and puts everything else in packages that must be imported. There is no prelude.
- **Rust** makes `Option` and `Result` library types but imports them through a prelude, and the `?` operator is language syntax that knows them.
- **Swift** does the same with less ceremony: `T?` is sugar for a library enum, and the standard library is imported implicitly.

Teak takes Go's shape, a short predeclared list and no prelude, with Swift's sugar for the option type, which the syntax conventions already fixed as `T?`.

## 1. What the language knows

These names are predeclared: visible in every file without an import, and known to the compiler. The list is deliberately short and this section is its only home; the stage 1 checker's universe scope is built from it.

**Number types.** The short names used by Rust, Zig, Odin, Hare, Carbon and by LLVM itself, plus Go's everyday words. This is the one place Teak's vocabulary departs from Go's on purpose: Go's syntax and keywords are what make Teak readable at first sight, while the spelling of a primitive type is vocabulary, and vocabulary is where a language shows it is not a dialect.

| Kind | Types |
|---|---|
| Signed integers | `i8`, `i16`, `i32`, `i64`, `int` |
| Unsigned integers | `u8`, `u16`, `u32`, `u64`, `uint` |
| Floating point | `f32`, `f64` |
| Aliases | `byte` for `u8`, `rune` for `i32` |

`int` and `uint` are the word size of the platform and `int` is the index type, as in Go, so there is no `usize`. `byte` and `rune` name a meaning rather than a width and stay because strings are UTF-8 as in Go. Integer arithmetic wraps on overflow as in Go; checked arithmetic is a library function returning `T?`, not a language mode. There is no `i128`, no complex type and no `uintptr`: the first two are library types if ever needed, the third waits for the foreign-function boundary. Literals take the type their context asks for; there is no untyped constant arithmetic in the first version.

**Other basic types.** `bool`, `string`, `error`.

**Option and result.** `T?` with `Some` and `None`; `Result<T, E>` with `Ok` and `Err`. Both are enums the compiler knows, because `?` and `??` and `match` exhaustiveness are language features over them. Their methods: `Expect`, `Unwrap`, `UnwrapOr`, `IsSome`, `IsNone`, `IsOk`, `IsErr`, `Map`, `MapErr`. The ones that give the inside away, `Expect`, `Unwrap`, `UnwrapOr`, `Map` and `MapErr`, take their receiver; the tests lend it (decided with the borrow checker, 2026-10-18).

**Functions.** `len`, `cap`, `make`, `take`, `panic`, `print`, `min`, `max` (the last two added 2026-10-19 with the examples: Go has them since 1.21, and example 10 uses `min`).

**Methods on the built-in collection types.** Go cannot declare a method on a built-in type, so it hides these behind `append`, `delete` and the `strings` package. Teak puts them on the value, which is what the examples already write.

| On | Methods |
|---|---|
| `[]T` | `Push`, `Pop`, `Insert`, `Remove`, `RemoveValue`, `Clear`, `Swap`, `Reverse`, `Sort`, `SortBy`, `Contains`, `Clone`. `Swap(i, j)` exchanges two elements in place, Rust's `slice::swap` and the `Swap` of Go's `sort.Interface`: the move an algorithm over elements that are not `Copy` makes, since `xs[i], xs[j] = xs[j], xs[i]` would move each out of the slice (decided 2026-10-22, with `heap`). A sub-slice `xs[lo:hi]` has the type of a slice and lends its slice's buffer, so the methods that change the length, and replacing it, panic on one (decided 2026-10-21, after the review of the standard library found them corrupting the slice they were cut from); the check is the runtime's, as an index check is, since a function given `mut []T` cannot know which it holds |
| `map[K]V` | `Get`, `GetMut`, `Insert`, `Remove`, `Contains`, `Clone`. `m[k]` on a missing key reads the zero value and changes nothing; `m[k] = v` and `m[k] += v` make the entry. A range visits entries in insertion order (decided 2026-10-18 with the C backend) |
| `string` | `Len`, `Clone`, `Fields`, `Lines`, `Split`, `SplitOnce`, `Trim`, `HasPrefix`, `HasSuffix`, `Contains`, `ToUpper`, `ToLower` |
| `byte` | `IsDigit`, `IsSpace`, `IsLetter`, `IsUpper`, `IsLower`, ASCII |

**The standard traits.** `Copy`, `Clone`, `Eq`, `Ord`, `Hash`, `Drop`, `Error`, and the operator traits `Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`. Every number type is `Copy`, `Eq`, `Ord` and `Hash`, and implements the operator traits.

**Decided 1 (2026-10-18): predeclared.** The collection methods are predeclared with their types, as above, because Go's `append` and `len` are, and because `xs.Push(v)` with an import line above it would surprise a Go developer. The alternative was a package the program imports for them.

**Decided 2 (2026-10-18): `rc`.** The package for `Rc` and `Weak` is `rc`, after Rust's `std::rc`, so the type reads `rc.Rc<T>`. The alternative, `shared`, says what the package is for but makes the type read `shared.Rc<T>`, a name that explains itself twice.

## 3. Go's package map, Teak's signatures

Package names and layout are Go's, so a Go developer knows where to look. Inside a package the rule is: **the same name when the meaning is the same, a new name when ownership changes the meaning.** `strings.Repeat` is the same function in both languages. `os.ReadFile` is not: Go's returns a byte slice and a nullable error, Teak's returns `Result<string, io.Error>`, so it is `os.ReadToString`. Kotlin treats Java's library the same way: the same names where nothing changed, new ones where null safety did. Two string methods keep a Go name for a different meaning, recorded here so that the difference is known (2026-10-21, found by the review of the standard library): `s.Trim()` is Go's `strings.TrimSpace`, not its `strings.Trim`, which takes the bytes to cut; and `s.Lines()` drops each newline, where Go 1.24's `strings.Lines` keeps it. Renaming them, to `TrimSpace` and to a name of their own, is the owner's decision; until then the book and `std/builtin` say so beside each. Everything else in `strings` and the string methods reads text as Go does: case by Unicode's simple mapping and white space by Unicode's `White_Space` property, as Go's `unicode` package reads them, from tables `runtime/mkunicode.go` writes out of the Unicode Character Database itself, `UnicodeData.txt` and `PropList.txt` at the version it names, so Teak's Unicode follows the standard and not the toolchain that builds the compiler, a byte that is not UTF-8 as U+FFFD, and a search in time in proportion to the text.

## 4. Three signature rules

Every library function follows these, so a reader can predict a signature from a function's meaning. They are Rust's conventions in Teak's words, and they follow from `04-borrows-ref-and-mut.md`.

1. A parameter that is only read is `ref T`: `strings.Repeat(s ref string, n int) string`, `fmt.Println(args ...ref any)`.
2. A parameter that is changed is `mut T`: `sort.Sort(xs mut []T)`, `fmt.Fprintln(w mut io.Writer, args ...ref any)`.
3. A parameter that is kept, stored or sent is taken by value, which moves it: `Push(v T)`, `arena.New(v T) Index<T>`, `sync.NewArc(v T) Arc<T>`.

Results are owned. `Copy` types are by value everywhere, and for them rule 1 reads as plain pass-by-value, as in Go.

## 5. The call-site rule

Rule 1 forces one language decision. The borrows note today says a borrow at a call site is written with the keyword, `strings.Fields(ref job.text)`, and every print call in the examples passes owned values without it: `fmt.Println("error:", e)`. Under the written rule that call moves `e` into `Println`, which is not what anyone means.

**Decided 3 (2026-10-18): yes.** An owned value passed where a `ref T` parameter is expected is borrowed for the call, exactly as a receiver already is: `x.Describe()` borrows `x` with no keyword. `mut` stays explicit at every call site, because a visible mutation is worth a word, as Go's `&x` and Swift's `&` are. Writing `ref` at the call site remains legal and means the same thing. With this rule the print calls are correct as written; the borrows note states the rule beside its call-site example.

## How the library is built

Decided 2026-10-19, with the first package. The library is Teak source under `std/`, one directory per import path holding one file named after the package, `std/math/math.teak`, embedded in the compiler binary so that a build needs no library path and no environment, as Go's toolchain carries its own standard library. When a program imports a path the compiler's table does not answer, the importer (`importer.Importer` in `compiler/importer/`, the counterpart of `go/importer`) parses and checks that package once, into the same `types.Info` as the program, and the C backend compiles the package with the program into the one C file, each of its top-level names qualified by the import path in the runtime's reserved space: `math.Sqrt` is `tk_math_Sqrt`. There is no separate compilation and no library binary; a Teak program is one translation unit, which is what lets the C compiler inline across the boundary.

A library function the runtime must provide is declared without a body, as a Go function implemented in assembly is, and the runtime defines it in C under that same qualified name: `func Sqrt(x f64) f64` in package `math` is `double tk_math_Sqrt(double)` in `teak.h`. A library variable declared without a value is the runtime's the same way: `var Args []string` in `os` is filled by the runtime at start-up. The runtime's side of `os` is small and primitive on purpose: each function takes a descriptor and returns the system's error number, zero on success, storing its result through its last parameter, and the Teak code builds the `Result` and the `io.Error`. A program may not declare a function without a body; the checker reports `missing function body`. Only the exported names of a package are visible to the program, by Go's capitalization rule, and so are only the exported fields and methods of its types; an import of a path the library does not have is reported at the import.

`io.Error` is a struct: the operation, the path and the system's reason, with a `Kind` the program can match on, `NotExist`, `Permission`, `Exists`, `Refused`, `Reset`, `TimedOut`, `Other`, and `Error()` giving Go's wording. **A socket's Error is Go's `net.OpError` in the same struct** (decided 2026-10-21, after the review of the standard library found network errors told apart only by their text): `Path` is the network and address, `tcp 127.0.0.1:1`, or both ends of a connection, `tcp 127.0.0.1:50338->127.0.0.1:8080`, and `Msg` names the system call before the system's reason, so the line reads as Go's, `dial tcp 127.0.0.1:1: connect: connection refused`; the three kinds a network program acts on, a refused dial, a reset or broken connection and one timed out, are `Kind`s rather than a type of `net`'s own, since a program matches on a `Kind` already and Go's own test, `errors.Is(err, syscall.ECONNREFUSED)`, is a test of the error number. An address is an IPv4 address and a port from 0 to 65535: an empty host is every address for `Listen` and this machine for `Dial`, as in Go, and a port out of range, a host name and an IPv6 address are refused with an Error that says which, `listen tcp: address 70000: invalid port`; looking names up and IPv6 are later work. It implements the standard trait `Error`, which its own name shadows inside package `io`; the syntax conventions resolve a trait's name as a trait for that reason. `io.Errno(op, path, code)` builds one from an error number, which is how `os` reports. `io.Reader` and `io.Writer` are traits with one method each, and `io.Copy` is generic over them, since a borrowed trait value is not a type yet.

Every package is a `.teak` file under `std/`, the ones the compiler writes included (decided 2026-10-19, at the owner's word: a reader expects `std/` to list the whole library, with the documentation where Go puts it). `std/fmt/fmt.teak` declares `Println`, `Printf`, `Sprint`, `Sprintf`, `Fprintln` and `Fprintf` without bodies, with `...ref any` for the arguments the compiler takes by their types, and the backend writes each call from a table of those six names and `os.Exit`; the checker holds no table of library names at all. `fmt` is the compiler's by design: its functions take arguments of any type and the compiler lowers each by its type, so there is no formatter in the runtime. `Fprintln` and `Fprintf` are generic over `W: io.Writer`, since a borrowed trait value is not a type yet, and the backend writes the formatted text with one call of the type's `Write`. `os.Exit` is declared `func Exit(code int)` and the checker knows the call never returns, as it knows of `panic`, until a signature can say so.

`arena` is written in Teak with no runtime at all (2026-10-19): `Arena<T>` is a slice of slots, each an `Option` of the value and a generation, a free list of slot numbers and a count; `Index<T>` is the slot number and the generation, `Copy`, `Eq` and `Hash`, with `T` as a phantom parameter so an index carries its element type. Generations start at 1 so that the zero `Index` names nothing. `Get` and `GetMut` match on the slot's `Option` through a borrow of the arena, and `Remove` takes the value out with `take` and raises the generation. `New<T>()` takes its type argument explicitly where nothing infers it, as example 15's `slots: arena.New()` would need; the iteration `for i, v := range a` of `02-arenas-and-indices.md` waits for the iterator trait.

`rc` is written in Teak over two functions the compiler provides (2026-10-19): `Rc<T>` and `Weak<T>` each hold an `Option` of an owned pointer to a shared cell, the value as an `Option` beside a strong and a weak count; `alias(p ref *cell<T>) *cell<T>` gives a second owned copy of the pointer a borrow lends, and `leak(p *cell<T>)` consumes a pointer and frees nothing. They are the one unsafe step reference counting needs, declared without bodies and unexported, so a program cannot reach them, and lowered by the backend to the pointer itself, as `fmt`'s functions are lowered to the printers. `Clone` and `Downgrade` alias the cell and raise a count; `Drop` takes the pointer out of the handle with `take`, lowers a count, drops the value with the last `Rc`, and either leaks the pointer, so the cell outlives this handle, or lets it go, so the last handle of either kind frees the cell. `Get` lends the value through the pointer; `GetMut` lends it only when the strong count is 1 and the weak count 0, since a `Weak` elsewhere could otherwise be upgraded and read while the `mut` borrow lives. There is no interior mutability: a tree whose nodes hold `Weak` links back to their parents cannot be built with `Rc`, since a node is shared by the time its link is set, and a lock, the other way to change a shared value, holds only a value that is `Send`, which an `Rc` is not; that tree is the arena's, as `examples/01-tree/README.md` says. An `Rc` and a `Weak` implement `fmt.Stringer` and print as the value they hold, an empty handle or a `Weak` whose value is gone as `rc.Rc()` or `rc.Weak()` (2026-10-21; printing one failed to build before, on the `local` field of its cell, which no printer now prints). An `Arena` implements `fmt.Stringer` too and prints the values it holds in slot order, `arena[a b c]`, rather than its slots and generations.

`bufio` is written in Teak over `io`'s traits (2026-10-19): `Writer<W: io.Writer>`, `Reader<R: io.Reader>` and `Scanner<R: io.Reader>` each hold a `mut` borrow of the value under them, so they are borrow-holding structs under the rules of `00-syntax-conventions.md`, lent and dropped but never stored, and `NewWriter(w mut W)` returns one tied to its one borrowed parameter. `Writer` implements `io.Writer` and `Reader` implements `io.Reader`, so `fmt.Fprintln` and `io.Copy` take them; for that the rule on type arguments gained its one exception, a generic function that only borrows values of a type parameter takes an argument holding a borrow (`lentOnly`). The buffer is a byte slice written out in blocks of 4096 bytes; the scanner keeps the unconsumed tail and reads a block when it has no newline, never more than its limit leaves room for, so a line past the limit is refused whatever the reader gives at a call, as Go's scanner reads into a buffer no larger than its limit; it strips `\n` and `\r\n`, and counts a last line without one. A `Reader` at the end of the input asks the reader under it again at the next call, as Go's does, so a file being appended to is read on; a `Writer` returns the error it keeps for an empty write too, and `NewWriterSize(w, 0)` is `NewWriter` (2026-10-21, after the review). A range over a scanner's lines, as example 19 writes it, waits for the iterator trait; the Go idiom `for sc.Scan()` stands until then.

**Decided 4 (2026-10-19): `std/builtin` documents the predeclared names.** `Option`, `Result` and the methods of section 1 stay the compiler's, since `?`, `??`, the `if` binding and `T?` are language features over them and a method of their own cannot be declared in Teak; but a reader of `std/` expects the whole library there, and `Push`, `Expect` and `Map` were documented nowhere a reader of the library would look. So `std/builtin/builtin.teak` declares them all with doc comments and no bodies, as Go's package `builtin` does, with the receivers written as a call would use them, `func (xs mut []T) Push(v T)`, `func (o T?) Map<U>(f func(v T) U) U?`. It is never compiled and its import is refused. The objection to a second statement of the signatures, that it drifts, is answered by a test: `TestBuiltin` under `std/` checks the file's methods as methods of holder structs and compares each with the checker's table, receiver mode, parameters and result, and reads the table's `case` names back to find a method the file omits. The file is thus the written specification of the predeclared surface, which the checker had only as code. Writing it found a parser gap: an optional tuple, `(ref string, ref string)?`, parsed as a parameter type but not as a result, so `SplitOnce`'s own signature could not be written; `parseResults` takes the `?` now.

Written in Teak: `math`, `io`, `os`, `strconv`, `strings`, `sort`, `time` but for `After` and `Tick`, which hand a `Time` over a channel and come with stage 3, `arena`, `rc` over its two compiler-provided primitives, and `bufio`; `fmt` is declared there and written by the compiler, and `builtin` documents the predeclared names. `sort.Sort` is the slice's `SortBy` with the element type's `Cmp`, and `time.Duration` is a number type over `i64`, so a `Duration` is written as a product with a constant, `10 * time.Millisecond`. Example 10 calls `sort.SliceBy`, which this table names `SortBy` as the slice method is; the example was changed to `SortBy` at task 2.7 (2026-10-19). `strings.Fields` returns the slice of borrows the string's method yields, a type only the library may write until the iterator trait exists. `strings.Builder` is a `[]byte` written to and copied out by `String()`; `strconv.Atoi` is written in Teak and `ParseFloat` reads through the runtime. The table below is now the predeclared methods alone.

**Decided 5 (2026-10-20): `sync`.** The package is written in Teak over nine bodiless runtime functions and three the compiler lowers, and four facts of the language shaped it:

**Decided 6 (2026-10-21, after the review of the standard library): `fmt` prints as Go's does, and checks its formats when the program is compiled.** A float prints in Go's shortest form, `strconv.FormatFloat(f, 'g', -1, 64)`, with Go's rule for the exponent, an exponent from a million up and below 0.0001, and `+Inf`, `-Inf` and `NaN`; an `f32` with the fewest digits that read back as the same `f32`; `%q` escapes as `strconv.Quote` does, over the printable runes as Go's `strconv.IsPrint` defines them, a letter, a mark, a number, a punctuation or a symbol, or the ASCII space, which the runtime carries in `runtime/c/unicode.c`, written by `mkunicode.go` from the Unicode Character Database with the case tables. The verbs are Go's `%v`, `%d`, `%s`, `%q`, `%f` and `%t` with a width, a precision and the minus flag. Since the compiler reads the format, the checker checks it against the arguments, as `go vet` does, but as an error: one grammar, `compiler/types/format.go`, serves the checker and both backends, which import the checker's package already. A type prints through its `String` method when it lists the trait `fmt.Stringer` after `impl`; Go matches `String() string` structurally, and a Teak trait is named, so the trait is declared in `std/fmt` and a type opts in, as it does for `Error`. `strconv.Error` has `Kind()`, `Syntax` or `Range`, read from its message, Go's `ErrSyntax` and `ErrRange`; `ParseFloat` reads Go's grammar, underscores and hexadecimal floats with their `p` exponent included. The predeclared `min` and `max` answer `NaN` when an argument is `NaN` and take `-0` as below `+0`, as Go's specification has them, where `math.Min` and `math.Max` keep Go's own order of special cases.

- **A `ref T` is a copy of `T` in the compiled program**, not a pointer, which is what makes a borrow of a small value free and a borrow of a pointer the pointer itself. So a lock cannot hold its value inline: `Lock` on a `ref Mutex<T>` would reach a copy of the value, and a change through the guard would be lost. `Mutex<T>` and `RwLock<T>` therefore own a pointer to a box on the heap, the lock's handle and the value, as `rc.Rc` owns a pointer to its cell; every borrow of the lock copies the pointer and reaches the one box.
- **The step from `ref` to `mut` is one lowered function.** `inside(p ref *box<T>) mut box<T>` returns the box a borrow of its pointer lends, as a `mut`: the pointer and the borrow of it are the same word, so the compiler writes nothing for it, exactly as for `rc.alias`. It is unexported, called only with the lock taken, and is the one place in the language a `mut` comes from a `ref`, which is the reason a lock exists. `Arc` uses `alias` and `leak` as `rc` does; the compiler lowers all three by package and name.
- **A guard is a borrow-holding struct with a `Drop`.** `Lock` and `Write` return `Guard<T>`, which holds the lock's handle and a `mut T`; `Read` returns `ReadGuard<T>` with a `ref T`. Both are tied to the lock they came from under the rules of `04-borrows-ref-and-mut.md`, so they cannot be stored, sent or outlive the lock, and `g := m.Lock().Get()` is refused as a borrow of a temporary. Their `Drop` gives the lock back. The value is reached through `Get`, as it is on `rc.Rc` and `arena.Arena`: `*g.Get() += 1` changes a number, `g.Get().Push(v)` a slice. A guard whose fields are the borrow was tried first, written `*g.v`, and set aside for the method, so that the three packages read alike.
- **A runtime lock is held as an `int`, as a file is.** The runtime's handle on a lock, its address since 2026-10-21 where it was first an index into a table the runtime kept, is a Teak `int`, so the library holds a handle the language can write and the runtime's structure stays its own; a `Mutex` or `RwLock` frees its lock in `Drop`, and a `WaitGroup`'s lock is freed by the last handle on the `Arc` it shares (2026-10-21). A lock is the runtime allocator's, so a debug build reports one that nothing freed. One runtime object serves all three: a lock held exclusively or shared, with a count for the wait group, and the list of waiting tasks the channels use, so the stage 4 scheduler parks a task on a lock as it parks one on a channel (`06-tasks-and-channels.md`).

The constructors are `NewArc`, `NewMutex`, `NewRwLock`, `NewOnce` and `NewWaitGroup`, since Teak has no function on a type, only methods on values: `sync.Arc.New(v)` as the examples first wrote it is not a form the language has. The zero value of each type is empty and its operations panic, as `rc.Rc`'s do, since a `Mutex<T>` has no value to protect before `NewMutex` gives it one; a `Once` is a `Mutex<bool>` and is made the same way. `Arc<T>` counts with one atomic add the runtime provides, on the cell's own field through `alias`, and needs no lock. `time.After` and `time.Tick` are written in Teak as a task that sleeps and sends on a channel of one, with `Tick` dropping a tick its receiver has not taken.

## The core library table

Stage 1 had no library code written in Teak: a table in the C emitter mapped each library name onto a function of the C runtime with the same meaning. What remains of it is the methods of section 1 on slices, maps, strings, options and results, each a runtime function, and the lowering of the seven functions the compiler provides. Library code written in Teak carries over to stage 4 unchanged.

## What this does not decide

Which functions exist beyond the ones above. The twenty examples are the specification for that, and task 2.6 keeps its criterion: every function the examples call exists with the signature the examples use.

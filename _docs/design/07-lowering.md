# Lowering: from the checked program to machine code

Status: decided. This note says how a Snello value is laid out and where it is released, as the C backend decided it and as the LLVM backend keeps or changes it. The two backends are checked against each other on every example by the differential test, so what they must agree on is written here once.

## The problem

A backend turns the checked program into the text of another language: C, or LLVM IR. Everything about ownership was decided before the backend sees the program. The checker records the type of every expression, every move, every capture of a closure and its kind, and the type arguments of every generic call; the backend reads those tables and decides nothing about ownership itself. What the backend does decide is the shape of every value in memory, the order of evaluation, where each value is released, and how a panic finds the values still to release. Those decisions were made in the C emitter one slice at a time and live in its code; a second backend must make the same ones or the two will disagree on some program, which the differential test would then find late. This note is the record both backends are written against.

## No intermediate form

The LLVM backend walks the checked syntax tree as the C emitter does, reading the same tables. A lowered form of its own between the tree and the IR, a sequence of instructions with explicit temporaries, drops and moves, was considered and set aside: every decision such a form would carry is a rule over the checker's tables, not a data structure, and the C emitter already applies those rules directly; making it print a lowered form instead would be a rewrite of a working backend for no new capability, and a form that only the LLVM backend used would be a second statement of the rules, not a shared one. What the backends share is a package of the rules that are pure functions over types, `compiler/emit/lower`, moved out of the C emitter as the LLVM backend needs them: the names of functions, instances and types, which must be the same symbols in both outputs since the runtime declares some of them; the predicates that say what a value of a type needs when dropped and whether a panic must find it; the capture classes of a closure; the monomorphization worklist; and the table of the library functions the compiler writes, `fmt`'s printing, `os.Exit`, the pointer primitives of `rc` and `sync`, and `testing.Catch`, whose function value each backend hands the runtime through an adapter as it hands the sort its order. The tree walk and the text are each backend's own. If a third backend ever arrives, the shared package is where a lowered form would grow from.

## The shape of every value

| Snello | C emitter | LLVM backend | Note |
|---|---|---|---|
| `int`, `uint`, `i8` to `i64`, `u8` to `u64`, `byte` | `int64_t`, `uint64_t` and the sized kinds | `i64`, `i8` to `i64` | arithmetic wraps on overflow in both, at the width of the type: the IR uses `add` on the type's own width without the no-wrap flags; the C emitter asks the C compiler for wrapping with `-fwrapv` and, since C adds two `u8`s as `int`s and anything beside a 64-bit literal as 64 bits, converts the result of `+`, `-`, `*`, a negation and a bitwise not to the type wherever the type is narrower than 64 bits, so that it is the type's when it is compared, passed or used as an index and not only when it is stored; an index of a narrow type is widened to the 64 bits of a length by its sign in the IR, and by C's own conversion in C. A literal is never wrapped: one its type cannot hold is refused by the checker, so no backend meets it, and nor is a constant, which the checker folds and refuses past its type, and which both backends write as its folded value. A float converted to an integer type drops its fraction, gives the nearest end of the type when it is past the range and zero when it is not a number, the rule of Rust's conversion, Java's and WebAssembly's saturating one, where C and the IR's plain conversion both leave such a float undefined and gave results that differed by processor and by build: the IR uses `llvm.fptosi.sat` and `llvm.fptoui.sat`, and the C emitter a function of the type, `sn_trunc_u8`, written on first use. A sum of constants that wraps is the same arithmetic, and the C compilers' warnings of overflow in a constant expression are off, `-Wno-overflow` for gcc and `-Wno-integer-overflow` for clang, since under them such a program would not compile at all. A shift by the width or more gives zero, or minus one for a negative number shifted right, with the count read as unsigned: C and the IR both leave such a count undefined and the processors disagree, so the IR settles it with a `select` and the C emitter with a function of the type, `sn_shl_u8`, written on first use as the division's is |
| `f32`, `f64` | `float`, `double` | `float`, `double` | every operation is rounded on its own, as IEEE 754 has it: a product and a sum stay two operations, never joined into one multiply-add that rounds once, so `a*b + c` gives the same digits through both backends and on every processor. The IR joins nothing unless told to; the C compiler is told not to with `-ffp-contract=off`. A literal beside an `f32` is written as a C `float`, `0.1f`, since a C `double` beside one would have C work the expression out in doubles and round once at the end |

| struct | a C struct of the fields, in order | a named struct type of the fields, in order | a type with a `Drop` method carries one more field, `sn_live` |

| `Result<T, E>` | `{bool ok; union {T val; E err}}` | `{i1, [n x i8]}` as an enum of two variants | |

| `[n]T` | a struct holding `T at[n]` | `[n x T]` inside a struct | a struct, so an array is copied and passed as a value |
| `map[K]V` | `sn_map`, eight words | the same | the runtime keeps the entries; the backend gives it the sizes, hash and equality of the key type |
| tuple | a struct of `e0`, `e1`, ... | a struct of the elements | |

| function value | `{result (*fn)(void *env, params...); uint64_t box[W]}` | `{ptr, [W x i64]}` | `W` is the program's largest closure of copies, at least four words; a closure that borrows keeps its environment in the writing frame and the box holds its address |
| trait value | `{const table *tab; void *data}` | `{ptr, ptr}` | the data is on the heap, owned by the value; the table is written once per implementing type and trait, with the drop first, then a function per method, then an accessor per trait field |
| a type parameter | never written | never written | every instance is written with its arguments substituted (`mono.go`) |

Two decisions carried over without change deserve their reason here. **The closure box is inline and of one size.** A function value must have one size per function type, since it is stored in fields and slices, so every one carries a box of `W` words, and a closure whose captures are all copies lives in the box entirely and is a value that goes anywhere, including out of the function that wrote it, with nothing to drop; a closure that borrows a variable keeps a pointer to it, in an environment in the writing frame, which the checker keeps from outliving that frame. Nothing is allocated for a closure, ever. **A trait value owns its data on the heap.** The alternative, a value large enough for any implementing type, would make every trait value as large as the largest type in the program; one allocation at the conversion and one indirect call per method is the price of a value of one size, and a `[]Shape` of three types is the case that chose it.

## What the LLVM backend changes

Three layouts change, each because the IR can say what C could not, and each is sound by a rule of the language.

- **`*T?` is a nullable pointer.** An owned pointer is never null, so null is free to mean `None`, and the option of a pointer costs nothing: a linked list's `next *Node?` is one word, as it would be by hand. The same holds for an option of a `mut` borrow, and of a `ref` borrow that is the address of its place, which a borrow always is but for a `ref` of a string or a slice, the view itself with no address (below), whose option stays `{i1, view}`. A borrow is made only of a place that exists, so it is never null either. The `ref` case matters for speed as much as for size: `Get`, `First`, `Peek`, `Find` and every iterator over a collection return `ref T?`, and once such a `Next` is written into a loop, the paths that build a pair `{i1, ptr}` meet in a phi of the pair, which LLVM does not take apart, so the loop is neither simplified nor vectorized; as the pointer alone, the loop over a deque in `bench/iterators.snello` went from 1.3 ns an item to 0.4, measured with only that layout changed in the IR. Rust guarantees the same layout for `Option<&T>`. The C emitter keeps the `{has, val}` struct, since C gives it no safe way to write the two as one type, and the C compiler takes the struct apart on its own; the difference is invisible to a program.
- **`ref T` is a pointer to the place.** The C emitter passes a `ref T` as a copy of the value, which is free for a number and a copy of three words for a string; a large struct lent to a method is copied whole. The borrow rules make a pointer sound: while a `ref` lives, no one changes or moves the value it lends, so the pointer always finds the value as it was lent, and many `ref`s to one value are many pointers to one place. The IR marks none of them `readonly` or `noalias`: `rc` and `sync` reach a cell's `mut` through a `ref` of its handle, which such a mark would make wrong. The library's lowered primitives follow the layout: the deque's `rawRef` gives the address of a slot as the `ref` when the element is lent by address and loads it when it is lent as its value, a string or a slice, and `rawMut` in `rc`, `sync` and `deque` gives the address as the `mut`; in C a `ref` is the value and a `mut` the address, and a field read through a `mut` is read in place.
- **A `ref` of a string or a slice is the view itself**, the three words, not a pointer to them (when the port reached `bufio`). The language types `s[lo:hi]` as a borrow of the slice or string it views, and such a view has no place behind it: a pointer to it would point into the frame that built it. The three words are what the C emitter passes too, and what the runtime takes for a `ref string` parameter; a `mut` borrow of a string or a slice stays a pointer, since it is written through. Everything that reads a value through its borrows asks the borrow's depth, and a view has none.
- **Through a borrowed option, the part is lent on.** `cur ?? else`, `x?`, `Expect` and a binding in a `match` or `if` on an option or a `Result` reached through a borrow yield the address of the value inside, as the checker types them, `ref *Node` for a `ref *Node?`; through an owned scrutinee they take the value out. The backend compares the depth of the type it must yield with the depth of the part and lends the address when the yield is deeper.
- **An enum is a tag and bytes.** The union's layout, written out as a byte array of the largest variant's size and the variants' alignment, since the IR has no unions. A variant's fields are reached through the variant's own struct type at the payload's address.

One rule of arithmetic is settled here because the IR forced the question: **an integer division by zero panics**, with the message `integer divide by zero`, and **the smallest number divided by minus one is the smallest number**, its remainder zero, as the wrapping of every other operation implies. C leaves both undefined and the processors disagree, so the C backend's programs trap on one processor and continue on another; the IR leaves both undefined too, and its optimizer would act on that, so the LLVM backend tests the divisor and settles the one overflowing quotient with a select, a few instructions per division. The C backend does the same through a function per integer type, `sn_quo_` and `sn_rem_` (when the two backends' tests became one table); before, its programs trapped on x86-64 and printed zero on arm64.

Everything else keeps its shape. The runtime is the same C runtime, linked unchanged: the LLVM backend calls `sn_alloc`, `sn_panic`, the string, slice and map functions, the printers, `sn_spawn`, the channels and the locks by the names and the layouts `snello.h` declares, and a library function declared without a body is the same runtime symbol under the same name, `sn_math_Sqrt`. The runtime's `main` calls `sn_main` as before. A debug build asks the same runtime checks at the same points: a pointer read, a string or slice read, a dropped place poisoned.

## Calling the runtime

The IR does not abstract the processor's calling convention away: an aggregate parameter in IR is passed as the IR says, which is not how C passes a struct. The runtime has exactly one aggregate at its boundary, the three-word struct of a string and of a `[]byte`, passed and returned by value by sixty of its functions, and clang lowers it in the way each platform's C convention says, which the backend must then match (`compiler/emit/llvm/abi.go`, decided by asking clang): on x86-64 under System V, Linux's and macOS's convention, a three-word parameter is a pointer to a copy the caller makes, marked `byval`, so the callee finds the copy in the argument area; on arm64, and on x86-64 under Windows' convention, which passes any struct of more than eight bytes so, it is a plain pointer to that copy, found in a register or the argument area; a three-word result comes back through a pointer the caller passes first, `sret`, on all. A scalar narrower than a register, a `bool`, a `u8` or a `u16`, is extended with zeros, `zeroext`, only where the convention requires it: Apple's, on both processors, and System V's x86-64 extend every one, Windows' x64 a `bool` alone, and AAPCS64 on Linux and Windows none, where a value declared extended would be read as clean when the C side left its upper bits unset (which found a mismatch on Linux on arm64 that no test had shown). The emitter declares every runtime function it calls in that form and writes its calls to match, and knows the convention of each platform it builds for, `TestABIMatchesClang` holding each to what clang does for the same C prototypes; another is an error until its convention is added, since a guessed convention is a miscompiled call. The program's own functions are not bound by this: both sides of a call between them are IR, and an aggregate passed as an IR value is read the same way by both. A map, a channel and a lock cross the boundary as a pointer or a number and need nothing. The module names its target triple, the processor and the system it is compiled for, so that clang lays it out for them whatever machine it runs on; the data layout is clang's own for that triple, not written by the backend.

## Evaluation order and temporaries

Operands are evaluated left to right, as the language says. Go orders only calls and channel operations and leaves a variable's read against them open; Snello orders everything, so `ys[i] = f()` writes `ys` at `i` as it was before `f` ran, as Java and C# do, and two backends cannot disagree. An assignment evaluates, left to right, the index and key operands of its places, then its values, and only then reaches the places and stores, a map's entry made last: `m[tick()] = tick()` keys the first value under the first tick, and `n["a"] = len(n)` counts no entry for `"a"`. The C emitter must work for this, since C leaves the order of arguments and initializers open. It measures rather than guesses: an operand is written, and when its writing wrote statements of its own, a map read saving its key or a `match` used as a value, the earlier operands whose order against them is visible, those with effects or all of them when the later operand has effects, are saved in temporaries before those statements (`operands` in `hoist.go`); an operand before the last one with effects is saved, and that one too when an operand after it reads anything; the right side of `&&` and `||` that wrote statements has them run under the test of the left side. Effects are a call, a `match`, `if`, `?` or `??`, a channel receive, and `mut m[k]`, which makes an entry (`lower.HasEffects`, shared by both backends); an assignment saves its places' operands and its value in the `pre` table a deferred call already uses (`orderAssignment`). In the IR every expression is a sequence of instructions in a basic block, so the order is the order written and the hoisting machinery has no counterpart: a `match` used as a value becomes blocks that join in a `phi`, or a store to a slot the arms share. The evaluation of a call's arguments before its receiver, which the borrows note decided, is a rule both backends follow. A compound assignment whose value may change its place, `c -= tick(mut c)` or `xs[0] += grow(mut xs)`, reads the old value first, a clone of a string, then evaluates the value, and only then reaches the place again and stores (`lower.OldReadFirst`, `changedCompound` in both backends); a type with an `Add` takes the old value and the value in its call, and the place is reached after it. A pointer to the place taken before the value would outlive a slice the value grows or a map it rehashes, as both backends had it before: the sum was written into the freed buffer and lost, and a string read freed memory. Java reads the old value first and Go evaluates such a value first; reading first is the left to right rule the rest of the language keeps, and a value that does not change the place keeps the single reach of the place it had. The failure of `?` is marked unlikely in both backends, `SN_UNLIKELY` in C and `llvm.expect` in the IR: a branch the optimizer cannot weigh it takes as even, so each `?` on a path halved its guess of how often the rest ran, and after a few the calls there were judged cold and left out of line, json's `expectByte` in `seekField` among them, which cost a decoded record 18 ns in C. A panic needs no mark, since `sn_panic` never returns.

A value no variable holds, a string built for a print or a struct built to be lent, is a temporary of the statement that made it: it is held until the statement ends and dropped then, in both backends, after the drops of any variable the statement declared. An owned operand the operation takes, evaluated before an operand that may end the statement, by `?` or a return in its else, or by a panic in a call, an index or a division, is held the same way until every operand is in, and only then moved out of its temporary into the operation, so that leaving drops it and a panic whose task has a handle drops it too, where it was lost before (after a task's group found a channel handle cloned for a call lost to the panic of the call's next argument). Two parts of a statement end sooner (after the backends were found to disagree on both). The condition of an `if` is decided before either branch runs, and its temporaries are dropped then, since nothing binds a borrow of them, an `if` used as a value's as well (after the C backend was found keeping those to the statement's end, which left the temporary of an `else if`'s condition dropped outside the block it was made in); a guard taken in the condition, `if *m.Lock().Get() == 0 { *m.Lock().Get() = 1 }`, is given back before the body takes the lock again, as Rust drops the temporaries of an `if` condition. An `if` binding keeps its temporaries through its body, since the binding may borrow from them. The right side of `&&` and `||` runs only when the left leaves the answer open, and what it built is dropped on that path, before the two paths meet: a temporary the right side would have built is never built, and never dropped, when the left decides. A `for` condition's temporaries are dropped on every pass, before the body: a condition that builds one is tested at the top of the body, never hoisted above the loop where it would be built once and dropped after it. A field, an element, or what a pointer points at is a place wherever the value is, in a temporary as in a variable (after the backends were found copying the part of a temporary out and dropping it beside the whole): `len(row().tags)` reads the slice inside the temporary that holds the row, `grow(mut row().tags)` lends it there, and the row is dropped once; the checker refuses every move of such a part, so no part leaves its temporary. A pointer built here and read through, dereferenced, `(*mk()).name`, `(**mk2()).name`, or as a method's `ref` or `mut` receiver, `mk().Size()`, `mk().Add()`, is held whole as any temporary, the pointer and not the value it points at, so its block is freed once when the statement ends (after both backends were found leaving the box of a `mut` receiver, and C copying the value of a `ref` one out of it). `compiler/emit/internal/differ` builds every statement form with every kind of temporary through both backends and requires one output.

A chain of string additions, `a + "-" + b + c`, parentheses looked through, is one concatenation: every operand evaluated left to right, the length summed, one block made, and the operands built here freed after (`lower.Addends`). Which operand was built here is read from its type and not from its shape: one whose type is a borrow is lent, whatever gave it, a variable, a field, a call that returns `ref string`, a `??`, an `if` or a `match`, and is never freed, since the string is its lender's (`isLent` in both backends; before, a call was taken for a value made there whatever it returned, and `d.Path() + "/"` freed the string `d` held, which `testdata/lent.snello` now holds both backends to in seventy-two forms); a type of the program's own with a `+` method is never part of a chain. `s += t` on a string is `sn_string_append`, which writes in place while the string owns room past its end and else moves it into a block twice as large; nothing can be viewing `s` while it changes, by the borrow rules.

## Where values are released

Every value is released where the checker said its owner dies, and each backend keeps a frame per scope it writes, holding the owned variables declared there that have something to release. The points are these, and a backend writes a drop at every one:

| Point | What is dropped |
|---|---|
| the end of a block | the block's variables, last declared first |
| before a `return` | the statement's temporaries, the variables of every open frame of the function and the deferred calls that ran, last registered first |
| before a `break` or `continue` | the variables of the frames down to the loop left or continued |
| the end of a `match` arm | the arm's bindings, and the parts of the scrutinee an arm consumed |
| the end of a statement | its temporaries |
| an assignment to a place that holds a value | the old value, before the new one is stored |
| a map write to an existing key | the old value, and the new key, since the entry keeps its own |
| a `take` | nothing: the place is left `None` and the value moves out |
| a closure capture consumed by the closure's body | the capture, when the body ends |
| a spawned task ending | the task's parameters and captures, as any function's |
| the end of `main` | the top-level variables of the program; nothing of other tasks |
| a panic | the deferred calls that ran and the guarded values of the panicking task, last registered first, by the runtime |

A move empties the place it moves from: an owned pointer becomes null, a string or slice gets a zero length and capacity, a struct with a `Drop` method clears its `sn_live` flag, a composite empties its parts. The drop of an emptied place does nothing, so a place is dropped exactly once whatever path reaches the end of its scope, and a conditional move needs no flag of its own beyond the place. A value that moves in and out of a loop body is handled by the same rule, since the loop's frame drops what the body left.

A value whose type has a `Drop` method, or holds one, is registered with the runtime's guard stack when it is built and unregistered when it is dropped or moved, so that a panic can run the methods of the values still owned, innermost first. The guard stack is per task. A string, slice, map or pointer with no `Drop` method is not registered: a panic ends the program, or the task whose handle contains it, and memory the program will not use again is not a leak worth a push and a pop per value. A channel handle is registered: a handle a panic abandoned would keep the channel open for every other handle, a task waiting on it never seeing it end, where the plain memory only stays allocated, and a task holds few handles.

## Panics

A panic prints its message, runs the deferred calls and the drops on the guard stack, and exits with status 2, in any task. The LLVM backend keeps this mechanism in its first step: it is the runtime's, it costs nothing to a program that does not panic except the registration of `Drop`-bearing values, and it is what the differential test compares. Zero-cost unwinding through the IR's `invoke` and landing pads, which would remove the registration and run the drops of every frame from tables, is the step after, recorded here as an option and not a plan: it changes the drop discipline from a runtime list to a static one, and the two must be compared on the same programs before one replaces the other.

A deferred call runs on a panic too, since a `defer` says what must happen on every exit and a panic is one; Go runs its deferred calls as a panic unwinds, from the chain of `_defer` records its runtime keeps per goroutine, and Snello does the same through the guard stack it already keeps per task. Each `defer` statement becomes a function of its own, its thunk, whose one parameter is a record holding what the statement saved: the arguments, a callee that is a value, a receiver the method takes by value, and the address of a receiver it lends, by `ref` or `mut`, so that the call reads the variable as it is when the call runs, which the borrow rules let the function change until then. The record is a local of the function, at its top, so it lives until the function returns, or until the panic ends the process or reaches a test's mark; its first member is the flag that says the statement ran, clear from the function's entry, so a return the statement did not reach, past an `if` not taken, skips the call. When the statement runs, it sets the flag and registers the record's address and the thunk on the guard stack, as a value with a `Drop` registers its own address and its dropper. The call is written once, in the thunk, and both exits go through it: a return, for each flag set, at its place in the order below, takes the guard off and then calls the thunk, which the C compiler and LLVM inline; a panic calls it from the guard stack as it calls a dropper. The guard comes off before the call, so a deferred call that panics on a return is not run again by its own panic, and the panic runs the deferred calls and drops still registered below it, as Go runs the rest of a function's deferred calls when one panics (`defer.go` in the C backend, `deferStmt` and `leaveFunction` in the LLVM backend's `stmt.go`).

Both exits keep one order, the reverse of registration, as C++ runs its scope guards and destructors and D its `scope(exit)` statements: whatever was registered last, a value or a deferred call, is released first. The unwinding has it from the guard stack; a return writes it, the statement's temporaries, the variables of every open frame and the deferred calls that ran, merged in the order the function registers them, which the source gives, since a `defer` is refused inside a loop and a loop's variables are open at a return only in the pass that returns. A deferred call therefore runs before the drop of every value declared before its statement, which is everything it may borrow, and after the drop of a value declared after it, which it cannot name; the borrow checker's rule that a deferred call runs before the variables it borrows are dropped holds on both exits.

A deferred call that panics while a panic unwinds is a drop that panics: it ends the process with both messages, printed as for a `Drop`, under a test's mark too. Go lets the later panic replace the first because `recover` can stop either; Snello has no `recover`, so the two are reported and the process ends.

The cost is one push and one pop on the task's guard stack for each `defer` statement that runs, the same as one value with a `Drop`. A function with no `defer` pays nothing, and the panic path costs nothing until a panic. `defer` stays refused inside a loop, so every statement has one record and one flag, which a loop would turn into a list.

## A panic's trace

A panic printed its message and nothing of where it came from. It now prints the panicking task's stack under the message, one line per frame, innermost first, each the function as the program names it and the file and line the frame is at:

```
panic: index out of range [5] with length 3
	Grid.At at grid.snello:41
	render at main.snello:17
	main at main.snello:9
```

**Decided.**

- **The frames are the Snello functions on the task's stack**, the program's and the library's, each at the line of the call it is in, or of the panic itself in the innermost; a function of a package is named with the package, `json.Parse`, a method with its type, `Grid.At`, a generic instance with its arguments, `Map[int, string].Get`. The runtime's own functions, which are C, are not shown: a reader of the trace wrote none of them. A function the optimizer wrote into its caller is shown as a frame of its own, at its own line, above its caller at the line of the call, as a symbolizer shows an inlined call; without that, a release build's trace would name the caller at a line inside the callee.
- **A debug build's trace is exact; a release build's may lose a line, or a frame the optimizer wrote into another, never a frame of its own.** A release build's optimizer merges the ends of two paths that end alike, two panics of one function first of all, and the merged code is at no line: its frame is printed with its file alone, `main at main.snello`; where the merged code was a function's written into its caller, the inlined call's record is gone with it, and the caller's frame alone is printed, as a symbolizer shows the enclosing function where the inline information is gone. A debug build's own code is not optimized (*Debugger information*), and the standard library's, which the LLVM backend optimizes around it, is compiled with the merging of the tails and of the common code of two paths off, with the outlining of common code into a function of its own, the splitting of a function's cold code, a panic's path first of all, into one, and the jump a call a function ends in becomes, so that every call and every line is kept its own; the switches are clang's (`compiler/emit/llvm/build.go`, `DebugFlags`). The generated entry, which calls `main` and which the optimizer writes `main` into, is written at `main`'s position and under its name, so that merged code of `main` is still `main`'s frame; its own lines are the generated file's, which the trace does not show.
- **The trace is read before the unwinding**, so that the frames are whole before the drops and the deferred calls run, and printed with the message wherever the message is printed: for a panic that ends the program, and for a panic a task's handle contains, which prints its message as the program's runtime has it today, as Rust's panic hook prints the trace at the panic whether or not a join catches it. A panic under a test prints nothing at the panic, since the test's runner prints the failure after the unwinding; the walk keeps the frames for it, and the runner prints the trace under its failure line, the runner's own frames among them, as Go's runner shows its own.
- **The walk allocates nothing** and takes no lock but the error stream's: it follows the frame pointers, keeps the return addresses in a buffer the thread owns, looks each up in a table the binary carries, and writes the lines under the lock the message is written under, so that two tasks failing at once do not interleave. A panic inside the allocator, or with the heap exhausted, prints its trace as any other. A task under a test's catch keeps a copy of its frames, in a block the catch allocated before the test ran, since the runner prints the trace after the unwinding, which may have parked the task and moved it to another thread, whose buffer is another's.
- **The walk trusts no frame pointer it has not checked**, as Go's walk checks each frame against the stack's bounds: a frame pointer is followed only when it is above the last of its stack, aligned to sixteen bytes and, for a task, within the task's stack or the guarded stack a panic moved it to, whose frames link across; and the walk ends at the first return address no function of the table covers, which is the C library's or the loader's, since the program, the runtime and every binding's C are one object. The first frame of a task is made by `make_context` with every saved register zero, and a zero frame pointer ends the walk too; the main thread's chain on x86-64 Linux ends in a saved frame pointer that is garbage, from a C library built without frame pointers, which the table's rule ends the walk before, and the bounds rule is what turns a corrupt frame into a short trace rather than a second fault. The buffer holds 128 frames, and a deeper stack is shown to that depth.
- **The table is the compiler's**, made when the program is built, from the line information the backends' own compilers write, and read at run time by two binary searches a frame, over the functions by address and over a function's rows by offset; the runtime reads no debugging format at a panic, and a binary needs no debugging information beside it, nor its symbols: a stripped binary prints the same trace. Go's runtime reads its own tables the same way; Rust's reads the debugging format at run time, allocating, and only when asked.

**How, in the backends.** Both backends write the source position of what they emit, so that the compiler behind them carries it through to the code: the C backend a `#line` directive before each line of C it writes for a statement and before each function's head, which also puts the Snello file and line in the C compiler's own messages; the LLVM backend a location on each instruction and a subprogram on each function, the generated helpers and entry included, since LLVM drops the locations of a call inlined into a function that has no subprogram, the IR's line-table metadata and nothing more in a release build, and in a debug build the full information of *Debugger information*. `snello emit` shows the directives and the metadata as the compiler writes them, and `snello emit -debug` as a debug build has them. Both write a table of names beside the program, each function's symbol and the name the program gives it, since the line information names the symbol. Both compile a release build with line tables only, `-g1`, which gcc and clang both read, and a debug build with the full information a debugger reads (*Debugger information*), whose line tables are the same: the tables are data beside the code and shape no instruction, and both compilers write an inlined call as a scope of its own with the file and line of the call. Every function that calls another keeps its frame pointer (`-fno-omit-frame-pointer` with `-momit-leaf-frame-pointer` for the C, the frame-pointer attribute `non-leaf` on every function of the IR), which arm64's convention keeps already and x86-64 drops at `-O2`: a leaf is never below another frame, and a function that panics is not a leaf, so the walk loses nothing and a leaf keeps its register.

**How, in the build.** The table describes the native code the binary is linked from. A release build's link optimizes the program, the runtime and every binding's C as one, and the build keeps the native object the real link writes, with the internalizing and inlining the real link does: on macOS the linker is asked for it (`-object_path_lto`); on Linux with clang the linker's plugin is (`-plugin-opt=obj-path`, with the functions in one section, since the plugin otherwise gives each its own and the linker orders them); with gcc the object is a partial link's (`-r -flinker-output=nolto-rel`), which cannot internalize what a later object might name, at that cost, which only the C backend's tests on gcc pay, with gcc's cold code kept in each function's section. A debug build's objects are native already, the program's with its line tables, and the table is read from each, since a partial link on macOS keeps no line tables; the runtime's, which have none, give their functions anchors with no rows, which the walk passes over. The compiler reads the line tables and the scopes with Go's own reader of the format, from the Mach-O object, which holds its relocations' values in place, and from the relocated ELF object; a row no scope covers, since a compiler writing line tables alone writes no scope for a function nothing was written into, is the frame of the function whose symbol holds it. It writes the table as one block of bytes with no pointer in it, a header and its parts at offsets the header gives: the anchors, one per function of the object, each the function's address, left for the build to write, the length it covers and its rows; the rows, each an offset into its function and a frame; the frames, each a function, a file, a line and the frame of its caller, the chain of an inlined call; the symbols and the files, each an offset of its name in the strings; and the strings. Offsets are from the function's own start, since a function is whole wherever the linker puts it, and the linker does move one: macOS's linker moved a function of the runtime between the first link and the final one. The block is written by the compiler itself as a native object, a Mach-O or an ELF relocatable of one data section and two symbols, since a C compiler's run on a file of data would cost a build a fair part of its time, and linked with the native object in a plain final link, with no optimization left to do, which strips the debugging sections from a release binary on Linux and keeps them in a debug one, where a debugger shows Snello lines through the directives; then the build writes each function's address, read from the binary's symbols as the bounds of the tasks' stacks are, into its anchor, puts the anchors in order of address for the runtime's search, writes the header's reference with the table's own address, from which the runtime learns at a panic how far the loader moved the program, and writes the binary once, with the bounds of the tasks' stacks. On Windows the table is read from a first link's image rather than an object, since Go's reader of COFF applies no relocations to an object's debugging information: the first link keeps its DWARF, `lld-link /debug:dwarf`, and the object the link-time optimizer wrote, `/lldsavetemps:prelink`, for the final link, and the table's anchors are the functions the program's native objects define, that object or a debug build's own, while the C library's functions the link added bound the others' code and have no anchor (`trace.ImageTable`); the table's object is COFF, and the final link keeps a symbol table, `/debug:symtab`, which the patch reads, and is given no `-g`, so it writes no PDB and a release image keeps no DWARF. A function the binary has no symbol of its own for, or two of, keeps no address, and the walk ends at a frame of it; the runtime's test of its static names keeps two of one name from arising. The runtime carries a weak table of its own, empty, compiled to native code whatever the build's optimization, so that a program linked with no table, a probe or a C program, links and prints no trace, and so that the optimizer leaves the runtime's reads of the table to the link, where the program's table answers them, rather than folding the empty one into the code. Line tables are written for the program's own code alone: the runtime's files are compiled without, since the trace shows no line of the runtime's, and the optimizing link is the shorter for writing none. The build gains a read of the line tables and a plain link; a program's binary gains its table; a program that never panics pays nothing at run time beyond the frame pointer.

**How, in the runtime.** `sn_panic` records its frame pointer and switches, as it does, to the guarded stack a small-stack task unwinds on; `panic_unwind` walks from the recorded frame there, with the room a walk wants, before the drops: each frame's saved frame pointer and return address sit together at the frame's base on both processors, and the return address less one is inside the call; a frame of the runtime's, which no row of a Snello frame covers, is passed over, and the walk ends by the rules above. The frames go in the thread's buffer; where the message is printed the lines follow it under the stream's lock, each the chain's names, files and lines, the names through the table of names; under a test the runner reads the buffer through the runtime (`sn_testing_trace`), before the task parks again, and prints the lines under its failure line. A drop that panics while a panic unwinds walks from its own frame, through the unwinding's frames of the runtime, hidden, to the first panic's, so its trace shows the drop under the frames the first panic was unwinding; a panic on a thread of the runtime's own, the timers' or the poller's, with no task, walks the same way and ends at the first address outside the object.

**What it costs.** Measured against main on the 8-core arm64 Mac: the bench table within its spread on every row; a release binary of `hello` no larger, the table's bytes under what the frame pointer saves, and the `json` example's larger by 1.2 KB, a debug binary by 13 KB; a build of `hello` longer by 70 ms in release, the plain final link at 38 ms, the line tables of the program's compile at 11 ms, the optimizing link's writing of them at 10 ms and the signing of the patched binary at 13 ms, and by 30 ms in debug; 1 KB a thread for the buffer, and 1 KB a test under the runner. The final link is the floor of the design, which reads the table from the code the optimizing link wrote: the linker alone takes 27 ms on the two objects, and no option of it shortens that. A panic's own path grows by the walk, which is nothing a program pays for before it panics. The frame pointer on x86-64's non-leaf functions is the one cost the Mac cannot measure; the image's bench holds it.

**Memory safe, no collector.** The table is read-only data; the walk reads the stack it runs on within bounds it checks and writes to a buffer of fixed size; the unwinding runs every `Drop` and deferred call as it did.

**Considered and not taken.** A per-task record of the current line written at every call, which Go's runtime does not do either: a store a call. Reading the debugging format at run time, which Rust does: a parser in the runtime, allocation, and on macOS a binary carries no debugging information unless a bundle is made beside it. Anchors taken through the linker's relocations, one per text section, with a check that the layout held: the linker moves a function on its own, which a per-section anchor cannot follow and a check can only report. The table reserved in the binary at the first link and written in place, which would spare the final link: its size is known only from the code that link writes, and a reservation sized from the source would carry a fallback to the second link and bytes no program uses. The table compiled from C: a C compiler's run for a file of data costs 25 ms, and the object is a page of bytes the compiler writes itself. Keeping the optimizer's merging off in a release build too, so that every line is exact: code shaped for the trace's sake in every program, where the debug build is the build for an exact trace. Tables of the compiler's own line format in place of the compilers': both backends' code is laid out by the compilers behind them, which write the standard tables for nothing; what Snello adds is the compact form the runtime reads.

**The precedent.** Go's `pclntab`, its own function and line tables read by its runtime without allocation, its traces one frame a line with the file and line, and its walk checked against the stack's bounds; Rust's panic hook, which prints the trace at the panic, and its `backtrace`, which symbolizes the debugging format at run time when asked; the symbolizers, which show inlined frames above their callers and the enclosing function where the inline information is gone. Snello's tables are Go's in form and made from the standard line tables in the build, as Go's are made by its own linker.

**Tests.** The shared program `trace`, a panic three calls deep through a method, a function and `main`, prints the three frames with their files and lines through both backends, in release and debug builds, and with gcc; `trace-tail` holds a debug build to the frame of a function whose last act is the call that panics; `trace-closures` names a closure's closure; `trace-task-drop` has a drop panic on a task's small stack while its panic unwinds on the guarded one; `panicking-drop` and `defer-panics-unwinding` print the drop's and the deferred call's frames under the frames the first panic was unwinding; the runtime's `TestPanicTrace` walks a hand-written table over its own functions, four frames of a recursion under `main` and none of the runtime's; `TestTableAndPatch` in `compiler/emit/trace` reads the table of a compiled object and finds each anchor written with its function's address in the linked binary; the test runner's `TestBoom` shows the trace under a test's failure, which an expectation's failure does not have, since its message names its line. The book's chapter on errors has a section on what a panic prints.

## Debugger information

A debug build gave a debugger nothing to stop at. Built with `snello build -debug`, a program's `sum` at `main.snello:13` was `no locations` to lldb, through either backend, for three reasons: the optimizer, at `-O1` for the C and `-O2` for the IR, had written `sum` into `main` and folded its loop to the constant it returns, so that no instruction was at the line; both compilers wrote line tables and nothing more, so that no variable was described; and on macOS the linker leaves the debugging information in the objects it links, which the build's directory held and the build removed.

**Decided.**

- **A debug build is built for the debugger**: the program's own functions, of its main package and of its own packages, are compiled with no optimization, and the whole program, a package's C included, with full debugging information, so that every line of the program's has its instructions, a step goes from one line to the next, and every variable is in its slot for its whole scope; the standard library's functions are optimized, as before, and the runtime as before, optimized and with no debugging information, so that a step goes over a call of it as over a call of the C library. This is Rust's split: its `dev` profile is `opt-level = 0` with full information for the crate, over a standard library and a C library built optimized; Swift's debug build is `-Onone -g` over an optimized standard library; Delve asks Go for `-gcflags=all="-N -l"`, no optimization and no inlining. The LLVM backend marks the program's own functions as clang's `-O0` marks every function, `optnone` and `noinline`, and the standard library's code is optimized around them. The C backend compiles the whole of its C at `-O0`, the standard library's functions with the program's: clang, told to leave one function of an optimized file alone, joins its multiplies and adds into one instruction whatever `-ffp-contract` and the C standard's `FP_CONTRACT` pragma say (measured: `multiply-then-add` printed other digits), which the language forbids, and clang does not at `-O0`. Measured on the 8-core arm64 Mac, everything unoptimized made a debug build of `json` 2.4 times slower, nearly all of it in the standard library's parser, and left a task of the standard library's `testing` unbounded under the LLVM backend, whose call through the function it is given the optimizer had made direct; the split keeps both as they were in the LLVM backend, the default. A frame of the program's own at `-O0` holds every variable and temporary in a slot of its own, two to five times a frame at `-O2`: the stacks' analysis bounds a debug build's tasks from those frames as it does any build's, and counts `__memset_chk`, which an unoptimized build calls where an optimized one writes the stores, as the C library function it is, measured as the others are. A frame of a page or more calls the system's probe first, `___chkstk_darwin` on macOS and `__chkstk` on Windows, through a register loaded from the import table, which the analysis takes for a call through a pointer, in a release build as in a debug one: such a task runs on a guarded stack, as a task the analysis cannot bound always does, and no frame of the shared programs, at `-O0` either, is that large. A debug build overflows a stack sooner than a release one, as Rust's do. A release build's code is unchanged.
- **Every local and parameter of the program is described**, under its Snello name, in the block that declares it, with its type, so that a debugger prints it, and two variables of one name in two blocks are two. The C backend has this from the C compiler, which describes the C's locals: a local keeps its Snello name in the C, and the C backend renames one only where C cannot say what Snello does, a local that shadows one still in scope, since C puts a variable in scope inside its own initializer and a loop's step written after the body would reach the body's (*Calls, closures and generics*); a name a sibling block declared is free again when that block ends, as every Snello block is a C block. The LLVM backend writes what clang writes at `-O0`: each variable's slot declared to the debugger (`llvm.dbg.declare`), each parameter with its position, and a lexical block for each Snello block, the scope of the locations of the instructions within it. A closure's captured variables are described under their own names in the LLVM backend, as rustc describes a closure's and clang a block's: through the one slot that holds the address of the closure's box, by expressions of the family clang writes for a block: a capture copied into the box is at an offset in it (`DW_OP_deref, DW_OP_plus_uconst, offset`), and a capture lent to the closure is the address at that offset (`DW_OP_deref, DW_OP_plus_uconst, offset, DW_OP_deref`). The C backend reaches a capture through the record, `sn_env->count`, which C, with no implicit `this` such as a C++ lambda's captures are resolved through, cannot spell otherwise.
- **A type is described by its layout, under the C backend's names**, so that a variable prints the same through either backend and one set of formatters serves both, which reads a value by its members' names: `sn_int`, `int32_t`, `_Bool`, `sn_string`, `sn_slice_int`, `sn_opt_int`, `Point`. A struct is its fields, and `sn_live` after them when the type has a `Drop`; a string and a slice their `ptr`, `len` and `cap`, `ptr` a pointer to the element, a string's to `uint8_t`; an option of a pointer the pointer, and any other option `has` and `val`; a result `ok` and a union of `val` and `err`; an enum its `tag` and a union of one struct a case, named after the case, with the case's fields or `f0`, `f1`; a tuple `e0`, `e1`; a function value `fn` and `box`; a borrow, an owned pointer and a channel handle a pointer; a map and a trait value the runtime's records. Each backend's offsets are its own layout's, the same but where the LLVM backend puts the payload of an enum or a result at a word's boundary and the C backend at its members' alignment. An option of a pointer is the pointer, which the LLVM backend describes as a record of it alone, `val`, so that a formatter shows a null one as `None`. An enum's tag is an enumeration whose enumerators are its cases, each named with the length of the enum's name, the name and the case's, `sn_case_5_Shape_Circle`, since C's enumerators are names of the whole file and `Tok_Kind`'s `Eof` and `Tok`'s `Kind_Eof` would otherwise be one, as a C programmer's tagged union is described, so that a debugger names the case even with no formatter; the C backend declares the tag with that enumeration's type, of the size of the `int` it was. The LLVM backend writes the chains of names the C compilers write for a fixed-width type, `sn_int` a name of `int64_t`, a name of the system's `long long` or `long`; the LLVM backend's arrays are arrays, and the C backend's a struct around one, `at`, which C needs to copy an array. The C backend switches on and subtracts a tag as an `int`, which an enumeration with no negative value is not.
- **A function of the program's own is named as the program names it**, `sum`, `Grid.At`, `main.func1`, in the LLVM backend's debugging information, as the panic's trace names it, so that a backtrace shows the program's names and `breakpoint set -n sum` in lldb and `break sum` in gdb stop there; its symbol, `sn__sum`, stays the binary's, which a profiler reads. A debugger shows a function by the name its debugging information gives it, and reaches the symbol through the function's address. The standard of C++, Rust and Swift, a name and a symbol beside it as the function's linkage name, was tried and left: lldb and gdb show a C unit's function by its linkage name where they have no demangler for it, as they have none for Snello's symbols, so a debugger showed and stopped at `sn__sum` again. A function of the standard library keeps its symbol for its name, since the optimizer may write it into another, where it has no address of its own to reach a symbol by; the C backend's functions are named by their symbols, the one name C gives a function. The trace's table, which is keyed by symbols, takes a function's symbol from the object's symbol table, at the function's address, and from its linkage name or its name where it has none of its own.
- **Code the compiler writes is stepped through, not stopped in.** The backends' generated helpers, the droppers, printers, adapters, deferred calls' thunks and tasks' trampolines, call the program's own functions, a `Drop`, a formatting method, the function a value holds, so a step must pass through them to the program's code: the LLVM backend marks each as the compiler's, an artificial subprogram (`DIFlagArtificial`) whose locations are all at line zero, which DWARF reserves for code of no source line and which lldb steps through, as LLVM marks the code it makes, so that a step on a line that calls a helper stops in the program's function the helper calls, or on the next line. The C backend's helpers are at the lines of the generated file, which a step may stop in and the debugger shows no text of: C forbids a line of zero (C11 6.10.4), which only some compilers take. The inline functions of the runtime's header, which call no code of the program's, are `nodebug` where the compiler is clang, through a macro of the header's, since the emitted C does not know its compiler, and the script has gdb skip the header where it is gcc. The C backend's temporaries, `sn_t12`, are C locals, which a debugger lists with the program's, before they hold a value as after; the LLVM backend's are slots of no name, which it does not.
- **A file is named by the path the compiler read it from**, relative to the directory the build ran in, which both backends record as the compile directory, as gcc and clang record a source, so that a debugger finds the source of a program built from any directory; the trace still shows the file's base name. The standard library's files are the compiler's own, embedded with no copy on disk, and are named under a fixed absolute prefix, `/snello/std/json/json.snello`, as Rust names its standard library's under `/rustc/<hash>/library`, so that no file of the user's is taken for one; a debugger stops at their lines and shows their text once pointed at a checkout (`settings set target.source-map /snello/std CHECKOUT/std` in lldb, `set substitute-path` in gdb).
- **The debugging information is where the platform's debuggers look.** On Linux it is in the binary, as gcc, clang, Go and Rust leave it; a debug build was never stripped. On macOS, `snello build -debug` gathers it from the objects with `dsymutil` into `NAME.dSYM` beside the binary, before the build's directory is removed, as clang's driver does when one run compiles and links, whose objects are temporary as the build's are, and as rustc does by default (`split-debuginfo=packed`); lldb takes the bundle beside the binary when its UUID matches the binary's, so that a bundle a release build leaves behind is passed over. `dsymutil` is the one on the path, which on macOS is the developer tools'; a debug build without it fails, naming it. The builds the test suites make, which no debugger reads, gather nothing.
- **A value is shown as the program writes it, and the tasks are shown, by one command.** `snello debug FILE|DIR [ARGS]` builds the program as `snello build -debug` does and starts the platform's debugger on it, lldb on macOS, gdb on Linux and `cdb` on Windows, with Snello's script loaded (`12-platforms.md` has Windows'), as Delve's `dlv debug` builds and debugs in one command and as Rust's `rust-lldb` and `rust-gdb` load Rust's formatters: neither debugger loads a script a binary names unless the user has trusted its place, gdb by its `auto-load safe-path` and lldb, for a script in a bundle's `Python` folder, by its `load-script-from-symbol-file`, `warn` upstream and `trusted` in Apple's, so the command loads it. The script is one Python file, its half for lldb or for gdb chosen by the debugger that imports it, embedded in the compiler and written to the cache directory. It shows a string as its text, a slice as its elements, an option as `Some(v)` or `None`, a result as `Ok(v)` or `Err(e)`, an enum as its case and fields, `Rect(2, 3)`, and a map as its count, since its entries are untyped to the debugger. It adds a command, `tasks`, which lists every task of the program with its state, running, ready, parked or not started, and a parked task's stack in the trace's form, `main.sum at main.snello:13`, each frame's line the debugger's own and its name through the trace's table of names; a running task is its thread's, which the debugger's own backtrace shows, and an ended one is not listed. The walk over a parked task's frames keeps the trace's rules, a frame pointer aligned, above the last and within the task's stack or the guarded one a panic moved it to, and ends at the zero frame pointer a task's first frame has, so that a stale context ends a listing rather than misleading it. What the formatters read is capped by the debugger's own limits, its longest summary and most children, so that a corrupt length reads no more. Go's `runtime-gdb.py`, with its `info goroutines` and `goroutine N bt`, is the precedent; Go's own documentation says gdb does not understand Go programs well, its stacks and its scheduler first of all, which is what the command is for. `snello debug` also writes the embedded standard library to the cache directory and points the debugger's source map at it, as `rust-lldb` maps Rust's `/rustc/<hash>` to the installed sources, so that a debugger shows the text of the library the program was built with; the script and the library are named by a hash of their content and written whole before they are named; with the cache off they are written for the one session into a directory the system makes for it, which only the user may write, and removed after, so that no file another user put under a name known in advance is run as the script; and the command names the debugger it could not find before it builds.
- **Only a debug build keeps what `tasks` reads**: each task's record pushed once, at its spawn, onto a list the runtime never pops, since a debug build never frees a task's record, as Go's list of every goroutine never shrinks; and a table the runtime publishes under a symbol, of where the script finds the list's head and, in a task's record, its saved context, state, the function it runs and its link, each from `offsetof`, and of the frame pointer and return address in a saved context, constants beside the switch's assembly that a test of the runtime's holds to a parked task's saved frame. The script holds no layout of its own, as glibc publishes its descriptors for the debuggers' thread library and CPython 3.13 its `_Py_DebugOffsets`. A task's state is published after its context is saved, so that a parked task's context is whole. A release build's spawn is unchanged.
- **A profiler reads the same information.** `perf` on Linux and Instruments on macOS name a debug build's functions by symbol and its samples by Snello file and line; a release build's functions by symbol, since its line tables are stripped on Linux and not gathered on macOS.

**How, in the backends.** The C backend's directives name the file by its path, the standard library's under the prefix; its program and a package's C are compiled with `-O0 -g` in a debug build, with `-DSN_DEBUG` as before, after any line-table flag, since the last `-g` given wins. The LLVM backend's unit is `FullDebug` and not optimized (`isOptimized: false`) in a debug build, each of the program's own functions `optnone noinline`, `LineTablesOnly` and optimized as before in a release one, both DWARF 4 as before, which the debuggers and the trace's reader read as they read the C compilers' DWARF 5; its file nodes carry the path and, in a debug build, the working directory, which a release build leaves out, since a compile unit with a directory makes macOS's linker write a map of the objects into the binary, a few kilobytes of names of files the build removes; a function's type names its result and parameters, as clang writes them, so that a debugger can call it; `local`, through which every variable and parameter gets its slot, declares the slot with the variable's node; a closure's record is kept in a slot, which each capture is declared on; each frame a block opens has a lexical block, the scope of the locations written while it is the innermost; the drops a block's end writes are at its closing brace's line, as clang places a C++ destructor's call; and a type's node is written once, a named type's under a node its own fields may name through a pointer, each member at the offset the backend's sizes and alignments lay it at.

**How, in the build.** A debug build compiles the module optimized as the release build is but without link-time optimization, the program's own functions marked to be left alone, and the program's C and a package's at `-O0` with `-g` and a frame pointer in every function, a leaf's too, since gdb finds where a function gcc compiled for x86-64 starts after its prologue by the frame pointer's setup and stops a leaf with none before its parameters are in their slots, and the runtime as before; `GCCDebug` and the runtime's use of `ClangDebug`, which kept an optimized debug program's calls and lines its own for the trace, go, since the program's own functions are no longer optimized and the runtime's frames are not shown; the LLVM backend's module keeps the switches, `DebugFlags`, for the standard library's code it optimizes, whose frames the trace shows. `snello build -debug` on macOS runs `dsymutil BINARY -o NAME.dSYM`; the patching of the binary after the link, the trace's table and the stacks' bounds, changes neither its symbols nor its UUID. `snello debug` builds the same way and runs `lldb -o "command script import SCRIPT" -- BINARY ARGS` or `gdb -x SCRIPT --args BINARY ARGS`.

**What it costs.** Measured against main on the 8-core arm64 Mac, and in the image on arm64 Linux. A release build is unchanged: its build takes the same time, `hello` 273 ms against 276 and `json` 439 against 437 through the LLVM backend, and its binary is the same to the byte, but for 40 bytes of the trace's table in the C backend's `json` on Linux, whose program and library files of one base name are now two. A debug build of `hello` takes 15 ms longer on macOS, the gathering of its bundle, 40 KB beside the binary, and one of `json` the same or less, the C program compiling faster unoptimized; its binary on Linux is larger by its debugging information, 0.6 to 7 KB. A debug build runs as fast as before through the LLVM backend, within 4% on the bench's programs, and through the C backend from 1% slower to 2.8 times on `json`, whose time is the standard library's, unoptimized there. The compiler's C emitter makes 28% fewer allocations than before and writes 13% more bytes, the longer names of the files in its directives, each name quoted once a file where it was quoted at every line; the IR emitter makes 0.3% more allocations and writes 0.7% more bytes. The test suites take the time they took. A debug build's spawn pays one atomic push.

**Memory safe, no collector.** The information is data in the binary or beside it; the script reads the stopped process; at run time a debug build adds one link per task.

**Considered and not taken.** Compiling everything at `-O0`, one rule for every function: measured, it made the standard library's code two to three times slower in a debug build and lost a task's bound. Keeping `-O1`: measured, clang wrote `sum` into `main` and folded it; clang's `-Og` is `-O1`, and gcc's `-Og`, a level of its own, still leaves a variable out where its value is in no register. Writing the debugging information into the binary, as Go's linker writes its own into a segment, and on an external link copies `dsymutil`'s output into one: a Mach-O writer of the compiler's own for what the platform keeps in a bundle. Leaving it in the objects, as Cargo's `dev` profile does on macOS (`split-debuginfo=unpacked`): the objects are in the build's directory, which the build removes. Making a function's symbol the program's name, `main.sum`, as Go and Zig name symbols: the stacks' analysis takes a symbol with a dot for a compiler's clone, and the C backend's symbols are C's identifiers. A script the binary names, in gdb's `.debug_gdb_scripts` section or a bundle's `Python` folder, as Go and Rust do for gdb: both debuggers decline it by default, with a warning that asks the user to change a setting. Compiling the runtime with debugging information, so that the script reads a task through the runtime's own types: a step would then go into the runtime's C, and the script needs five offsets. Keeping a release build's line tables for a profiler, as Go keeps its information in every binary: a larger binary on Linux and a bundle and a `dsymutil` run on every release build on macOS, where Rust's release profile, by default, keeps no line either, and a debug build has them. Renaming every second local of a name in a C function, as the C backend did: a debugger then showed `sn_t7_i` for the second loop's `i`.

**The precedent.** The debug builds of Rust, Swift and Zig, and Go's `-N -l`, for no optimization and full information; clang's own output at `-O0` for the declared slots, the lexical blocks, a block's captures and a function's type; the C compilers' `-g` for the C backend; clang's driver and rustc for `dsymutil` on macOS; gcc, clang, Go and Rust for the information left in a Linux binary; Rust's `/rustc/` prefix for the standard library's files; clang's `nodebug` and Go's `<autogenerated>` for code that is not stepped into; Delve's `dlv debug` for the one command, `rust-lldb` and `rust-gdb` for the script it loads, and Go's `runtime-gdb.py` for the formatters and the list of tasks.

**Tests.** `TestDebugger` builds a program the way `snello build -debug` does, through both backends and on Linux with gcc too, its build directory removed so that macOS reads the bundle, and drives lldb on macOS and gdb on Linux in batch mode, under a timeout, gdb with address randomization left on as a container allows: it stops at a line, steps to the next and over a line that calls a helper, prints a local, a parameter, a struct's field, a captured variable and a variable of an inner block, two blocks' variables of one name each under its name, lists the source of a file in a directory below the one built from, and finds the stop in the backtrace; then, with the script loaded, prints a string, a slice, an option, a result and an enum as the program writes them, and lists the tasks, one parked on a channel with its stack, and again while main waits on a task stopped at a breakpoint; it also stops in a function of the program's own package and prints options of a pointer as `None` and `Some`. A test reads the debugging information of one program from both backends' objects with Go's reader and finds each type of one layout in both alike in its members' names and offsets, the names of fixed-width types compared after their chains; a test of the runtime's parks a task and reads its saved frame pointer and return address at the published offsets; the image installs Debian's `gdb`, with its Python. The LLVM backend's tests check the nodes of each kind of type and of a capture; `TestTableAndPatch` reads a table from an object at `-O0`; the trace's shared programs hold a debug build's trace unchanged; the C backend's tests hold the renaming to shadowing alone. The book's chapter on debugging and profiling shows an lldb and a gdb session, `snello debug` with its formatters and `tasks`, a `perf` session and an Instruments one through `xctrace`.

## Calls, closures and generics

A method is a function whose first parameter is the receiver, by value, as a `ref` or as a `mut`, under the layouts above. A function value is called through its pair: the function pointer with the box's address first. A generic function or method is written once per instance, with its type arguments substituted throughout, from a worklist that ends when no new instance is asked for; a trait's default method is one such instance per implementing type. Both backends emit the instances under the same names. The IR is one module per program, as the C output is one translation unit, which is what lets the optimizer inline a method across the program and remove the pair of a closure that never leaves its function.

A type a backend makes, a slice, an option or a tuple of others, is named by its parts, `sn_slice_int`, `sn_tup2_1A_3x_B`, each name of the program's among them after its length, as the Itanium C++ ABI's mangling writes a name, since a name may hold the underscore that joins the parts or be one of the words that name a kind: `(A_x, B)` and `(A, x_B)` were one name, and so were a `struct unit` beside `()`, and the C backend wrote one struct for both; no name and no kind's word begins with a digit, so a part that does is a name's length. An instance of a generic type is named in the runtime's space, `sn_g4Pair_int` for `Pair<int>`, which no name the program declares reaches, since a declared name that begins with `sn_` is written with an underscore after it: `Pair<int>` and a `struct Pair_int` were one (the shared program `mangled-names`). The LLVM backend quotes a name of the module that holds a letter past ASCII, `@"sn__größe"`, as LLVM's own printer writes one, in one pass over the module, which a module of ASCII alone passes through untouched.

A local keeps its Snello name in the C output, except where the name is taken already: by a local declared before it in the same C function, or by a type or trait of the program, which C writes under its own name too. Such a local is written under a temporary's number and its name, `sn_t12_cur`, where no name of the program reaches (after `cur := cur.Expect(...)` in a loop's body was found reading the new `cur` in its own initializer, as C puts a variable in scope there, and the loop's step written after the body reaching it). The IR names every local by its slot and has no such clash. The program's functions, top-level variables and constants are in the `sn__` space in both backends, `write` as `sn__write`, as Go's linker writes `main.write` (when link-time optimization, which merges the program and the runtime into one unit so that the runtime's small functions are inlined, bound the runtime's call of libc's `write` to a program's own `write`); and a name in capitals alone, the form of C's macros, `SIZE_MAX`, is written with an underscore after it, since no list of the headers' macros is complete.

Tasks and channels lower to the interface of `06-tasks-and-channels.md` in both backends: a spawn is a block of the moved arguments, built in the spawning function's frame and copied by `sn_spawn` into the task's record, which holds room for a few words of them and takes the rest from the system's heap, and a trampoline the backend writes that runs the call on the copy; a `select` is an array of cases handed to `sn_select`; the rest is runtime calls. Nothing about them is a layout question.

## Optimization

The C backend hands its text to the system's C compiler, at `-O2` with link-time optimization for a release build and, for a debug build, the program at `-O0` and the runtime at `-O1`, with wrapping arithmetic and strict aliasing switched off, and that is the whole of its optimization control. The compiler is the system's `cc`, clang on a Mac and gcc on most Linux systems, and clang on Windows, which has no `cc` and whose gcc builds for MinGW alone, and the runtime and the emitted C pass the warnings of both as errors; the C backend's tests build a set of programs with gcc where the system's `gcc` is gcc, as it is in the image the Makefile and CI run in, and is not on a Mac, where the name is clang's. The LLVM backend runs the standard pipeline and gains what it is for: a `ref` that is a pointer and not a copy, a `*T?` that is one word, inlining decided over the whole program, the removal of the dead stores that empty a moved place when nothing reads the place again, and the debug build's checks compiled out rather than switched off. Where the two differ in speed, the benchmarks say by how much, next to the table in `01-language-design.md`; this note promises no number.

## The runtime, compiled once

Both backends link every program with the runtime under `runtime/c/`, 26 files the C compiler turns into objects. Compiling them is nearly the whole of a build: for `hello` it is three quarters of a release build and nine tenths of a debug one, and the test suite builds hundreds of programs. So the runtime is compiled once for each compiler and set of flags and kept, and a build compiles only the program and links the runtime's objects.

- **The key.** An entry in the cache is named by a hash of everything its objects depend on: the runtime's sources and headers, the compiler, and the flags. The compiler is identified by the path it resolves to, the file's size and modification time, which a compiler rebuilt in place changes even when its version does not, and what `--version` says, which names its target too. The environment the compiler reads is in the key too: `CPATH` and `C_INCLUDE_PATH`, and on Apple systems `SDKROOT` and `MACOSX_DEPLOYMENT_TARGET`, as ccache hashes them. The backend enters the key through the compiler and the flags it compiles the runtime with: a debug build compiles the runtime the same way under either backend, and the two share an entry.
- **The system's headers.** The key cannot hold the headers the runtime includes from the system, which an update may change under the same compiler. When an entry is made, the compiler writes the headers each file read (`-MD`), and the entry's manifest records each with its size and modification time. A build that finds one changed sets the entry aside and makes it anew. A few hundred `stat` calls are the cost of a use.
- **Where it lives.** Under `runtime/` in `SNELLO_CACHE`, when it names a directory, else in `snello/` in the user's cache directory: `~/Library/Caches` on macOS, `$XDG_CACHE_HOME` or `~/.cache` on Linux, `%LocalAppData%` on Windows, as the book's chapter 32 lists them. `SNELLO_CACHE=off` turns the cache off, and every build compiles the runtime beside the program as before; so does a build that finds the cache unusable, a directory it cannot make or write, since the cache is a saving, never a requirement. A failure of the compiler on the runtime's files is the build's own, reported as it always was. Inside the Linux image the Makefile and CI run in, the cache is the host's, mounted, and CI keeps it between runs with the Go caches.
- **Two builds at once.** An entry is compiled in a directory of its own and renamed into place, so a build sees an entry whole or not at all. Of two processes that make one at once, the second to rename keeps the first's and removes its own. Builds of one process that miss the same entry wait for the first, so a test run compiles each entry once. An entry missing an object or its manifest is set aside and made anew.
- **Clearing it.** Removing the directory clears it; nothing else holds its state. An entry unused for five days is removed when another is made, and a use renews an entry's time at most once an hour. A directory left half made, or set aside, by a build that stopped is removed after an hour.

Nothing of the program is cached: its own C, and a package's C binding, change with the program and are compiled with it. A release build's link still optimizes the program and the runtime together, since the runtime's objects are the compiler's IR under `-flto`; the link reads only the parts the program reaches.

**Every function of the module names the runtime's processor.** LLVM writes one function into another in place of a call only when the processor the caller is compiled for has every feature the callee is compiled for. Clang names the processor and its features on each function of the runtime, `"target-cpu"="apple-m1"` and a list of features on an Apple machine; a function of a module that names none is compiled for the plainest processor of its kind, which lacks some of them, and then no function of the runtime is ever written into the program, whatever the link optimizes: a push, a map lookup and a string search each stay a call, and such loops run from one and a half to four times slower. So every `define` the emitter writes refers to one attribute group, as clang's and Rust's compilers put the processor on every function they write. The emitter knows nothing of the machine and writes the group at the end of the module holding a mark alone, since a group may not be empty; `llvm.Targeted` puts the target's attributes in the mark's place, and `llvm.Build` calls it on every module it is given, so that no way of building a program can leave them out, and `snello emit` calls it too, so that it prints the module as it is built. What the attributes are is asked of clang, by compiling an empty function for the module's triple, and the answer is kept in `target/` in the cache directory, since asking costs a tenth of a small build. The file is named by the triple and by the compiler as the runtime's cache knows one, its path, size and time and what it says its version is, since the clang on a Mac's path is a launcher that an update of the compiler leaves unchanged; a file that does not hold an answer is passed over and written anew; and a clang that cannot be asked fails the build, since a program built without the answer would run, slower, and say nothing. `TestRuntimeInlined` holds the result: a one-line function of the runtime that the program alone calls is gone from a release build's binary.

The mechanics are the established ones. The runtime is compiled on the user's machine and cached, as Zig compiles its `compiler_rt` and libc on first use and keeps them, rather than shipped prebuilt for each target, as Rust and Swift ship theirs: Snello's runtime is compiled by the user's own C compiler with flags that differ by backend and mode, and the cross build will name more targets. The key of every input is Go's build cache's and ccache's; the compiler's size and time beside its version are ccache's default check; the headers recorded from the compiler's dependency files are ccache's direct mode, and what Make and Ninja read; the rename into place is ccache's and Bazel's; the five days and the hour are Go's.

## Building for another platform

`snello build -target linux/arm64` builds the program for a platform other than the one the compiler runs on; `snello check` and `snello emit` take the flag too, so a package's files for another system are checked from any machine. The targets are the six the runtime supports, `darwin/amd64`, `darwin/arm64`, `linux/amd64`, `linux/arm64`, `windows/amd64` and `windows/arm64`, named as Go names them; any other is refused with the list, `unknown target freebsd/amd64: the targets are darwin/amd64, darwin/arm64, linux/amd64, linux/arm64, windows/amd64 and windows/arm64`, and a name that is not SYSTEM/PROCESSOR with the form. Without the flag the target is the host, and a build is what it was: no flag is added to any command, so the runtime's cache keeps its entries.

**What the target changes.** Four things, each where it already lives. The packages' files are chosen for it, `08-packages.md` section 7, the program's directory with them. The LLVM backend writes the target's triple into the module, `x86_64-unknown-linux-gnu`, and asks clang for that triple's processor attributes, as it asks for the host's. The C compiler compiles the runtime, the program's C and a package's C with the target's triple, `--target=`, which clang takes for every target from one binary; the flags are part of the runtime cache's key, so each target's runtime is compiled once and kept beside the host's. The link writes the target's binary: the trace's table as the target's object format, Mach-O, ELF or COFF for its processor, and the stack analysis and the signing read the binary's format, not the host's, so a Mach-O binary is signed and an ELF or a PE one is not, wherever it was built; the analysis does not read a PE binary yet, so a Windows program's tasks are unbounded; the analysis reads a Linux binary with the objdump for its processor, the system's own for the host's, else GNU's built for it, `x86_64-linux-gnu-objdump`, which a distribution's cross binutils install, else LLVM's, which reads every processor's and is a Mac's `objdump`. **A macOS binary names the oldest macOS it runs on**, 14.4, the first with the waits on an address the runtime's scheduler and locks are built on, in the triple of every macOS build, the host's included, `arm64-apple-macosx14.4`, so that a binary built with a later SDK runs on that version and every later one, as Go and Rust name a minimum for each target; without it clang names the SDK's own version, and a binary built on the newest macOS ran on no other.

**What a build for another platform needs.** A compiler that builds for the target, the target's system files and a linker that writes its binaries. Clang builds for any target; gcc is built for one, so a cross build through gcc needs a gcc built for the target named by `CC`, which `gcc -dumpmachine` must name, and is refused otherwise, `cc is gcc for aarch64-linux-gnu, which builds for its own target alone; set CC to clang, or to a gcc built for linux/amd64`; such a gcc links with the linker built with it, which reads its own link-time optimizer's objects, as Go's cgo and Cargo's `linker` setting use a cross gcc. The system files are the target's C library, its headers, start files and libraries, the kernel's headers and the compiler's support library: on a Debian or Ubuntu host, the distribution's cross packages, `libc6-dev-amd64-cross` and `libgcc-14-dev-amd64-cross`, put them where clang finds them with nothing set; anywhere else, macOS among them, the variable `SNELLO_SYSROOT_linux_amd64` names a directory holding them, a sysroot, which `--sysroot` gives the compiler. One variable per target, as the `cc` crate Cargo builds C with reads `CC_<target>` and `CFLAGS_<target>`, so one shell builds for both Linux processors. A build for Linux on a host that is not Linux, with no sysroot named, is refused before anything is compiled, with the variable to set. The linker is LLVM's, `ld.lld`, through `-fuse-ld=lld`, for every Linux that is not the host when clang builds: a Linux system's own `ld` writes its own processor's binaries alone, and macOS has none for ELF; it reads the link-time optimizer's options as the system's linker does, and a build refuses to start without it, `install lld`. macOS is built for on macOS alone, both processors with the SDK the host's compiler has; Apple's SDK and linker run on macOS and its licence keeps the SDK there, so a build for macOS elsewhere is refused, `takes Apple's SDK and linker, which run on macOS alone`. Windows is built for by clang alone, a gcc being refused, which builds for MinGW alone, linked by LLVM's COFF linker, `lld-link`, found beside the clang a build runs or on the path, against Microsoft's SDK and C runtime: on Windows those Visual Studio's Build Tools install, which clang finds, and elsewhere those in the directory `SNELLO_SYSROOT_windows_<processor>` names, laid out as the `xwin` tool writes them, which must hold the libraries of the target's processor (`12-platforms.md`, the toolchain).

**A sysroot.** `build/sysroot.sh linux/amd64 DIR` writes one from Debian's stable image, at the digest the development image pins, in the target processor's image under Docker's emulation: the C library's headers and libraries, the dynamic loader its `libc.so` names, the kernel's headers, which `usr/include/<multiarch>/asm` links into `usr/lib/linux`, and libgcc. A program built against it runs on that Debian and on any Linux with that C library or a later one.

**What building for another platform found.** Faults the host's builds never met. LLVM's linker writes the link-time optimizer's object with a section per function, whatever `-function-sections=0` asks, and every section of an object is at address zero: the trace's table, read from that object, gave each function the line rows and scopes of every other, and a panic's trace printed its frames twice. The table's reader now lays an ELF object's sections of code out one after another before reading its debugging information, as the link will, `trace.layOut`. The stack analysis read GNU objdump's x86-64 text, and a Mac's objdump is LLVM's, which writes a space after each comma and a mask as a signed number: every task of a `linux/amd64` program built on a Mac was left unbounded, and its text is now read to the same frames and calls, function by function, as GNU objdump's of the same binary. A gcc built for the other Linux, the C backend's other compiler, found the fourth: with the runtime's cache off, the runtime's objects are compiled into the build's directory, where the trace's table was written as `trace.o`, the name of the object of the runtime's `trace.c`, over it; the link's own files are now named with a dot in their stem, `trace.table.o`, which no runtime file's object has, and `TestLinkFileNames` holds them apart. On macOS x86-64, a thread-local variable is reached through a call of the descriptor `lea` loads, which the analysis now reads as the system's accessor, as it reads arm64's. But a bound counts each C library function at the stack it was measured to take, and the measures are of macOS on arm64 and of Linux on both processors, the systems CI runs `TestCLibraryStack` on; macOS's accessor of thread-local variables on x86-64 saves the processor's vector registers in a buffer sized at run time, larger than arm64's, and a bound too small is a task writing over its neighbour's, since small stacks are packed without guard pages. So a task of a `darwin/amd64` program that calls into the C library is unbounded and runs on a guarded stack, which is safe and larger, until the C library is measured on an Intel Mac; otool's listing of x86-64 also loses its place at a zero byte the linker pads with between functions. GitHub's Intel Mac now runs the suite in CI; a bound there still takes a listing of x86-64 that keeps its place, so the analysis takes it as no measured platform, `stack.Measured`.

**How it is tested.** `TestCrossBuild` builds two examples for every target but the host that the machine has the tools for, through both backends: `examples/bound`, whose packages bind C and choose files by platform, and `examples/pipeline`, whose tasks the analysis must bound for every target whose C library is measured; and it runs each where the machine can: under qemu's user mode for the other Linux processor, which the development image carries with Debian's cross packages and binutils, so CI's two Linux runners each build, bound and run the other's; under Rosetta for macOS on Intel from an Apple Mac. On a Mac with lld and the two sysroots it builds every Linux target, which runs in the Linux image. Where a Windows sysroot is named it builds both examples for Windows too and checks that each is a PE binary for the processor, and neither runs them nor checks their bounds, which the analysis checks only where the C library's stacks are measured, `stack.Measured`.

**The precedents**, run. Go sets `GOOS` and `GOARCH` in the environment and cross-compiles with no C toolchain while cgo is off; with cgo, `CC` must name a compiler for the target and that compiler a sysroot, which is Snello's case, since its runtime is C. Rust takes `--target` after `rustup target add`, which ships the standard library compiled for it, and leaves the linker and the C library to the user, through `CARGO_TARGET_<TRIPLE>_LINKER` or a container, `cross`. Zig ships the C library of every target with the compiler and needs nothing more, the one that does; Swift ships SDKs for a target as packages. Snello's compiler carries no C library, as Go's and Rust's do not, and takes the target as a flag, as Rust and Zig do, rather than from the environment, where a variable set for one build is left set for the next.

**Memory safety.** A build for another platform compiles the same checked program; nothing of the checker, the borrow rules or the runtime's ownership depends on the target, and no collector is involved.

## What it costs

- Two backends apply the rules of this note from two tree walks, and a rule changed in one must change in the other; the differential test is what makes that a test failure and not a drift.
- The LLVM backend's three changed layouts mean a program compiled by the two backends has values of different sizes; nothing in the language can observe that, and the runtime, which sees only the shapes it declares, is not touched.
- The guard stack stays, and with it a push and a pop per `Drop`-bearing value, until landing pads are measured against it.

## Precedent

Rust's MIR and Go's SSA are the lowered forms this note declines for now: each exists because its compiler has one backend and many analyses to run between the front and the back, borrow checking in Rust's case; Snello's checker does its analysis on the tree, and its backends have no analysis of their own to share. The null-pointer option is Rust's niche optimization in its simplest instance, applied to the one type where the language guarantees the niche. The inline closure box with a fixed size is how Swift passes closures that capture nothing escaping; the heap-allocated trait value with a table is Go's interface value, one allocation per conversion, which is also what Snello's `[]Shape` wants. The guard stack for drops under a panic is the register-and-unwind scheme of early exception runtimes, kept here for its simplicity until a measurement says otherwise.

## Package variables made on first use

A top-level variable whose initializer is a literal is a static of the output, as it always was. One whose initializer is a call, or anything else that is not a literal, is made on first use (`03-ownership-across-tasks.md`, package variables), and both backends write it the same way: the cell, zero until made; the runtime's `sn_lazy` beside it; the initializer as a function of its own, `NAME_init`, whose body is the assignment of the value to the cell, written as any statement is so that temporaries, drops and generic instances come for free; and a getter, `NAME_get`, that every use of the variable goes through, one acquire load of the lazy's state and a call of `sn_lazy_make` when it is not made, which returns the cell's address. The initializer's own mention of the variable names the cell, not the getter. A lazy variable that owns something is dropped at the end of `main` when it was made, after the plain statics. `lazyVar` in `compiler/emit/c/c.go` and `compiler/emit/llvm/llvm.go`; the programs `lazy-globals`, `lazy-cycle` and `lazy-panic` pin it through both backends.
